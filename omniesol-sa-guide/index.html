OmniEsol SA 실전 가이드

OmniEsol을 사용하는 사람들에게 꼭 필요한 ERP, UC, Kubernetes, Oracle, Network, Security의 기초 인프라 개념을 실무 언어로 정리한 책입니다.

집필 목적

이 책은 OmniEsol 제품 기능을 설명하는 매뉴얼이 아니다. 이 책의 목적은 OmniEsol을 실제로 도입하고 운영하는 사람들이 반드시 알아야 할 기초 인프라 개념과 실무 판단 기준을 정리하는 것이다.

ERP와 UC 시스템은 단순히 설치만으로 완성되지 않는다. 사용자 수, 동시 접속, DB 성능, 네트워크 구조, 방화벽 정책, SSL 인증서, Kubernetes 운영, 백업과 복구 체계가 함께 맞물려야 안정적으로 운영된다.

핵심 원칙: OmniEsol은 설치하는 시스템이 아니라, 안정적으로 운영되도록 설계해야 하는 업무 플랫폼이다.

1장 미리보기 — 정식 원고 읽기

1.1 OmniEsol을 인프라 관점에서 이해해야 하는 이유

OmniEsol은 기업의 업무 데이터를 처리하는 ERP 영역과 메일, 메신저, 협업, 알림 등 사용자 커뮤니케이션을 담당하는 UC 영역이 결합된 업무 플랫폼이다. 겉으로는 하나의 제품처럼 보이지만, 실제 인프라 관점에서는 Web, WAS, Database, Kubernetes, Network, Security, Backup이 결합된 복합 시스템이다.

따라서 OmniEsol을 안정적으로 구축하려면 기능 목록보다 시스템 구조를 먼저 이해해야 한다. 사용자가 접속하는 경로, 요청이 처리되는 계층, 데이터가 저장되는 위치, 장애가 발생했을 때 영향 범위가 어디까지 확산되는지를 파악해야 한다.

1.2 ERP와 UC의 성격 차이

구분ERPUC
핵심 목적회계, 인사, 영업, 구매 등 업무 트랜잭션 처리메일, 메신저, 협업, 일정, 알림 처리
중요 요소데이터 정합성, DB 안정성, 트랜잭션 무결성실시간 접속, 세션 유지, 외부 접속, 확장성

1.3 SA의 역할

OmniEsol 환경에서 SA는 단순 설치 담당자가 아니다. SA는 고객 요구사항을 인프라 설계 기준으로 변환하고, 제품 구조와 고객 환경 사이의 간극을 줄이는 역할을 수행한다.

SA 역할설명
아키텍처 설계ERP, UC, DB, K8s, Network, Security 전체 구조를 정의한다.
Sizing 기준 수립사용자 수, 동시 접속, 업무량, 외부 접속 기준으로 서버 자원을 산정한다.
설치 전 점검OS, 네트워크, 방화벽, DNS, NTP, Storage, Backup 준비 상태를 확인한다.
리스크 관리성능, 보안, 라이선스, 장애 격리, 백업/복구 리스크를 사전에 고지한다.
운영 기준 정의모니터링, 로그, 계정, 인증서, 패치, 장애 대응 기준을 수립한다.

OmniEsol 아키텍처 유형

OmniEsol 아키텍처는 제품 기준이 아니라 고객 도입 범위와 운영 리스크 기준으로 분류해야 한다. 책에서는 최소한 네 가지 표준 아키텍처를 다룬다.

유형설명권장 고객
ERP 단독형ERP 업무만 구축하는 구조. Oracle DB 안정성과 WAS 성능이 핵심이다.ERP만 도입하는 고객
UC 단독형UC 서비스를 Kubernetes 기반으로 구축하는 구조. 외부 접속과 실시간 연결이 핵심이다.그룹웨어/메일/협업 중심 고객
통합형 K8sERP와 UC를 하나의 Kubernetes 또는 공통 플랫폼 영역에서 함께 운영하는 구조.소규모~중견, 비용 효율 중시 고객
분리형ERP와 UC를 서버, 네트워크, DB, 운영 책임 관점에서 분리하는 구조.중대형, 공공, 금융, 장애 격리 요구 고객

통합형(K8s)과 분리형의 장단점

통합형(K8s)은 비용 효율형 구조이고, 분리형은 리스크 관리형 구조다. 아키텍처 선택은 서버 수를 줄이는 문제가 아니라 고객의 업무 중요도, 사용자 규모, 보안 요구사항, 장애 허용 범위를 기준으로 결정해야 한다.

비교 항목통합형(K8s)분리형
초기 구축비낮음높음
서버 수적음많음
구성 단순성높음낮음
장애 격리약함강함
성능 예측성중간높음
보안 분리제한적우수
확장성중간높음
장애 분석 난이도높음중간
권장 용도소규모/중견, PoC, 비용절감형중대형, 공공, 금융, 중요 업무
주의: 통합형은 비용과 운영 포인트를 줄일 수 있지만, UC 부하나 Kubernetes 장애가 ERP 서비스에 영향을 줄 수 있다. 운영 환경에서는 Resource Limit, Namespace 분리, Node 분리, DB 분리, 모니터링 기준을 반드시 설계해야 한다.
