1장. OmniEsol과 SA의 역할

ERP와 협업 서비스를 하나의 업무 플랫폼으로 바라보고, 이를 가능하게 하는 인프라 계층을 이해한다.

공개 기술서 이용 안내

독립 교육용 초안으로서 제조사의 공식 설치·지원 매뉴얼이 아니다. 실제 구축에서는 계약된 제품 범위, 공식 호환 버전, 고객 보안 정책과 승인된 변경절차를 우선한다.

1.1 OmniEsol을 이해하는 출발점

OmniEsol은 ERP 기능을 중심으로 그룹웨어, 문서관리, AI 등 기업 업무 솔루션의 연결을 지향하는 통합 비즈니스 플랫폼이다. 실제 도입 범위는 계약, 모듈, 버전 및 고객별 구축 조건에 따라 달라진다. 이 책이 다루는 것은 제품 화면의 메뉴 설명이 아니라, 사용자가 해당 업무를 처리하도록 지원하는 서버·네트워크·데이터·보안의 구조다.

사용자가 브라우저에서 로그인을 하고 전표를 조회한다고 가정해 보자. DNS가 서비스 주소를 IP로 해석하고, HTTPS 연결이 구성되며, Proxy나 Load Balancer가 요청을 애플리케이션 서버로 전달한다. 애플리케이션은 권한을 확인하고 데이터베이스에 쿼리를 실행한다. 같은 제품이라고 해도 이 흐름을 담당하는 시스템은 여러 개일 수 있다.

제품 범위의 근거

공개 제품 소개는 ERP, 그룹웨어, 문서관리, AI 등 기능 범위를 설명한다. 특정 DBMS·Kubernetes·WAS 배포 조합이 모든 고객에게 동일하다는 뜻은 아니다. ERP & More 제품 소개와 실제 지원 Matrix를 구분한다.

1.2 ERP와 UC의 업무 특성

ERP는 회계·인사·구매·영업·생산 등 업무 트랜잭션의 정확성이 중요하다. UC는 이 책에서 메일, 일정, 협업, 메시지, 알림 등 커뮤니케이션 기능을 설명하기 위한 실무적 분류로 사용한다. 실제 제품 구성과 계약 범위에 따라 해당 기능의 배포 단위가 달라질 수 있다.

분류ERP 업무UC/협업 업무
주요 요구정확한 입력·조회·수정·승인지속적인 연결·알림·파일/메시지 처리
주요 부하SQL, 업무 로직, 보고서, 배치세션, API, WebSocket, 파일 I/O
장애 영향업무 처리 지연·정합성 위험협업 기능 중단·사용자 경험 저하
관찰 항목DB 대기·WAS 풀·업무 처리 시간연결 수·오류율·큐 적체·스토리지
복구 우선순위정합성 검증과 트랜잭션 재처리전달 보장·메시지/파일 보존 확인

ERP는 성능이 중요하지 않고 UC는 데이터 정합성이 중요하지 않다는 뜻이 아니다. 둘 모두 안정성과 데이터 보호가 필수이지만, 성능 지표와 장애 분석의 우선순위가 다르다는 의미다.

1.3 WEB, WAS, DB의 역할

영역기본 역할현장 점검 포인트
WEB / Reverse ProxyHTTPS 수신, 라우팅, 정적 파일, 요청 전달HTTP 상태코드, 업스트림 연결, TLS 설정
WAS / AP업무 로직 실행, 세션·연결 관리스레드 수, JVM 메모리, DB 연결 풀
DBMS데이터 영속화와 트랜잭션 처리락, 대기 이벤트, redo, 백업·복원
스토리지데이터/로그/파일 저장과 I/O 제공Latency, Throughput, 공간, 다중 경로
인프라 공통DNS, 시간 동기화, 방화벽, 로드밸런싱설계 흐름과 실제 패킷 경로의 일치

3-Tier 구조는 역할을 구분하는 논리적 개념이다. 서버가 반드시 3대 필요하다는 뜻은 아니다. 반대로 단일 VM에 모두 구성해도 논리적으로는 WEB·WAS·DB 역할이 존재한다. 물리적 통합 여부는 Sizing·보안·지원 사양·장애 격리 요구를 검토해 결정한다.

1.4 Kubernetes를 이해해야 하는 이유

Kubernetes는 컨테이너를 실행하는 데 그치지 않고, Pod의 배포·스케줄링·상태 검사·서비스 진입점을 관리한다. 일부 업무 구성에서 컨테이너 기반 배포가 사용된다면 SA는 Pod, Node, Service, Ingress/Gateway, PVC의 관계를 이해해야 한다.

구성요소핵심 역할잘못된 판단
Node워크로드 실행 자원 제공노드 수=가용성 보장
Pod애플리케이션 컨테이너 실행 단위Running=정상 업무 처리
Service준비된 Pod에 연결할 추상적 진입점Service만 있으면 모든 Pod 연결
Ingress/Gateway외부 HTTP 요청 라우팅이것만으로 보안·인가 완결
PVC영속 스토리지 연결PVC=백업과 복구 보장
설계상 주의

Kubernetes를 도입했다고 무중단, 자동 확장, 데이터 무손실이 자동으로 달성되지는 않는다. 애플리케이션 설계, 스토리지, PodDisruptionBudget, 여유 노드, readiness 검증이 함께 필요하다.

1.5 OmniEsol SA의 역할

SA(System 또는 Solution Architect)는 개별 설정을 대신하는 사람이 아니라, 업무 요구를 기술 설계로 변환하고 각 구성요소의 관계를 정의하는 책임자다. 현장에서는 설치 기술보다 설계 의사결정과 검증 조건이 더 높은 가치를 만든다.

활동SA가 정의해야 할 질문산출물
요구사항누가 어떤 망에서 어떤 기능을 사용하는가?업무/접속 요구사항 정의서
아키텍처통합형·분리형·단독형 중 어떤 구조가 맞는가?논리/물리 아키텍처
용량부하는 얼마며 N+1과 성장 여유가 있는가?Sizing Matrix와 가정
보안데이터와 접근 권한의 신뢰 경계는?통신 경로/접근 통제표
운영누가 감시·복구·변경 승인하는가?운영 Runbook/RACI

DBA·보안담당·네트워크·제품 기술지원과 의견이 다를 때는 개인 경험만으로 결론을 내리지 않는다. 업무 영향, 공식 지원 범위, 시험 결과와 비용·위험을 근거로 Architecture Decision Record를 남긴다.

1.6 첫 번째 실습: 요청 흐름 추적

브라우저에서 “화면이 열리지 않는다”는 장애를 받았다고 가정하자. 서버를 바로 재시작하지 말고 영향 범위, 변경 이력, 관찰 가능한 로그를 확보한다.

1. 동일 URL의 내부망/외부망 접속 결과를 분리
2. DNS 응답 IP와 인증서 CN/SAN 및 SNI 경로 확인
3. TCP 연결 및 HTTP 상태코드 확인
4. Proxy가 연결할 백엔드 주소와 상태 확인
5. WAS 로그 및 DB 연결 풀/대기 확인
6. 실제 로그인·조회·저장 업무로 복구 검증
실습 완료 기준

사용자 → 네트워크 → WEB → WAS → DB 경로를 한 장의 그림으로 설명하고, 장애 시 계층별 담당자와 최소 수집 증거를 적을 수 있어야 한다.
