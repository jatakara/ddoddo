1장. OmniEsol과 SA의 역할

제품 기능을 나열하기보다 요청과 데이터가 이동하는 경로를 이해하는 것부터 시작한다.

독립 교육용 참조 원고

OmniEsol의 공식 설치·지원 사양을 대신하지 않는다. 구성 예시와 명령은 학습 및 검토용이며, 실제 고객 환경에서는 계약 범위·검증 버전·보안 정책·변경 승인을 확인한다.

1.1 OmniEsol을 시스템으로 이해하기

OmniEsol은 ERP 업무 기능과 협업·문서·AI 업무를 연결하는 비즈니스 플랫폼이다. 사용자는 하나의 웹 화면을 통해 업무를 수행하지만, SA는 그 화면 뒤에서 여러 계층이 어떤 순서로 요청을 처리하는지 파악해야 한다.

예를 들어 사용자가 전표를 저장할 때 브라우저는 HTTPS 요청을 전송하고, 진입 계층은 요청을 적절한 애플리케이션에 전달한다. 애플리케이션은 권한·업무 규칙을 검사하고 데이터베이스 트랜잭션을 수행한 뒤 결과를 반환한다. 이 경로 중 어느 하나가 실패해도 사용자는 'ERP가 안 된다'고 느낀다.

기술서의 범위

공개 자료에서 확인되는 제품 기능 범위와 일반적인 인프라 기술 원리를 구분해 서술한다. Kubernetes 또는 특정 DBMS가 모든 OmniEsol 배포에 필수라는 뜻은 아니다.

1.2 ERP와 협업 서비스는 왜 다르게 설계하는가

ERP는 회계·인사·영업·구매 등 기록과 변경의 정합성이 핵심이다. UC라는 이름으로 묶어 설명하는 협업·커뮤니케이션 서비스는 알림·메시지·파일·실시간 연결 등 부하 패턴이 달라질 수 있다. 두 영역을 같은 서버에 올리는 것과 같은 장애 도메인에 두는 것은 별개 문제다.

구분ERP 업무 영역협업/UC 영역
우선 보호 대상거래의 정확성, 일관성, 복구 가능성세션 지속, 메시지 전달, 데이터 보존
전형적 자원 부담SQL·잠금·배치·보고서접속 수·네트워크·검색·파일 I/O
진단 출발점오류 시점의 트랜잭션과 DB 대기특정 기능/클라이언트의 접속 경로
설계 시 주의DB 복구와 정합성을 분리해 검증세션·영속 데이터·메시지의 소유 계층 확인

구현 기술의 차이보다 중요한 것은 서비스 목표, 데이터 책임, 장애가 퍼지는 경로이다. 예를 들어 메신저 응답이 늦어지는 현상이 DB 쓰기 지연 때문이라면 Pod 증설만으로 해결되지 않는다.

1.3 기초 인프라 용어를 정확히 쓰기

용어현장에서의 뜻혼동하기 쉬운 점
WEB / Reverse ProxyHTTP 요청의 수신·라우팅·정적 콘텐츠 처리모든 업무 로직을 처리하는 WAS와 다름
WAS / AP업무 로직과 애플리케이션 실행서버 대수=처리량이 아님
DBMS데이터와 트랜잭션 관리백업 파일이 존재한다고 복구가 보장되지는 않음
VIP / Load Balancer접속 지점을 제공하고 백엔드로 전달백엔드가 모두 장애라면 VIP만으로 HA 불가
Kubernetes컨테이너 워크로드 배포·스케줄링·복구 플랫폼자동 복구가 데이터 무손실을 보장하진 않음
RPO / RTO허용 데이터 손실 시점 / 허용 복구시간복구 목표와 실제 시험 결과를 구분

아키텍처 문서에서는 용어 하나를 다르게 이해하면 잘못된 견적과 장애 책임 문제가 생긴다. '서버 이중화'라고만 쓰지 말고 WEB, WAS, DB, Storage, 네트워크 중 무엇을 이중화하는지 명시한다.

1.4 SA의 책임: 설계에서 검증까지

이 책의 SA는 Solution/System Architect로서 제품 서비스 목표와 고객 인프라 제약을 연결하는 역할이다. 모든 장비를 직접 설정하는 사람이라는 뜻은 아니다. 설계 결정의 근거를 기록하고, 전문 담당자가 검증해야 하는 조건을 남기는 사람이 SA다.

활동SA가 결정·검토할 일산출물
요구 정의업무 범위, 접속 대상, 중요 기능, RTO/RPO요구사항 정의·결정 기록
아키텍처ERP 단독/UC 단독/통합/분리 후보 비교논리·물리 구성도
사양 산정동접·업무량·성장·N+1 여유Sizing 가정 및 시험 기준
보안 협의신뢰 경계와 최소 통신 경로통신 흐름/방화벽 검토표
운영 인계시작·중지·관찰·백업·장애 대응Runbook 및 인수 조건

버전별 지원 조합, DB 라이선스 조건, 보안 예외 허용 여부처럼 SA 혼자 확정해서는 안 되는 사안은 제품 책임 조직·DBA·보안 담당의 검토를 받아야 한다.

1.5 장애를 설명하는 세 개의 질문

현장에서 “접속이 안 됩니다”라는 요청을 받으면 단순히 서버를 재시작하기보다 다음 세 질문을 순서대로 던진다.

  • 범위: 특정 사용자만, 외부망만, ERP만, UC만, 모두인가?
  • 시점: 언제부터이며 바로 앞서 변경된 인증서·DNS·배포·정책이 있는가?
  • 근거: 브라우저 오류·HTTP 상태·접속 로그·AP/DB 지표 중 어떤 증거가 있는가?
증상: 외부 모바일에서만 접속 실패
영향: 사내 PC 정상 / 외부 모바일 실패
우선 가설: 외부 DNS, WAF, TLS, Reverse Proxy 경로
증거: nslookup(내·외부), HTTP 상태, 요청 시각, Proxy 로그
주의: 원인 확인 없이 전체 서비스 재기동 금지
실무 원칙

상태 확인 → 가설 수립 → 영향 최소화 검증 → 변경 승인 → 조치 → 서비스/업무 검증 → 기록. 이 순서가 구성요소 이름을 외우는 것보다 중요하다.

1.6 학습 과제와 참고 근거

실제 고객 정보를 사용하지 말고 시험용 구조를 가정해 브라우저부터 데이터베이스까지 경로를 그려 본다. 각 구간에 필요한 프로토콜, 보안 통제, 로그를 1개씩 적는다. 마지막으로 어떤 단일 장애가 모든 사용자에게 영향을 미치는지 표시한다.
