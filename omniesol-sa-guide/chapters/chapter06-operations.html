6장. 운영 기본과 인수인계

서비스를 재시작하는 능력보다 상태를 관찰하고 안전하게 변경·복구하는 운영 습관을 정립한다.

독립 교육용 참조 원고

OmniEsol의 공식 설치·지원 사양을 대신하지 않는다. 구성 예시와 명령은 학습 및 검토용이며, 실제 고객 환경에서는 계약 범위·검증 버전·보안 정책·변경 승인을 확인한다.

6.1 운영의 기준은 프로세스가 아니라 업무 성공

WEB, WAS, DB, Kubernetes가 정상 기동 중이어도 사용자가 로그인하거나 업무를 저장하지 못하면 서비스는 정상이라고 볼 수 없다. 운영자는 인프라 신호뿐 아니라 실제 사용자 업무의 성공률과 응답시간을 관찰해야 한다.

측정 범주대표 지표판단 예
사용자 경험로그인 성공률, p95 응답시간, 5xx 비율특정 URI 또는 사용자군의 실패만 발생하는가?
애플리케이션JVM Heap/GC, Thread, 커넥션 풀DB 연결 대기 때문에 응답이 지연되는가?
데이터DB 대기·Lock·Redo/Archive트랜잭션 지속성과 I/O가 정상인가?
플랫폼Pod Ready, Restart, 노드 여유노드 1대 장애 시 대체 배치가 가능한가?
기반 인프라Disk/FS, NTP, TLS 만료, 백업공통 장애 위험이 누적되고 있는가?

특정 CPU 사용률 수치만으로 자동 장애 등급을 확정하지 않는다. 서비스 SLO와 부하 특성, 피크 업무 시간을 기준으로 경보 임계치를 검증한다.

6.2 일일·주간·월간 운영 점검

주기점검 내용남길 증거
매일서비스 업무 테스트, 주요 오류, Disk/DB 공간, 백업 결과상태 요약·이상 유무
매주패치·인증서 만료 예정, 리소스 추세, 접근 로그, 경보 정확도위험 목록·조치 담당
매월복원 샘플 시험, 용량 전망, 권한 리뷰, SLO 추이, DR 계획변경 제안서·운영 검토 기록
정기 훈련WAS/Pod 장애 전환, DB 복구·네트워크 경로 확인실측 RTO/RPO·개선 과제

운영 점검표의 목적은 모든 항목에 정상 표시를 하는 것이 아니라, 조기에 변화를 알아채고 조치 근거를 축적하는 것이다.

6.3 Linux·WEB·Kubernetes 읽기 전용 점검 예제

# OS 자원/기동 상태 확인
uptime
free -h
df -hT
ss -lnt
journalctl -p err -n 50 --no-pager

# 업무 HTTP 응답의 최소 확인 (가상 주소)
curl -I --connect-timeout 5 https://erp.example.invalid/

# K8s 가용 상태 (승인된 조회 권한만)
kubectl get nodes -o wide
kubectl -n example-uc get pods -o wide
kubectl -n example-uc get events --sort-by=.lastTimestamp
민감정보 취급

URL 쿼리·Cookie·토큰·DB 접속 문자열·사용자 정보는 로그 수집/공유 전에 검토·마스킹한다. 운영 점검 스크립트가 기밀값을 그대로 출력하거나 외부 서버로 전송하지 않도록 한다.

6.4 변경관리: 적용보다 원복을 먼저 준비

안정적인 운영은 변경을 피하는 것이 아니라 안전하게 변경하고 실패하면 예측 가능하게 되돌리는 능력이다. WAS/Reverse Proxy의 파라미터나 Kubernetes 이미지 태그를 변경할 때도 승인·스냅샷·검증·원복 절차가 필요하다.

  • 적용 전: 현행 설정 파일과 릴리스 버전, 변경 차이를 보관한다.
  • 적용 중: 동시 변경 항목 수를 최소화해 원인 추적성을 보장한다.
  • 적용 후: 서비스와 업무 거래, 보안 정책, 로그 오류를 함께 검증한다.
  • 실패 시: 원복 자체로 DB 스키마나 외부 데이터까지 되돌릴 수 있는지 별도 판단한다.

6.5 장애 대응 기본 Runbook

장애를 접수하면 먼저 영향 범위와 비즈니스 우선순위를 분류한다. 이어 최초 오류 시각과 변경 이력을 확보하고, 네트워크에서 데이터베이스까지 계층적으로 진단한다. 무분별한 재기동은 로그 증거와 세션 상태를 잃게 할 수 있다.

단계수행할 일종료 조건
1. 분류사용자·기능·접속망·발생 시각·업무 영향 확인영향 범위와 장애 등급 합의
2. 증거요청 ID/시간, HTTP 상태, WEB/WAS/DB/K8s 지표 수집재현 조건 또는 이상 구간 식별
3. 완화고객 승인 아래 우회·트래픽 분산·기능 제한추가 피해 최소화
4. 복구원인 조치 또는 검증된 원복기본 접속·핵심 업무 정상
5. 검증성능, 데이터 정합성, 보안 정책 재확인업무 담당 확인
6. 회고원인·타임라인·재발 방지·책임자 기록Runbook/경보 기준 업데이트

특히 HTTP 502/503/504는 원인이 다를 수 있다. 502는 업스트림 응답 문제, 503은 서비스 제공 불가, 504는 게이트웨이 대기 시간 초과의 전형적 신호지만 실제 맥락은 프록시 구현과 로그를 통해 확정한다.

6.6 운영 인수인계에 반드시 포함할 자료

산출물누가 무엇을 확인하는가
최종 구성도실제 VM/Node, VIP, FQDN, 통신, 저장소 매핑
검증 버전 목록OS·Middleware·DB·K8s·제품 릴리스 승인 내역
운영 절차서비스 기동/중지, 배포, 백업, 복원, 장애 에스컬레이션
계정 정책계정 소유자, 최소권한, 비밀정보 인계 수단
모니터링대시보드, 알림 수신자, 임계치 설정 근거
미해결 리스크담당자, 해소기한, 고객 확인 및 운영상 임시조치
비밀번호 전달

설치결과서에 평문 비밀번호를 넣지 않는다. 승인된 비밀관리 체계 또는 만료되는 안전한 전달 수단을 사용하고, 수신자와 권한을 분리한다.

6.7 운영 시작 7일 체크리스트

시점확인할 것
D+0접속·핵심 저장 업무·API·백업·알림 수신 검증
D+1업무 피크 로그와 오류·접속 경로·동시성 확인
D+2DB/스토리지 증가 추세와 응답 지연 분석
D+3운영자 계정·보안 경계·인증서 확인
D+4복구 절차와 데이터 보존 검증 계획 확인
D+5외부 모바일·내부 사용자별 차이 재확인
D+7이상 항목·향후 용량·미완료 리스크 인수인계

이 장은 운영 기본 루틴을 소개한다. 더 상세한 SLI/SLO, 모니터링, 장애 등급, 정기 검증은 14장 운영 점검과 SLO 및 15장 트러블슈팅을 참고한다.
