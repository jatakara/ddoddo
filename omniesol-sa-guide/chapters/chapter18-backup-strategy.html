특정 고객·제품 버전의 공식 설치·지원·복구 매뉴얼이 아니다. 모든 수치와 토폴로지는 가상 예시다. 실서버 복구·전환·삭제는 공식 지원 Matrix, 백업 소유자, 보안 정책, 변경 승인과 복구 훈련을 전제로 한다.

18.1 백업, 복원, 복구, HA, DR의 차이

ERP·UC 인프라를 설계할 때 “백업 서버가 있으니 이중화는 필요 없다”거나 “DB 이중화가 있으니 백업은 필요 없다”는 결론은 모두 위험하다. 각각 해결하는 장애 유형이 다르다. Backup은 복구 가능한 데이터를 보존하고, Restore는 사본을 되돌리며, Recovery는 로그 적용과 정합성 확인으로 사용 가능한 상태까지 전진시키는 과정이다. HA는 장애 중 서비스 중단을 줄이는 기술이고, DR은 주 운영 환경을 잃었을 때 대체 장소·절차로 업무를 복구하는 체계다.

개념목표대응 장애놓치기 쉬운 한계
백업(Backup)특정 시점 데이터 사본 보존삭제·논리 오류·랜섬웨어·장비 손실사본이 있어도 복원 성공을 보증하지 않음
복원(Restore)백업으로 데이터 파일 재구성DB·파일 손실애플리케이션 기동과 업무 검증은 별도
복구(Recovery)로그 적용·트랜잭션 정합성 확보백업 이후 데이터 차이필요 로그가 누락되면 목표 시점 도달 불가
HA단일 구성요소 고장에 대한 서비스 지속AP/DB/노드 일부 장애잘못된 데이터 변경은 복제될 수 있음
DR센터·공통 장애 도메인 손실 대응시설·스토리지·광역 네트워크 장애DNS·인증·외부 연계·운영자 접근까지 필요
SA 판단 원칙

HA, 백업, DR은 서로 대체재가 아니다. 하나의 DB 장애를 막는 구성과 고객 업무 데이터를 복구하는 구성은 별도 승인·시험이 필요하다.

18.2 업무 요구에서 RTO·RPO를 도출하기

RTO(Recovery Time Objective)는 사고 이후 업무를 다시 제공하기까지 허용하는 최대 시간이다. RPO(Recovery Point Objective)는 복구 시점에서 허용하는 데이터 손실 시간의 상한이다. 수치가 낮을수록 복제, 스토리지, 네트워크, 운영 인력 비용이 증가하는 경향이 있다. 이는 인프라 담당자가 단독으로 정할 수 없으며 업무 소유자의 승인이 필요하다.

업무 분류(교육용 예시)목표 RTO목표 RPO기술·비용 검토
급여·전표 확정 등 핵심 거래2시간15분지속 로그 보존, DR 사전 구성, 정합성 재처리
일반 업무 조회8시간4시간정기 백업+로그 복구 또는 복제 검토
검색 인덱스·재생성 가능 캐시24시간원본 기준 재생성원본 보호와 재구축 시간 검증

위 숫자는 공식 제품 권장값이 아닌 가상 업무 협의 예시다. 서비스별 RTO/RPO를 단일 시스템 전체에 기계적으로 적용하면 불필요한 비용이 발생하거나 중요한 데이터가 누락될 수 있다.

가정: 매일 02:00에 완전 백업 1회, 중간 로그 백업 없음
장애 시각: 같은 날 18:00
마지막 복구 가능 시점: 02:00
실제 손실 가능 구간: 16시간
다음 백업 직전 사고라면 손실 가능 구간은 거의 24시간
=> RPO 15분이라는 목표를 충족할 수 없음

백업 주기는 RPO를 결정하는 하나의 요소일 뿐이다. 마지막으로 원격에 안전하게 보존되어 실제 복구에 사용할 수 있는 로그의 시각을 기준으로 RPO를 검증한다.

18.3 ERP·UC 데이터 자산별 보호 Matrix

ERP DB만 백업하면 제품 전체가 복구된다고 볼 수 없다. UC는 메시지·파일·메타데이터·인증 연계 등 다중 저장소를 사용할 수 있다. 실제 저장 위치는 도입한 제품 모듈과 검증된 배포 구성에 따라 조사해야 한다.

자산보호 단위필수 정합성/복구 질문책임 주체(예시)
ERP 업무 DBDB 데이터·제어파일·복구 로그전표 Commit까지 재현 가능한가?DBA
UC 데이터베이스메시지·협업 메타데이터첨부파일·메타데이터 시점 일치?UC 운영/DBA
첨부파일/객체 저장소파일 본문·버전·메타데이터DB 참조 파일이 실제 존재하는가?스토리지/서비스
인증/SSO 연계구성·인증서·신뢰 설정복구 후 로그인·토큰 갱신 가능한가?IAM/보안
K8s 설정GitOps 매니페스트·CRD·PVC 매핑동일 버전과 의존성으로 재배포 가능한가?플랫폼 운영
배포 Artifact이미지·패키지·환경 설정원본 Registry 장애 시 재구축 가능한가?배포 운영
암호화 키TDE·백업 키·KMS·Secret 관리키 없이 복구가 불가능한가?보안/DBA
주의: 백업 대상 누락

DB 백업은 정상인데 암호화 키, 이미지 태그, 파일 저장소가 유실되면 서비스 복구가 실패할 수 있다. 자산별 복구 의존성 표를 백업 설계와 함께 관리한다.

18.4 복구 의존성 지도와 최소 복구 단위

기술적으로 DB가 열려도 인증서·DNS·Proxy가 준비되지 않으면 사용자 RTO는 달성되지 않는다. 따라서 RTO는 데이터베이스가 OPEN되는 시간이 아니라 승인된 핵심 업무가 성공한 시각까지 측정한다. 복구 절차는 인프라 의존성 순서와 데이터 정합성 순서를 함께 고려해야 한다.

복구 단위검증할 사용자 기능
DB 단독DB 연결·읽기·쓰기·Commit 및 복구 시점
ERP 업무로그인, 전표 조회, 승인·저장, 배치 재개
UC 협업로그인, 메시지·알림·파일 다운로드, 연계 API
전체 플랫폼ERP↔UC 링크·인증·공통 기능·외부 사용자 경로

18.5 백업 보존·복제·격리 설계

백업을 운영 서버의 같은 파일시스템에 보관하면 스토리지 손상이나 권한 탈취 시 함께 손실될 수 있다. 3-2-1은 복수 사본·서로 다른 저장 매체·외부 보관을 점검하는 출발점이며, 랜섬웨어 대응에서는 별도 자격증명·변조 방지·오프라인/격리 사본을 추가로 검토한다. 모든 환경에 동일한 제품·숫자를 강제하는 규정으로 해석하지 않는다.

설계 옵션장점한계·Trade-off
운영센터 로컬 백업빠른 복원·낮은 네트워크 비용센터 전체 장애에 취약
별도 백업 저장소운영 스토리지 장애 격리관리 계정 공유 시 동시 침해 가능
원격 복제/오프사이트센터 장애·데이터 손실 위험 감소회선·보존·복제 지연 비용
Immutable/Offline 사본삭제·암호화 공격 방어 강화보관 비용·키 관리·복구 절차 복잡화

백업 저장소는 별도 관리자 권한, MFA, 암호화, 키 복구, 감사 로그, 보존·삭제 승인 정책을 갖춘다. 복구 테스트 계정과 실제 운영 데이터 접근권한도 분리한다.
