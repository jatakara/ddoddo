20.1 모니터링과 관측성의 차이

모니터링(Monitoring)은 미리 정의한 정상·비정상 조건을 확인한다. 관측성(Observability)은 시스템 외부에서 얻은 신호로 내부 상태를 설명하는 능력이다. “CPU가 40%”라는 수치보다 “ERP 전표 저장 p95가 3초를 넘었고, 같은 시간대 WAS DB Pool 대기와 DB Lock이 늘었다”라는 연관 증거가 더 유용하다.

관점모니터링관측성
주요 질문지금 장애인가?왜, 어느 경로에서 느려졌는가?
기본 수단임계치·Health Check·알람Metrics·Logs·Traces·Topology·Change Event
강점비용·운영 난이도가 비교적 낮음복잡한 분산 요청의 원인 추적
한계알지 못한 실패 유형을 놓칠 수 있음수집량·보관비·개인정보 위험 증가

따라서 관측성은 모니터링을 대체하는 기술이 아니라, 기존 점검과 사용자 경험을 같은 시간축에 연결하는 운영 설계다. ERP/UC 서비스의 실제 배포 방식에 따라 수집 가능 신호는 달라진다.

메트릭은 대체로 집계 지표, 로그는 사건의 상세 기록, 트레이스는 분산 호출의 연결 관계를 표현한다. 모든 신호를 모든 컴포넌트에서 동일한 방식으로 얻을 수는 없으므로, 수집 범위를 먼저 결정해야 한다.

20.3 서비스 맵과 Golden Signals

사용자에게 중요한 서비스는 프로세스명이 아니라 업무 기능이다. ERP의 “로그인·전표 저장·조회”, UC의 “메시지 전송·메일 접근·파일 업로드”를 우선 서비스로 정의한다. 이후 각 기능에 Latency·Traffic·Errors·Saturation(일명 Golden Signals)을 연결한다.

서비스LatencyTrafficErrorsSaturation
ERP 전표 저장p95 저장 완료시간저장 요청/s실패 저장/전체 저장WAS Pool·DB Lock·Redo 지연
ERP 조회p95 응답시간조회 RPS업무 오류율DB Active Session·I/O
UC 메시지전송→확인 지연메시지/s전달 실패율큐 적체·Pod CPU·DB
UC 파일업로드 완료시간Bytes/s·요청/s업로드 실패율저장소 Latency·공간

실제 업무 성공률은 HTTP 200만으로 판단하지 않는다. 서버가 200을 반환해도 응답 본문이 비즈니스 오류를 포함하거나 SSE 스트림이 중간에 종료될 수 있다. 사용자 시나리오와 업무 결과를 별도 계측한다.

20.4 Trace Context와 로그 상관관계

분산 요청의 추적에는 W3C Trace Context의 traceparent 같은 표준 헤더를 사용할 수 있다. WEB→WAS→UC API를 거칠 때 Trace ID가 유지되면, 각 계층의 Span과 로그를 연결할 수 있다. 단, 프록시의 헤더 전달과 SDK의 계측이 함께 구현되어야 한다.

# 비식별 가상 로그 예시 (실제 값 아님)
2026-11-02T00:00:00Z service=erp-web
  trace_id=aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa
  route=/erp/document/save status=502 duration_ms=820
2026-11-02T00:00:00Z service=erp-ap
  trace_id=aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa
  operation=document.save db_pool_wait_ms=680 outcome=error
  • Trace ID는 요청 연결에 쓰되 사용자 실명·메일주소·토큰을 라벨이나 Span에 싣지 않는다.
  • 서비스명·환경명·버전·인스턴스·route 등 낮은 카디널리티 속성을 표준화한다.
  • DB 내부 추적은 성능·보안 영향이 있으므로 별도 승인과 샘플링을 적용한다.
  • 비동기 메시징은 Context 전달 실패 시 별도 Correlation ID와 전달 경계를 기록한다.
현장 판단

Trace가 보이지 않는다고 요청이 없었다고 단정하지 않는다. 미계측 구간, 샘플링, Collector Drop, 비동기 경계가 원인일 수 있다.

20.5 Collector 배치·비용·보안 Trade-off

방식장점단점/위험권장 검토 조건
Node Agent / DaemonSet로그·노드 신호 수집이 용이노드 자원과 권한 부담K8s 노드/호스트 로그 중심
Gateway Collector중앙 정책·배치·전송 제어집중 장애점·네트워크 비용서비스 간 표준화·격리 필요
앱 SDK 직접 전송트레이스·업무 계측 세밀함코드 변경과 송신 실패 처리 필요핵심 거래 계측
Exporter 기반 수집레거시 DB·WAS 연계 용이지원 지표 제한, 자격 증명 관리기존 플랫폼의 읽기 전용 진단

운영 Collector는 전송 실패 시 애플리케이션 요청을 막지 않도록 비동기 큐와 적절한 타임아웃을 사용한다. 그러나 큐와 배치에는 메모리 사용량 및 데이터 유실 Trade-off가 있다. 수집량·보관기간·샘플링·압축·접근권한·TLS를 함께 설계한다.

보안 체크

Collector/Exporter에 최소 권한을 부여하고 관리 포트는 공개망에 노출하지 않는다. 텔레메트리 파이프라인의 비밀값·개인정보 제거, 보존·파기 정책, 감사기록을 확인한다.
