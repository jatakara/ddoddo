공개 기술서 이용 안내

독립 교육용 초안으로서 제조사의 공식 설치·지원 매뉴얼이 아니다. 실제 구축에서는 계약된 제품 범위, 공식 호환 버전, 고객 보안 정책과 승인된 변경절차를 우선한다.

3.1 ERP의 3-Tier 아키텍처

ERP의 기본 이해를 돕는 모델은 WEB, WAS(AP), Database로 역할을 나눈 3-Tier 구조다. 이 구조가 특정 제품 버전의 고정 설치 방식을 뜻하지는 않는다. 각 계층이 어디에서 시작·종료되는지와 네트워크 정책을 분명히 하는 것이 핵심이다.

사용자가 문서를 저장할 때 WAS는 권한 확인과 비즈니스 검증을 거치고 DB에 변경을 요청한다. DB는 트랜잭션의 성공·실패를 결정한다. 화면 응답 속도는 사용자 네트워크뿐 아니라 AP 처리시간, DB 대기와 스토리지 지연을 합한 결과로 나타날 수 있다.

3.2 WEB·Proxy·WAS 구분

영역정상 동작 기준대표 장애증거
DNS/TLS정확한 서비스 IP와 유효한 연결해석 실패, 인증서 불일치DNS 응답·TLS 핸드셰이크
WEB/Proxy정상 백엔드로 라우팅502, 503, 504, 리다이렉트 반복Access/Error/Upstream 로그
WAS/AP업무 요청 처리와 결과 반환스레드 포화, 세션·메모리 문제WAS 상태, GC/Thread/Pool 지표
DBSQL 및 Commit 정상 처리락, Wait Event, I/O 지연세션·대기·실행계획

HTTP 502는 Proxy와 백엔드 통신 문제를 시사하지만 특정 원인을 확정하지 않는다. 503은 준비된 엔드포인트 부재 또는 서비스 불가 상황일 수 있으며, 504는 업스트림 응답 시간 초과가 흔하다. 요청별 로그와 재현 조건으로 확인해야 한다.

3.3 UC와 Kubernetes의 구성요소

Kubernetes 기반 서비스는 Pod, Service, Ingress 또는 Gateway, Node의 역할을 분리해 봐야 한다. 배포 단위가 컨테이너라고 해서 데이터 보존까지 자동으로 해결되는 것은 아니다. DB·검색 인덱스·첨부파일과 세션 저장소는 각자의 지속성·가용성 정책을 가진다.

구성요소역할운영 시 확인
Pod/Deployment워크로드 실행·배포Ready 상태·재시작·Requests/Limits
Service/EndpointSlice트래픽 연결실제 Ready Endpoint 존재
Ingress/Gateway호스트·경로 라우팅TLS·Path·버퍼링 정책
Persistent Volume영속 데이터 저장공유·백업·성능·볼륨 복구
Node/Cluster워크로드 실행 기반N+1 여유·CNI·DNS·Control Plane

3.4 데이터와 세션의 경계

ERP의 거래 데이터, 협업 서비스의 메시지·첨부파일, 캐시·세션은 보존 기간과 복구 중요도가 다르다. Redis와 같은 인메모리 저장소는 캐시와 세션에 활용할 수 있지만, 데이터 영속화가 필요한 서비스에 대한 단독 보존 수단이라고 가정하면 위험하다.

  • 업무 DB: Commit 무결성, 복구 가능한 시점, 권한을 명시한다.
  • 세션 저장소: TTL·로그아웃·장애 후 재로그인 허용 범위를 정의한다.
  • 메일·문서·파일: 원본 저장 위치와 메타데이터 DB의 정합성을 함께 점검한다.
  • 검색 인덱스: 원본으로부터 재생성 가능한지, 복구 시간을 얼마로 볼지 결정한다.
설계 원칙

서비스별 데이터 보존·백업 책임이 확인되지 않은 상태에서 'Kubernetes Pod가 자동 복구되므로 안전하다'고 결론내리지 않는다.

3.5 인증·네트워크 및 접근통제

포털에서 메뉴를 숨겨도 사용자에게 권한이 없는 업무 API는 서버 측에서 반드시 차단해야 한다. 외부 모바일 접속만 허용하려면 URL 경로만이 아니라 실제 API, 인증, 정적 리소스, 파일 다운로드의 호출 관계를 확인해야 한다.

검토판단 질문
DNS내부·외부에서 동일 FQDN이 어디로 해석되는가?
TLS인증서 SAN, Chain, 종료 위치가 일치하는가?
SSOERP·UC 토큰 전달과 만료 정책이 호환되는가?
Reverse ProxyHost, URI, WebSocket, SSE, Timeout 정책은?
인가권한 없는 API를 서버가 거부하는가?
감사중요 설정 변경과 외부 접속을 기록하는가?

3.6 기초 점검 명령과 업무 검증

아래는 단순 관찰용 예시다. 주소는 가상 도메인으로 표시하며 실제 고객 환경에서의 사용은 승인된 읽기 권한 범위에서 수행한다.

# 이름 해석 확인
getent hosts erp.example.invalid
# TLS/HTTP 응답 헤더
curl -I --connect-timeout 5 https://erp.example.invalid/
# 서버 리스닝 포트
ss -lnt
# Kubernetes 상태 확인 (권한/네임스페이스 확인)
kubectl get nodes
kubectl -n example-uc get pods -o wide
kubectl -n example-uc get svc,endpointslices

정상 종료 조건은 위 명령이 성공하는 것이 아니다. 승인된 테스트 계정으로 로그인, 목록 조회, 파일 처리와 업무 저장 등 실제 사용자 시나리오가 성공해야 한다.
