독립 교육용 참조 원고

OmniEsol의 공식 설치·지원 사양을 대신하지 않는다. 구성 예시와 명령은 학습 및 검토용이며, 실제 고객 환경에서는 계약 범위·검증 버전·보안 정책·변경 승인을 확인한다.

3.1 3-Tier의 실제 의미

ERP의 전형적인 3-Tier는 표현(Web), 업무 로직(Application), 데이터(Database)를 논리적으로 구분한다. 이는 반드시 물리 서버 3대가 필요하다는 뜻이 아니라, 운영상 역할과 책임을 분리하는 설계 원칙이다.

화면 반응이 느릴 때 브라우저 네트워크 탭의 TTFB가 길면 서버 측 처리나 네트워크를, 응답은 빠른데 렌더링이 느리다면 프런트엔드 로직과 정적 리소스를 살펴본다.

Reverse Proxy가 정상 실행 중이어도 백엔드 WAS가 준비되지 않았다면 502/503이 발생할 수 있다. 프로세스 기동, 포트 접속, HTTP 응답, 실제 업무 성공을 서로 다른 단계로 검증해야 한다.

3.3 Kubernetes UC 구조의 기본 원리

Kubernetes의 Pod는 배포·스케줄링 단위이며, Service는 변동되는 Pod 엔드포인트에 대한 안정적인 접근점을 제공한다. Ingress Controller는 HTTP(S) 진입과 라우팅을 담당할 수 있다. 실제 구성은 제품 패키징과 지원 버전, 로드밸런서 정책에 따라 다르다.

구성필요한 이유흔한 오해
NodePod가 실행될 계산 자원Worker를 늘리면 DB 병목도 해결된다
Pod애플리케이션 실행 단위Running이면 반드시 요청이 성공한다
Service/EndpointSlice준비된 Pod로 트래픽 연결Service가 있으면 엔드포인트도 존재한다
Persistent Volume상태 데이터 영속화 수단PVC 하나면 백업과 DR도 해결된다
Resource Requests/Limits스케줄링과 사용량 상한CPU Limit 초과 시 성능 영향이 없다

3.4 인증·세션·데이터의 경계

ERP와 UC가 같은 포털에서 연결되더라도 인증 토큰, 쿠키 범위, 세션 저장소, 데이터 접근 권한이 자동으로 동일해지는 것은 아니다. 서비스별 인증 연계가 어떻게 구현됐는지 확인하지 않으면 일부 메뉴가 보이지만 실행되지 않거나 반대로 허용하지 않은 기능이 노출될 수 있다.

  • 인증 경로: IdP/SSO 의존성과 토큰 갱신 경로를 기록한다.
  • 세션 경계: 브라우저 쿠키 SameSite, 도메인, HTTPS, 타임아웃을 확인한다.
  • 데이터 경계: ERP DB, 협업 DB, 파일 저장소의 보존/복구 정책을 구분한다.
  • 외부 접속: 프런트 메뉴 숨김이 API 접근 차단을 의미하지 않으므로 서버 측 인가를 검증한다.
보안 검토

접근 불가 요구사항은 화면 UI 숨김이 아닌 서버의 인증·인가와 Reverse Proxy·방화벽 등 방어 계층으로 검증한다.

3.5 요청 경로를 따라가는 읽기 전용 점검

아래 예시는 장애 상황에서 원인을 좁히기 위한 기본 관찰 명령이다. 지정된 권한과 정책 아래에서 실행하며 실제 주소는 임의의 가상값으로 대체한다.

# DNS 해석 (사내/외부 비교)
getent hosts erp.example.invalid

# TLS/HTTP 상태 및 응답 헤더 (데이터 기록 정책 준수)
curl -I --connect-timeout 5 https://erp.example.invalid/

# LISTEN 소켓 및 연결 상태
ss -lnt

# K8s (승인된 조회 권한으로)
kubectl get nodes
kubectl -n example-uc get pods -o wide
kubectl -n example-uc get svc,endpointslices

명령이 성공했다고 사용자 업무가 성공하는 것은 아니다. 실무 종료 조건에는 로그인, 실제 조회, 등록 또는 저장과 같은 업무 기능 검증을 포함한다.

3.6 아키텍처 선택 전 설계 질문

질문필요한 증거
ERP와 UC를 함께 도입하는가?도입 범위 / 서비스별 사용자 / 라이선스
외부 접근이 필요한 서비스는?FQDN·이용 주체·접속망·허용 URI
