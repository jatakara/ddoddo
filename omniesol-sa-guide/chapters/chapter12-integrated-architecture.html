12장 1부. 통합형 Kubernetes 아키텍처

12.1~12.4 · 공유 경계, 참조 구조, 선택 기준, 자원 경합

이 장의 전제

통합형은 ERP와 UC가 일부 인프라 자원 또는 운영 플랫폼을 공유하는 구성이다. 공유 물리 서버, 공유 Kubernetes 클러스터, ERP VM과 UC Kubernetes의 공통 가상화 기반은 서로 다른 설계다. 모두를 ‘ERP와 UC가 K8s에 올라간다’고 표현하면 배포 범위와 장애 책임을 잘못 이해하게 된다.

공식 제품 사양과 구분: 이 장은 일반적인 참조 아키텍처다. ERP 컨테이너화 가능 여부, UC 필수 컴포넌트, 지원 OS·Kubernetes·DB·CNI·CSI·라이선스는 해당 OmniEsol 릴리스의 공식 자료와 공급사 승인을 우선한다.

12.1 무엇을 공유하는가?

모델공유 자원대표 리스크
A. 인프라 공유형물리 서버, 가상화, 스토리지ERP가 VM에 있어도 호스트·SAN 장애는 UC에 전파될 수 있음
B. 클러스터 공유형Control Plane, Worker, CNI/CSI, IngressNamespace 분리만으로 공통 장애를 제거하지 못함
C. 하이브리드형일부 네트워크·인증·관측·운영 체계DB·AP·UC 실행 위치와 책임 경계가 모호해지기 쉬움

SA는 설계도에 ERP 실행 위치, UC 실행 위치, DB 위치, 공통 기반, 장애 도메인, 관리 주체를 각각 기록한다. 공유 영역을 숨긴 채 ‘논리 분리’만 강조하는 것은 기술적 부채다.

12.2 논리 참조 구성도

         [Browser / Mobile / Integration]
                      │ HTTPS
               [DNS / WAF / LB]
                      │
             [Ingress / Gateway]
                ┌─────┴─────┐
                │           │
         [ERP Service] [UC Service]
          [ERP Pods]*   [UC Pods]
                │           │
            [ERP DB]*   [UC Data]
                └─────┬─────┘
              [공유 K8s 기반]
     [Control Plane / Worker / CNI / CSI]
         [Monitoring / Logging / Backup]

* ERP Pods·DB는 제품 지원 범위에 따라
  VM 또는 별도 서버로 대체될 수 있다.

DNS, Ingress, 스토리지, 인증 서비스가 공통 단일 장애 지점이면 ERP·UC가 동시에 영향을 받는다. Control Plane의 HA만으로 애플리케이션 무중단을 보장할 수 없다.

핵심 질문: UC 부하 급증, Worker 한 대 장애, 공통 인증 장애 상황에서도 ERP 핵심 업무의 응답시간과 오류율 목표를 만족하는가?

12.3 통합형 vs 분리형: 트레이드오프

항목통합형분리형
비용공유로 초기 투자 절감 가능, HA 여유는 별도 필요중복 투자 증가, 서비스별 비용 귀속 명확
운영배포·관측 표준화 용이, 플랫폼 전문성 필요업무별 독립 운영 가능, 관리 포인트 증가
성능CPU·메모리·I/O 경합 관리 필요자원 예측성 향상, 과잉 프로비저닝 가능
가용성공통 실패 도메인 존재독립 장애 격리 용이, 공유 DNS/SSO는 예외
보안논리 격리 증빙 필요강한 운영·네트워크 분리 설계 용이
확장워크로드별 HPA 가능, 노드·DB 병목 검토서비스별 독립 증설 가능, 비용 증가

통합형이 항상 저렴하거나 확장성이 낮은 것은 아니다. 총소유비용(TCO), 피크 부하의 상관관계, 장애 영향, 규제 요건을 함께 검토한다.

12.4 CPU·메모리·I/O 자원 경합

자원증상대응 원칙
CPUERP p99 상승, throttlingrequests 실측, limits 재검토, 노드 풀 분리
메모리OOMKilled, MemoryPressureHeap/RSS/OS 예약량 구분
스토리지DB commit 지연, 파일 처리 정체IOPS·Latency 계측, 데이터 경로 분리
네트워크504, 연결 끊김LB·Ingress·CNI·DNS 구간별 확인

스케줄러는 주로 Pod의 requests를 기준으로 배치한다. ResourceQuota는 Namespace 총량, LimitRange는 개별 리소스 범위·기본값을 관리한다. 둘 다 모든 런타임 간섭을 제거하지는 못한다. DB는 제품 지원 범위 내에서 전용 자원을 검토한다.
