7장. Server Sizing Matrix

OmniEsol을 사용하는 사람이 서버 사양의 근거를 이해하고, 업무량·동시성·장애 여유·데이터 성장에 맞는 용량 계획을 수립하기 위한 실무 장.

7.1 용량 산정의 목적과 전제

Server Sizing은 서버 모델을 먼저 선택하는 작업이 아니다. 목표 응답시간과 가용성을 만족하기 위해 CPU, 메모리, 저장장치, 네트워크 및 운영 여유를 수치화하는 과정이다. ERP는 트랜잭션·SQL·배치, UC는 세션·알림·파일·검색 부하를 구분한다.

공식 제품 사양이 아님: 이 장의 수치와 산식은 일반적인 인프라 용량 계획을 설명하기 위한 가상 예시다. OmniEsol의 공식 최소·권장 사양이나 성능 보증이 아니다. 실제 제안에는 제품 지원 매트릭스, 라이선스 검토, 부하 시험과 공급사 확인이 필요하다.
업무 범위 → 동시성 → 요청량 → 자원 사용량 → HA·성장률 → 시험 → 최종 승인 순서로 결정한다.

7.5 CPU·메모리·스토리지 산정의 기본

CPU: 처리량과 실제 CPU 소비시간

RPS = 활동 사용자 수 × 사용자당 초당 요청 수
CPU 수요(core) ≈ RPS × 요청당 CPU 사용시간(초)
목표 코어 ≈ CPU 수요 ÷ 목표 평균 CPU 사용률

위 산식은 AP 계층 초기 추정이다. I/O 대기와 DB CPU는 별도로 계측한다. 캐시 적중률, GC, 배치, 장애 시 부하 이동과 요청별 편차를 시험으로 보정한다.

메모리: JVM Heap만 더하면 안 된다

WAS 메모리 예산 = Σ(Heap + Native/Metaspace + Direct Buffer)
                + OS/Agent/파일 캐시 + 안전 여유

DB는 SGA/PGA 및 OS 캐시를 별도 산정한다. Kubernetes는 노드의 물리 메모리가 아닌 실제 Allocatable과 Pod Requests/Limits를 비교한다.

스토리지: 용량과 I/O 성능을 구분

n년 뒤 데이터 = 현재 데이터 × (1 + 연간 증가율)^n
필요 공간 = 데이터 + 인덱스/로그 + 임시영역 + 여유

백업은 보존 주기, 전체/증분 방식과 변경량으로 별도 산정한다. 스냅샷만으로 복구 체계가 완성되지 않는다. IOPS, 읽기/쓰기 비율, 블록 크기, 지연시간 p95를 측정한다.

네트워크: 경로와 지연도 산정 대상

업무망·DB망·백업망, L4/L7, WAF, TLS 종료, 방화벽 세션, Reverse Proxy와 외부 연계 타임아웃을 확인한다. 대용량 파일과 백업 트래픽이 업무망을 잠식하지 않도록 한다.

7.6 Kubernetes 용량 산정

Pod의 requests는 스케줄링에 사용되며, limits는 사용량 제한에 영향을 준다. 노드 전체 자원에서 OS·kubelet·런타임 예약 자원을 제외한 배치 가능 자원을 기준으로 계산한다.

항목설계 판단
Requests / Limits실측 기반 설정, CPU Throttling·OOM 점검
Node Allocatable시스템 예약량을 제외한 실제 배치 자원
Replica / HPA최소 복제 수, 확장 조건, 시작 시간
N+1노드 1대 손실 후 필수 Pod 재배치 가능 여부
배치 제약Anti-affinity, topology spread, PDB
StatefulDB/캐시 영속성, 스토리지 장애, 백업·복구
보안Namespace/RBAC, NetworkPolicy, Secret, 이미지 검사
‘3노드 = 고가용성’은 성립하지 않는다. Control Plane, 스토리지, Ingress, Pod 배치 제약과 장애 후 잔여 CPU·메모리를 검증해야 한다.

7.7 가상 계산 예제

다음은 AP 계층의 계산 절차를 보여주기 위한 가상 데이터다. 실제 OmniEsol 실측치나 권장 사양이 아니다.

가정값
등록 사용자600명
피크 활동률25%
활동 사용자당 요청량0.2 RPS
요청당 AP CPU 시간0.10 CPU·초
목표 평균 CPU 사용률60% (가정)
활동 사용자 = 600 × 0.25 = 150명
AP 요청량 = 150 × 0.2 = 30 RPS
AP CPU 수요 = 30 × 0.10 = 3 vCPU
목표 코어 = 3 ÷ 0.60 = 5 vCPU

해석: 5 vCPU는 AP 정상상태의 이론치일 뿐 구매 권장 사양이 아니다. DB·배치·GC·HA·피크 편차·지원 사양을 반영한 뒤 부하 시험으로 확정한다.

메모리 예시

WAS 2개 × (Heap 8 GiB + Native 2 GiB)
+ OS/Agent 3 GiB = 23 GiB
운영 여유 20% 가정 → 27.6 GiB
→ 32 GiB급부터 시험 가능, 확정 사양 아님

DB 성장 예시

현재 DB 데이터 500 GiB, 연간 증가율 25% 가정
3년 후 데이터 ≈ 500 × 1.25^3 ≈ 977 GiB

인덱스·로그·백업·임시영역·복제 공간과 I/O 성능은 위 값에 포함되지 않는다.

7.9 사양 확정 검증 절차

  1. 측정값과 가정값을 구분해 문서화한다.
  2. 정상·피크 CPU, RSS·Heap, GC, SQL 대기, IOPS, p95를 계측한다.
  3. 로그인·조회·저장·보고서·배치·UC 혼합 부하를 재현한다.
  4. WAS/Pod/노드 장애, DB 전환과 백업 복구를 검증한다.
  5. 성장 시나리오와 증설 리드타임을 검토한다.
  6. 최소 권한, 암호화, 감사 로그, 이미지 취약점, 네트워크 경계를 점검한다.
  7. 목표 충족 여부와 잔여 위험을 승인 문서에 남긴다.
승인 기준: 목표 p95 응답시간, 오류율, 배치 완료 시간과 장애 복구 목표를 사전에 합의하고 시험 결과로 판단한다. 단일 CPU 평균값만으로 승인하지 않는다.

7.10 SA 사전 점검 체크리스트

  • □ ERP/UC 도입 범위와 피크 업무가 확인되었는가?
  • □ 등록 사용자와 실제 활동 사용자를 구분했는가?
  • □ RPS·p95·SQL 대기 등의 측정 근거가 있는가?
  • □ AP, DB, 캐시, 파일, 배치 부하를 구분했는가?
  • □ JVM 외 메모리와 DB 증가율, 백업 공간을 반영했는가?
  • □ K8s Node Allocatable 및 노드 장애 여유를 검토했는가?
  • □ L4/L7, WAF, DNS, TLS, 외부 연계 병목을 확인했는가?
  • □ 라이선스와 제품 지원 조건을 공급사와 확인했는가?
  • □ 성능·장애 시험과 변경관리 승인 이력이 있는가?
공개 자료 보호: 고객 식별 정보, 내부 IP·토폴로지, 실제 운영 로그, 비공개 제품 사양과 인증 정보를 GitHub에 공개하지 않는다. 사례는 익명·가상 데이터로 재구성한다.
