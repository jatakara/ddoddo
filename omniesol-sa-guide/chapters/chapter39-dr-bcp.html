39장 재해복구 아키텍처와 업무 연속성 설계

공개 교육용 참조 설계. 실제 제품 지원 조건 및 라이선스는 별도 확인한다.

39.1 HA와 DR

HA는 구성요소 장애를 견디는 설계이고 DR은 사이트 전체 손실에서 업무를 복구하는 설계다. 동일 전원·스토리지·관리망을 공유하면 서버 이중화만으로 사이트 장애를 견딜 수 없다. BCP는 업무 담당자, 대체 업무 절차, 외부 연계까지 포함한다.

사용자 → DNS / Global Traffic Manager
             ├─ 운영 사이트: WEB → WAS → DB
             │              UC → K8s → 데이터 저장소
             └─ 복구 사이트: WEB → WAS → DB 복제본
                            UC → K8s → 복구 저장소
별도 장애 도메인: 불변 백업 + 독립 관리 접근

39.2 복구 목표

RTO는 업무 중단부터 정상 업무 재개까지, RPO는 허용 가능한 데이터 손실 시간이다. 복제 지연만으로 RPO를 판단하지 말고 실제 복구 가능한 일관된 업무 시점을 확인한다.

방식장점위험
Cold낮은 상시 비용복원 및 설치 시간
Warm standby사전 구성 및 복제증설·전환 지연
Hot standby빠른 전환 가능상시 비용, split brain
Active-active자원 활용 및 분산쓰기 충돌, 세션 및 데이터 일관성

39.3 Oracle 복구

RMAN 백업 복원 또는 지원되는 복제 기술을 선택한다. Data Guard 사용 가능 여부는 에디션·계약을 확인한다. 복제는 삭제나 논리 오류도 전파하므로 독립 백업이 필요하다. DBA는 복구 시점, 아카이브 로그, PDB 및 업무 정합성을 검증한다.

SELECT database_role, open_mode, protection_mode FROM v$database;
SELECT name, value, unit, time_computed FROM v$dataguard_stats;

두 번째 조회는 Data Guard 환경에서 의미가 있으며 권한과 역할을 확인한다.

39.4 UC 및 Kubernetes

별도 클러스터를 준비하고 선언형 배포 상태, 이미지, Secret 복구 절차, PVC 데이터 및 외부 DB를 각각 검증한다. etcd 백업만으로 업무 데이터가 복구되지는 않는다. 사이트 간 단일 클러스터는 지연과 quorum 손실 위험을 별도 검증한다.

kubectl get nodes
kubectl get pods -A
kubectl get pvc -A
kubectl get storageclass
kubectl get endpointslices -A

39.5 DR Sizing

교육용 예: 복구 사이트 노드당 allocatable CPU 12, 목표 사용률 70%, 필수 업무 18 CPU라면 3노드 정상 25.2 CPU, 한 노드 장애 시 16.8 CPU로 부족하다. 4노드 장애 시 25.2 CPU다. 메모리, requests, 배치 제약, IOPS, 복제 대역폭도 별도 검증한다. 필수 업무만 수용하는 축소 DR은 업무 소유자 승인과 확장 리드타임이 필요하다.

39.7 Failback

신규 사이트 쓰기 이후에는 단순 DNS 원복 금지. 역복제 또는 재동기화, 쓰기 격리, 데이터 대사, 재전환 승인 순으로 진행한다. 양쪽 쓰기 활성화 방지를 위한 fencing을 검증한다.

39.8 비용과 보안

예시 RTO 60분: 선언 10분 + 데이터 복구 20분 + 업무 검증 25분 + 라우팅 10분 = 65분으로 실패. 병렬화는 의존성을 확인한 후 적용한다. 비용은 복구 서버, 라이선스, 복제 회선, 백업, 훈련 인력, 업무 손실을 포함한다. 관리 계정과 백업 삭제 권한을 분리하고 암호화 키 복구를 시험한다.

39.9 훈련 체크리스트

  • 사이트 장애 및 관리망 단절 시나리오
  • 복구 시점과 업무 재개 시간 실측
  • 외부 인증·메일·파일·배치 의존성 확인
  • 복구 사이트 N+1 및 데이터 정합성 검증
  • Failback 및 보안 권한 회수
  • 업무 소유자 승인과 개선 과제 등록
