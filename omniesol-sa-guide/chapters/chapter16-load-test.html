아래 시나리오·처리량·목표치는 모두 가상 예시다. 실제 제품 성능 보증이나 특정 고객의 운영 데이터가 아니다. 부하 시험은 승인된 비운영 환경에서 합성 데이터로 수행한다.

16.6 부하 시험의 여섯 가지 유형

한 번의 최대 RPS 시험으로 서버를 승인하면 장시간 메모리 증가, 배치 중 I/O 병목, 장애 후 재배치 실패를 놓치기 쉽다. 시험의 목적과 관측 지표를 먼저 분리한다.

시험목적가상 실행 예
Baseline낮은 부하에서 기능·관측 정상 확인목표의 20~30%로 기초 지표 수집
Step/Ramp부하 증가에 따른 포화 구간 확인60→90→120→150 RPS, 단계별 10~15분
Peak목표 업무 피크 처리 가능 여부120 RPS 유지, 업무 Mix 고정
Soak누수·연결 풀 누적·장시간 변동 탐지안정 부하로 수시간 지속
Spike짧은 로그인·배치 집중과 회복력 확인일시적으로 목표보다 높은 도착률
Failover노드/Pod 장애 후 서비스 지속승인된 Worker 격리 후 재배치·업무 검증

순서는 기능 확인 → Baseline → 목표 피크 → 장시간/확장 → 장애/복구가 합리적이다. 실제 운영에서의 강제 장애 주입이나 대량 트래픽 생성은 별도 영향 평가와 변경 승인이 필요하다.

부하 모델의 Trade-off

개방형(Open-loop) 부하는 지정한 요청 도착률을 유지해 포화와 큐 적체를 드러내기 쉽다. 폐쇄형(Closed-loop) 가상 사용자는 응답을 기다린 뒤 다음 동작을 수행하므로, 서버가 느려지면 실제 RPS가 떨어질 수 있다. 사용자 행동을 재현하는 시험과 최대 처리량을 측정하는 시험의 목적을 구분한다.

16.7 ERP·UC 혼합 부하 시나리오

ERP 조회, 저장·승인, UC 검색의 비중을 정하고, 성공 조건을 HTTP 응답이 아닌 업무 완료와 데이터 정합성으로 정의한다. 등록 사용자 수를 RPS로 단순 환산하지 않는다.

업무 시나리오요청 비중목표 RPS결과 검증
ERP 조회70%84조회 조건·페이징·권한·결과 값
ERP 저장/승인20%24Commit·중복·누락·인가
UC 검색/알림 조회10%12검색 결과·메시지 상태
합계100%120성공 요청만 처리량으로 집계

120 RPS를 60분 유지하면 총 요청은 432,000건(120×3,600)이다. 0.5%의 실패는 최대 약 2,160건에 해당한다. 이 수준을 허용할 수 있는지는 업무 중요도에 따라 별도 합의해야 한다. 금융·회계 등 거래 정합성 오류는 단순 오류율과 별도로 0건을 목표로 검증한다.

가상 시험 정의서 PERF-16-DEMO-01
환경: 비운영 / 합성 데이터 / 승인된 테스트 계정
도착률: 120 RPS, 60분
업무 Mix: ERP 조회 70% / 저장 20% / UC 조회 10%
예시 목표: 핵심 거래 p95 ≤ 1.5초, p99 ≤ 3.0초
예시 오류율: 0.5% 미만
데이터 중복·누락·무단 변경: 0건
장애 시험: Worker 1대 장애 후 성공 TPS·p95·복구시간 검증
중단 조건: 정합성 위험, 예상 밖 운영 영향, 보안 정책 위반
필수 증거: 스크립트 버전, 실제 RPS, 오류, Trace, WAS/DB/K8s 지표

동일한 키나 동일한 조회조건만 반복하면 캐시가 지나치게 잘 맞거나 락 경합이 비정상적으로 커질 수 있다. 합성 데이터의 키 분포, 문서 크기, 기간, 권한, 사용자 Think Time을 현실적인 비율로 설계한다.

Oracle DB의 성능은 DB CPU, Wait Event, 락, 실행계획, I/O 지연을 분리해 진단한다. AWR/ASH와 같은 특정 진단 기능은 별도 라이선스 조건이 있을 수 있으므로 DBA가 사용 가능 여부를 확인한다. 관측 결과에는 실제 수집 시간 구간과 데이터 소스를 명시한다.

도구 사용 시 주의

iostat는 sysstat 패키지 설치 여부에 따라 없을 수 있다. kubectl top은 지표 파이프라인이 있어야 동작한다. 읽기 전용 조회 명령만으로 성능 문제가 해결되지는 않는다.

16.9 성능 결과를 잘못 해석하는 다섯 가지 경우

잘못된 결론문제올바른 검증
평균 0.2초이므로 정상p99 10초 거래가 숨을 수 있음업무별 p95/p99와 오류율
CPU 40%라서 병목 없음DB 락·I/O·Pool 대기가 원인일 수 있음CPU와 Wait/Queue 동시 관찰
Pod 2배면 처리량 2배공유 DB·Storage가 병목일 수 있음증설 전후 동일 조건 시험
목표 RPS를 달성함오류 응답도 전체 RPS에 포함될 수 있음성공 업무 TPS와 정합성
p95가 개선됨캐시·데이터·부하 조건이 달라졌을 수 있음동일 조건 반복 측정

폐쇄형 부하 시험에서 서버가 느려질수록 요청 자체가 줄어드는 coordinated omission을 주의한다. 목표 도착률이 유지되어야 하는 시험이라면 일정한 도착률을 만들고, 실제로 보내지 못한 요청과 지연을 별도로 보고한다.

설정 변경 후 p95만 낮아졌더라도 DB 대기와 오류율이 상승했다면 병목이 다른 계층으로 옮겨졌을 수 있다. 지표를 한 묶음으로 판단한다.

16.10 결과 보고서와 Go/No-Go

보고 항목필수 기록
재현성스크립트·제품 버전·환경·데이터 생성 방법·설정 차이
성능목표/실제 성공 RPS, p50/p95/p99, 오류율
안정성GC·메모리 증가·Pod Restart·WAS/DB Pool 대기
정합성업무 저장 결과, 중복·누락·권한 위반
가용성장애 후 성공 TPS, p95, RTO/RPO, 데이터 검증
보안합성 데이터, 테스트 권한, 로그 마스킹, 외부 접근 통제
결정Go / Conditional Go / No-Go, 잔여 위험·책임자·기한
  • Go: 목표 피크에서 사용자 업무, 정합성, 장애 후 처리량, 복구 목표를 충족한다.
  • Conditional Go: 비핵심 잔여 위험이 기록되고 보완책·기한·책임자와 승인이 있다.
  • No-Go: 핵심 거래 SLO 미달, 정합성 실패, 보안 위반, 복구 목표 미충족이 남아 있다.
