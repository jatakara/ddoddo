13.5 DNS와 사용자 접속 경로

ERP와 UC 각각에 대해 내부 사용자, 외부 브라우저, 모바일, 외부 시스템의 접속 경로를 분리해 작성한다. 확인 순서는 FQDN → DNS 응답 → IP → 방화벽 → WAF/LB → WEB/Ingress → AP이다.

모델장점주의점
Split DNS: 동일 FQDN, 내부/외부 응답 분리URL 일관성, 내부 경로 최적화존·리졸버 관리, 인증서 일치
공인 DNS + Hairpin NAT공인 DNS 단일화방화벽 지원, 경로 비대칭 검증
내·외부 FQDN 분리접속·보안 정책 분리 명확SSO Redirect, 쿠키, CORS 복잡도

ERP는 내부 전용, UC는 외부 접속을 허용하는 경우 동일한 공개 경로를 강제할 필요가 없다. 내부 DNS Forwarder, 조건부 전달, 외부 사설 주소 노출 여부를 검증한다.

# 가상 주소를 이용한 읽기 전용 점검 예시
dig +short erp.example.com
dig +short uc.example.com
curl -I --max-time 10 https://erp.example.com/
curl -I --max-time 10 https://uc.example.com/

HTTP 200만으로 로그인·업무 API·WebSocket·파일 업로드가 정상임을 단정하지 않는다.

13.6 ERP↔UC 연계 계약

제품이 공식 지원하는 연계 방식을 우선한다. 일반적으로 서비스 간 연결은 인증된 API 또는 메시지 인터페이스로 제한하며 직접 DB 접근을 기본 허용하지 않는다. 데이터 소유권, 호출 주체, 인증, 타임아웃, 재시도, 멱등성, 오류 처리, 감사 추적을 계약에 명시한다.

항목설계 원칙피해야 할 부채
인증공식 지원 SSO/OIDC/SAML, 토큰 검증·수명 관리공유 관리자 계정, 토큰 URL 노출
서비스 호출허용된 API 경로와 서버 간 TLS영역 간 전체 포트 허용
재시도시간 제한, 백오프, 멱등키무제한 재시도로 연쇄 장애
정합성데이터 소유 시스템 지정, 실패 보상별도 DB를 하나의 트랜잭션처럼 취급
관측Correlation ID, 성공률·지연·오류율개인정보·비밀정보 원문 로그

실무 진단: UC 메뉴만 표시되지 않을 때 UC 서버 장애로 단정하지 않는다. DNS 응답, 메뉴 API 반환 URL, SSO Redirect, 쿠키 속성, CORS, 프록시 라우팅을 순서대로 확인한다.

13.7 보안과 확장성

경계필수 통제확장 시 검증
외부 접속UC 공개 서비스 최소화, ERP DB 비공개, WAF 예외 최소화신규 Ingress 경로 정책
영역 간 통신기본 차단, 필요한 출발지·목적지·포트만 허용노드·Pod IP 변경 대응
관리자 접근MFA, Bastion, 최소 권한, 접근 기록공통 계정 권한 확대 방지
인증서·비밀TLS 만료 모니터링, 비밀정보 회전다중 시스템 배포 자동화
취약점·패치OS·WEB/WAS·DB·K8s 지원 버전 검증서비스별 유지보수 창 조정
데이터최소 수집, 암호화, 보존·삭제 정책연계 복제본의 소유·삭제 책임

VLAN·Namespace만으로 완전한 보안 분리가 이뤄지지는 않는다. 관리 API와 백업 계정이 공유되면 횡적 이동 위험이 남는다. 외부 접속 범위가 확대되면 위협 모델과 허용 정책을 갱신한다.

13.8 RACI와 변경관리

RACI는 R(실행), A(최종 책임), C(협의), I(통보)를 의미한다. 아래 표는 조직에 맞게 수정해야 하는 예시다.

활동인프라팀ERP 운영UC 운영보안팀
DNS·LB·방화벽 변경A/RCCC
ERP 배포·복구CA/RIC
UC 배포·복구CIA/RC
보안 정책 변경RCCA
통합 장애 지휘ARRC

공통 인증·LB·DNS를 변경할 때는 두 서비스의 회귀 시험을 수행한다. 알림 채널, 원복 권한, 변경 동결 기간, 에스컬레이션 시간을 운영 문서로 연결한다.
