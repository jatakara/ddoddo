35.1 설치 자동화가 시험하기 어려운 이유

설치 성공은 프로세스 종료 코드 0이 아니라 서비스가 요구 상태로 동작하고 재시작 후에도 유지되는 것이다. 운영 서버를 직접 테스트 대상으로 사용하지 않는다. 실습 환경은 테스트 데이터, 별도 자격증명, 격리된 네트워크로 구성한다.

35.2 테스트 환경 계층

단위 시험은 DAG와 정책 판정 함수를 대상으로 한다. 계약 시험은 SSH Runner·Oracle Adapter·Kubernetes API의 입출력을 모사한다. 통합 시험은 가상머신과 컨테이너에서 파일 전송, 재접속, 서비스 기동을 검증한다. E2E 시험은 실제 지원 조합에 가까운 격리된 설치 환경에서 수행한다. DB나 UC 기능의 Mock 성공만으로 제품 설치 성공을 선언하지 않는다.

35.3 아키텍처별 Matrix

유형핵심 경로필수 검증
ERP 단독OS→DB→WAS→WEBDB 연결, 업무 요청, 재기동
UC 단독OS→K8s→UCNode/Pod, 서비스 연결, 메일 테스트
통합형공유 자원+ERP/UC자원 경합, 격리, 장애 영향
분리형ERP↔UCDNS/TLS/방화벽/연계

OS·DB·Kubernetes 버전 조합은 공식 지원 Matrix를 확인한 뒤 별도 관리한다. 여기서 특정 버전을 지원한다고 주장하지 않는다.

35.4 테스트 데이터와 초기화

VM 스냅샷은 반복 시험에 유용하지만 외부 DB, 스토리지, DNS 변경까지 자동으로 되돌리지는 못한다. 매 시험에 고유 run_id를 부여하고 가상 환경의 수명, 데이터 삭제, 테스트 계정 폐기를 명시한다. 개인 정보와 고객 데이터는 사용하지 않는다.

35.5 용량과 병렬 시험

동시 시험 수는 CPU뿐 아니라 RAM, IOPS, IP 대역, 이미지 다운로드 부하가 제한한다. 동일 스토리지에서 대량 VM을 병렬 부팅하면 설치 시간 측정이 왜곡된다. 기준 시험은 단독 실행, 확장성 시험은 별도 부하 조건으로 분리한다.

35.6 현장 체크리스트

  • 실제 운영망과 격리된 네트워크 및 테스트 자격증명
  • 테스트 대상별 OS·DB·K8s·아티팩트 digest 기록
  • 초기 상태 재현 및 테스트 종료 후 자원 정리
  • 지원 Matrix와 실제 설치 BOM 비교
  • 비밀정보 마스킹, 로그 접근권한 및 보존 기간 확인
