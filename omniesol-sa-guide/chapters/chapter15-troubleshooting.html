15장. 계층별 장애 대응과 트러블슈팅

DNS → TCP → TLS → Reverse Proxy → ERP WAS / UC Kubernetes → DB·Storage

장별 목차← 14장 2부책 소개

학습 목표와 적용 범위

증상만으로 원인을 단정하지 않고, 계층별 관측값으로 장애 위치를 좁힌다. HTTP 오류코드와 업무 실패를 구분하고, 복구 이후에는 사용자 여정·SLO·데이터 정합성·보안 상태를 함께 검증한다.

예시 IP(192.0.2.0/24)와 example.invalid는 문서용 값이다. 실환경에 적용하기 전에 대상·명령·권한·업무 영향·보안 정책을 확인한다. 모든 SLO 및 임계값은 교육용이다.

15.1 장애 대응의 목적: 빠른 복구와 근거 기반 진단

장애 대응은 ‘어느 서버를 재시작할 것인가’가 아니라 사용자 영향과 데이터 위험을 통제하면서 실패한 계층을 증거로 좁히는 과정이다. ERP 저장 실패는 데이터 정합성이, UC 접속 실패는 인증·세션·실시간 연결이 핵심일 수 있다. HTTP 200, Pod Running, CPU 정상만으로 업무 정상 여부를 판정하지 않는다.

사용자 경험 실패 확인
  → 영향 범위(ERP/UC, 내부/외부, 기능/사용자, 발생 시각)
  → 공통 의존성(DNS/인증서/WAF/SSO/LB)
  → 접속 계층(DNS → TCP → TLS → HTTP/Proxy)
  → 실행 계층(ERP WEB/WAS 또는 UC Ingress/Service/Pod)
  → 데이터 계층(DB/Queue/Storage)
  → 승인된 완화·원복 → 업무 재검증 → 사후 분석

본 장은 공개 교육용 참조 Runbook이다. 제품별 설정 키, 포트, 공식 지원 버전, 운영 변경 절차는 고객의 검증된 설계서와 제조사 자료를 우선한다. 예시 도메인과 IP는 실제 고객 정보를 포함하지 않는다.

15.4 DNS와 네트워크: 이름이 맞아도 경로는 틀릴 수 있다

내부/외부 사용자가 같은 FQDN을 사용하더라도 서로 다른 IP로 해석될 수 있다(Split DNS). 외부 IP를 내부에서 사용한다면 NAT loopback(Hairpin NAT) 지원 여부를 별도 확인한다. 특정 단말의 hosts 수정은 임시 진단 도구일 뿐 표준 운영 설계가 아니다.

# Linux: 서버에서 사용 중인 resolver와 DNS 응답 확인
cat /etc/resolv.conf
getent ahosts erp.example.invalid
dig erp.example.invalid A
dig @192.0.2.53 erp.example.invalid A    # 예시 DNS 서버(문서용 IP)

# TCP 연결 확인: 정책 승인된 목적지에만 실행
nc -vz -w 3 192.0.2.20 443
ip route get 192.0.2.20
ss -tn state established '( dport = :443 )'

판정: 이름 해석 → 목적지 IP → 경로 → TCP 3-way handshake → TLS → HTTP → 실제 업무 호출을 분리 기록한다. dig 결과와 브라우저 결과가 다르면 단말 DNS 캐시, 프록시/PAC, VPN, DoH, IPv6 우선순위를 비교한다.

운영 서버에서 대량 포트 스캔·임의 방화벽 개방은 금지한다. 보안장비 차단 로그와 변경 승인 기록을 우선 활용한다.

15.5 TLS·HTTP·Reverse Proxy: 502/503/504를 분해한다

# GET 기반 상태/타이밍: 인증정보 없이 허용된 진단 URL만 사용
curl -sS -o /dev/null -w 'code=%{http_code} remote=%{remote_ip} connect=%{time_connect} tls=%{time_appconnect} ttfb=%{time_starttransfer} total=%{time_total}\n' \
  --connect-timeout 3 --max-time 10 https://erp.example.invalid/health

# DNS를 우회해 특정 백엔드 VIP의 SNI/Host 동작 확인 (TLS 검증 유지)
curl --resolve erp.example.invalid:443:192.0.2.20 \
  -sS -o /dev/null -w '%{http_code} %{time_total}\n' \
  https://erp.example.invalid/health

# 인증서 체인·SNI 점검 (출력에 개인정보 없음)
openssl s_client -connect 192.0.2.20:443 \
  -servername erp.example.invalid -showcerts </dev/null
코드뜻(대표적)점검 순서
502게이트웨이가 upstream의 유효 응답을 받지 못함Proxy 오류 로그 → upstream TCP/TLS → Host/SNI → HTTP 프로토콜 → WAS 로그
503가용 백엔드 없음/과부하/서비스 준비 안 됨 등LB healthy pool → K8s EndpointSlice → readiness → 배포 상태
504upstream 응답을 제한 시간 내 받지 못함connect vs read timeout → WAS thread → DB wait/lock → 외부 API

진단 시 유의: curl -k로 인증서 검증을 무력화한 결과는 운영 정상 증거가 아니다. 필요 시 테스트 용도로만 사용하고, 정상 판정에는 반드시 체인 검증을 포함한다. curl -I는 HEAD를 지원하지 않는 서비스에서 오해를 낳으므로 실제 읽기 전용 GET을 사용한다.

Proxy 제품별 설정은 상이하다. WebtoB 등 제품 전용 지시어는 적용 버전의 공식 문서 및 구성 검증 없이 다른 환경에 복사하지 않는다.

15.6 HTTP/2·SSE·WebSocket: 장기 연결은 일반 요청과 다르다

UC 알림이나 AI 스트리밍과 같은 SSE는 서버가 응답을 지속 전송한다. 프록시 버퍼링·압축·HTTP/2 처리·WAF 검사·idle timeout이 개입하면 최초 200 이후 이벤트가 지연되거나 끊길 수 있다. WebSocket은 HTTP Upgrade 및 중간 장비의 연결 유지 정책을 확인한다.

# 승인된 테스트 엔드포인트에서 SSE 스트림 관찰
curl --http1.1 -N --max-time 20 \
  -H 'Accept: text/event-stream' \
  https://uc.example.invalid/test-stream

# HTTP/2 협상 및 헤더 확인 (민감한 쿠키/토큰 출력 금지)
curl --http2 -sS -o /dev/null -w 'version=%{http_version} code=%{http_code}\n' \
  https://uc.example.invalid/health
확인 항목정상 판단주의
첫 이벤트 도착지정된 기준 시간 내 이벤트 수신200 응답만으로 성공 판정 금지
연결 유지정해진 유지 시간·heartbeat 충족중간 프록시 idle timeout 확인
프록시 버퍼링스트림이 의도대로 즉시 전달일괄 버퍼링이 지연 유발 가능
HTTP/1.1 vs HTTP/2지원 조합에서 동일한 기능 결과무분별한 전역 HTTP/2 해제는 성능·호환성 영향
WAF 예외정확한 경로·메서드·기간에만 적용전체 경로 예외는 보안 부채

HTTP/2 비활성화, WAF 예외, 압축 변경은 반드시 범위를 최소화하고 A/B 검증·원복 계획을 수립한다. 제품과 프록시별 지원 조합이 다르므로 특정 프로토콜을 무조건 권장하지 않는다.

15.7 ERP WEB/WAS/DB: 지연의 원인을 계층별로 구분한다

ERP 저장 지연은 브라우저 렌더링, Reverse Proxy, WAS 대기열, DB Lock/Wait, 스토리지 지연 중 하나 이상에서 발생한다. p95 응답시간을 구간별로 분해하고 동일 요청의 correlation ID로 연결한다.

# OS 자원 관찰(읽기 전용)
uptime
vmstat 1 5
free -h
df -h
iostat -xz 1 3  # sysstat 설치 환경에서만
ss -s

# 서비스 로그는 권한이 허용된 범위에서만, 토큰/개인정보 마스킹
journalctl --since '-10 min' --no-pager | tail -n 100
영역확인 지표의미
WASactive threads, queue depth, connection pool wait, GC pause대기열/풀 포화와 처리 시간 분리
DB활성 세션, lock/wait event, long-running SQL, log syncCPU가 낮아도 동시성 병목 가능
스토리지await, util, IOPS, throughput, filesystem usage평균 대역폭보다 tail latency 중요
OS 메모리swap-in/out, major faults, OOM, RSSswap 점유량 자체보다 현재 paging 여부 중요

Oracle DB의 세션/대기 조회는 권한이 허용된 DBA 계정과 승인된 진단 SQL만 사용한다. 시스템 뷰 접근 권한과 제품 버전에 따라 조회 방법이 다르다. 실행계획 변경, 통계 재수집, 세션 강제 종료, 파라미터 변경은 진단이 아니라 변경 작업이다.

15.9 사례 A: 내부 ERP 정상, 외부 모바일만 실패

가상 시나리오: 내부 PC에서는 ERP 로그인·저장이 정상이나 외부 모바일에서만 인증 후 메뉴 호출이 실패한다. 원인 후보를 DNS, 외부 WAF, Reverse Proxy, 인증 쿠키, UC 연계 API로 분리한다.

1) 내부/외부 DNS 응답 및 목적지 VIP 비교
2) 외부 단말의 인증 리다이렉트/Set-Cookie/SameSite/Secure 확인
3) WAF 차단 로그와 실패 URL·메서드·상태코드 매칭
4) Proxy access/error 로그에서 upstream 주소·응답시간 확인
5) API 요청이 실제 ERP/UC 실행 계층까지 도달했는지 확인
6) 최소 범위의 수정안 승인 → 외부/내부 모두 회귀 시험

금지할 단정: ‘로그인이 되니 네트워크는 정상’ 또는 ‘내부에서 되니 애플리케이션 문제는 아님’. 실제로 메뉴·API가 서로 다른 FQDN이나 인증 경로를 사용할 수 있다.

15.10 사례 B: 502 또는 503이 발생하지만 백엔드 프로세스는 살아 있다

가상 시나리오: Proxy는 502를 기록하지만 WAS 프로세스가 실행 중이다. 프로세스 존재 여부와 서비스 준비 상태는 별개다. TCP 연결, TLS SNI, HTTP Host, upstream 경로, 애플리케이션 스레드/풀 상태를 차례로 확인한다. UC 503이라면 Ingress → Service → EndpointSlice → Ready Pod로 추적한다.

Proxy 502:
  upstream TCP 실패? → 방화벽/라우팅/리스너
  TLS 실패?          → SNI/신뢰 체인/버전
  HTTP 오류?         → Host/path/protocol/upstream 로그
  응답 지연?         → WAS pool/DB wait

Kubernetes 503:
  Ingress route? → Service selector/port? → EndpointSlice? → Ready Pod?
  → App readiness/logs → DB/Queue/Storage dependency

변경 후보를 동시에 여러 개 적용하지 않는다. 가설 하나 → 최소 변경 하나 → 전후 증거 비교를 원칙으로 한다.

15.11 복구 검증, 확장성·보안 트레이드오프

대응책기대 효과기술적 부채/위험검증

서비스 복구 완료 기준: 핵심 ERP 조회·저장과 UC 로그인·메뉴·실시간 기능을 대표 사용자 경로에서 재검증하고, 오류율·p95·DB/Pod 지표가 기준선으로 회복됐는지 확인한다. 원인 미확정 상태의 완화 조치는 미해결 과제로 남긴다.

보안 검증: 긴급 변경으로 생긴 WAF/방화벽 예외, 임시 계정, 로그의 토큰, TLS 검증 우회, 네트워크 공개 범위를 변경 티켓에 기록하고 만료일을 지정한다.
