11장 3부. 용량 산정과 보안

11.7 UC 용량 산정과 확장

등록 사용자 수만으로 Pod 수를 정하지 않는다. 동시 API 요청, 실시간 연결, 파일 전송량, 알림 이벤트, 데이터베이스 처리량을 분리해 측정한다.

계층핵심 지표확장 판단
Web/APIp95 응답시간, RPS, CPU 사용·제한, 메모리수평 확장과 요청당 자원 비용 검증
실시간 통신동시 연결, 재연결 수, 이벤트 지연세션 유지·연결 분산 정책 확인
DB/캐시쿼리 지연, 연결 수, IOPS애플리케이션 증설 후 병목 재측정
스토리지처리량, 지연, 용량, 복구 부하피크 파일 업로드·복원 시험

가상 N+1 계산: Worker Node 3대, 각 Node의 Allocatable 자원이 8 vCPU/24 GiB라면 노드 1대 장애 후 잔여 용량은 16 vCPU/48 GiB다. 시스템 워크로드와 애플리케이션의 자원 요청 합계가 이 범위 안에서 실제로 재배치 가능한지 검증한다. 이는 제품 공식 권장 사양이 아니다.

정상: 3 × 8 vCPU = 24 vCPU
장애 후: 2 × 8 vCPU = 16 vCPU
정상 메모리: 72 GiB → 장애 후 48 GiB
추가 검증: 배치 제약, 영속 볼륨 접근, CPU 제한, DB 처리량
확장 방식장점한계
Pod 수평 확장무상태 처리량 확장DB·세션 병목을 해결하지 못함
Node 증설배치 공간과 장애 여유 확보비용·운영 복잡도 증가
Pod 자원 상향단일 프로세스 병목에 간단노드 종속성 증가

11.8 보안과 운영 경계

항목점검 기준
관리 접근관리 API를 일반 사용자 접속망과 분리하고 역할별 최소 권한 부여
워크로드불필요한 높은 권한·호스트 접근 제한, 지원 범위 확인
네트워크워크로드 간 통신 허용 범위 문서화, 정책 적용 후 기능 시험
이미지신뢰 출처, 지원 버전, 취약점 점검, 패치 주기 관리
민감 정보설정 저장소와 운영 로그에 비밀번호 등 노출 방지
확장성신규 Pod·Node에도 접근 정책과 모니터링 자동 적용

보안 강화로 DNS·DB·모니터링 연결이 끊어질 수 있으므로 변경 승인, 영향 시험, 롤백 절차를 마련한다. 운영과 보안은 서비스 확장 이후에도 유지되어야 한다.
