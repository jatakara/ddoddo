32.1 서비스 경계와 관측성

AI 기술지원은 ERP·UC 본 서비스와 별개의 지원 서비스로 취급한다. 지원 시스템 장애가 업무 트랜잭션에 영향을 주지 않도록 별도 자원과 접근 권한을 사용한다. Metrics는 수치의 추세, Logs는 사건의 상세 기록, Traces는 요청이 여러 구성요소를 통과하는 경로를 설명한다. 사용자 문의에 대한 답변 성공 여부는 HTTP 200만으로 판단할 수 없다.

32.2 요청 추적 설계

Gateway에서 무작위 trace ID를 생성하고 인증, 검색, 모델 호출, 출처 검사, 이관까지 전파한다. 각 span은 시작·종료 시각, 상태, 처리 건수와 버전만 기록한다. 원문 질문, 검색 문서 본문, 토큰 및 인증 헤더는 기본 수집 대상에서 제외한다. 비동기 색인 작업은 별도 trace와 작업 ID를 연결한다.

32.3 SLI와 SLO 정의

유효 문의는 인증 및 입력 정책을 통과한 요청이다. 서비스 성공률은 유효 문의 중 검증된 답변 또는 정상 이관이 완료된 비율이며, 답변 정확도와는 별도로 관리한다. 응답시간은 Gateway 수신부터 최종 응답까지 측정하고 스트리밍 첫 토큰 지연은 별도 지표로 기록한다. 월 10,000건에 SLO 99.5%이면 오류 예산은 50건이다. 실패 25건은 예산 50% 소진에 해당한다.

32.5 Prometheus 실습

히스토그램 기반 p95 예시이며 실제 metric 이름과 label은 구현에 맞춘다. 여러 인스턴스의 p95를 평균하지 않고 bucket을 합산한다.

histogram_quantile(0.95,
  sum by (le) (rate(support_request_duration_seconds_bucket[5m])))

sum(rate(support_requests_total{outcome="failed"}[5m]))
/ sum(rate(support_requests_total[5m]))
분모가 0이면 미측정으로 취급한다. 요청 ID·사용자 ID를 metric label로 사용하면 cardinality가 폭증하므로 제한한다.

32.6 현장 장애 진단

응답 p95가 6초에서 14초로 증가했다면 먼저 요청량과 오류율을 비교한다. 검색 span이 0.4초에서 0.5초, 모델 span이 4초에서 12초라면 모델 공급자 지연 또는 큐 대기를 우선 조사한다. 이는 원인 가설이며 모델 호출 상태, 재시도, 동시성 제한으로 검증한다. ERP·UC 서버 CPU 증설은 이 증거만으로 정당화되지 않는다.
