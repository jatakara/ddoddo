25.7 장애 접수 카드와 영향 범위

장애 초기에는 추정 원인을 확정적으로 기록하지 않는다. 사용자에게 나타난 현상, 최초 탐지, 영향 업무, 최근 변경, 증거 신뢰도를 분리해야 한다.

Incident ID: INC-EXAMPLE-001
최초 탐지: YYYY-MM-DD HH:MM KST
보고자/담당 역할: <...>
서비스 ID: ERP-EXAMPLE | UC-EXAMPLE
영향: ERP 저장 실패 / 외부망 UC 연결 끊김 등
영향 사용자/범위: 확인된 범위만 기재
현재 상태: Investigating | Mitigated | Resolved
최근 변경: 변경 ID 또는 '확인 중'

관측 증거: 로그 요청 ID, 메트릭 시각, 알람 ID
가설: H1 / H2 / H3 (확인 전)
다음 점검 시각/책임자: <...>

25.8 타임라인과 원인 분석(PIR)

사후 분석(Post-Incident Review)은 개인 책임 추궁보다 시스템적 재발 방지에 초점을 둔다. '원인'은 로그·재현·설정 차이 등의 증거로 뒷받침되어야 하며, 확인되지 않은 경우 가설로 남긴다.

시각(예시)관측 사실근거판단
10:02외부 UC 연결 실패율 증가Proxy 지표확인됨
10:05내부 경로는 정상Synthetic Test확인됨
10:10L7 변경 이력 발견변경 기록상관관계
10:18설정 차이 확인승인된 설정 Diff가설 강화
10:35승인된 원복 후 업무 복구연결·메시지 시험복구 확인
PIR 요약
- 사고 개요 및 실제 업무 영향:
- 탐지 지연/대응 시간/업무 복구 시간:
- 확정된 기술 원인 / 남은 가설:
- 기여 요인: 모니터링, 변경 검증, 문서, 공통 장애점
- 잘 작동한 통제 / 실패한 통제:
- 단기 재발 방지: <Owner, Due date, Evidence>
- 구조적 개선: <ADR/개선 과제 ID>

- 최종 검토/승인: <역할>
현장 적용 판단

원인 미확정 상태에서 'WAS 장애' 등 단정적 결론을 내리지 않는다. 장애가 복구되었더라도 데이터 정합성·미처리 큐·재전송 여부를 별도 확인한다.

25.9 변경 승인서의 필수 항목

운영 변경은 기술적 성공뿐 아니라 실패 시의 업무 손실을 검토해야 한다. 위험도는 영향 범위, 변경의 되돌릴 수 있는 정도, 데이터 변경, 예상 중단 시간과 검증 가능성으로 판단한다.

25.10 배포 Manifest와 증거 체인

디렉터리 기반 배포는 승인되지 않은 파일이 함께 반영되는 위험이 있다. 릴리스 Artifact를 고정하고 해시·승인 Manifest를 통해 실제 배포 범위를 명시해야 한다.

release_id: REL-EXAMPLE-025
artifact: omniesol-example-package.tar.gz
sha256: <64자리 검증된 해시>
approved_paths:
  - /app/static/released/
  - /app/config/approved/
excluded_paths:
  - /app/work-in-progress/
environment: STAGE -> PROD
approval_ticket: CHG-EXAMPLE-025
rollback_artifact: REL-EXAMPLE-024
db_migration: NONE | FORWARD_ONLY | REVERSIBLE
verification:
  - erp-login
  - erp-save-transaction
  - uc-external-connection

실제 파일 해시는 빌드 시스템에서 계산하며 문서에 가상의 해시를 복사해 사용하지 않는다. 배포 실행 시 승인된 Manifest와 실제 파일 목록을 비교하고 차이가 있으면 배포를 중단한다.

현장 적용 판단

기존 배포 구조를 유지하면 도입 비용은 낮지만 누락된 의존성이나 잘못된 예외 필터의 위험이 남는다. 완전한 Immutable Artifact 배포는 통제력이 높지만 파이프라인 개선 비용과 운영 전환 부담이 크다.

25.11 Go/No-Go와 변경 후 검증

GateGONO-GO
지원성제품·OS·DB·WAS 버전 검증미검증 조합
보안접근·인증·TLS 영향 검토과권한/미승인 포트
복구원복 경로와 백업 확인비가역 변경 대응 없음
성능Baseline과 N+1 여유부하 증거 없음
업무시험 계정·검증 시나리오 준비업무 성공 판정 불가
승인책임자 승인 기록승인자 불명확

변경 후에는 프로세스 Running 상태만 확인하지 않는다. 승인된 업무 시나리오를 수행하고 오류율·지연·데이터 정합성을 비교한다. 관측값이 기준을 초과하면 사전 정의된 중단·원복 조건을 적용한다.

  • 실행 로그와 변경 전후 설정 Diff를 저장한다.
  • 업무 Owner가 사용자 관점의 정상성을 확인한다.
  • DB 데이터 변경은 애플리케이션 롤백과 별도로 판단한다.
  • 원복 후에도 데이터 및 메시지 중복·누락을 검증한다.

25.12 2부 완료 기준

  • 장애 접수 카드에 사실과 가설이 분리되어 있다.
  • 타임라인의 시각·로그·변경 이력에 상호 참조 ID가 있다.
  • PIR 개선 과제에 Owner·기한·검증 방법이 있다.
  • 변경 승인서에 지원성·보안·용량·원복·업무 검증이 포함된다.
  • 배포 Manifest가 승인 파일과 제외 파일을 명시한다.
  • 운영 변경 권한과 승인 권한이 분리되어 있다.
