서비스 카탈로그와 운영 점검표

모든 식별자·업무 시나리오·시간·점수는 가상 예시다. 실제 고객 정보·내부 IP·계정·인증정보를 수록하지 않는다. 공식 지원 사양·계약·승인 절차가 우선한다.

25.1 표준 운영 산출물의 역할

23장 구축 검수와 24장 운영 KPI를 실제 운영으로 연결하려면 반복 사용 가능한 양식이 필요하다. 템플릿의 목적은 보고서 분량을 늘리는 것이 아니라 업무 영향, 관측 증거, 조치 책임, 복구 판단을 같은 언어로 기록하는 것이다. OmniEsol ERP·UC는 고객별 도입 범위와 설치 형태가 다르므로 아래 항목은 교육용 기준이며 실제 지원 구성과 계약을 우선한다.

산출물사용 시점필수 승인/검증
서비스 카탈로그신규 구축·변경·인수인계업무 Owner와 운영 책임
일일·주간 점검정기 운영지표·업무 검증 증거
장애 기록/PIR사고 발생 및 종료영향·타임라인·재발방지
변경 승인서운영 변경 전후위험·원복·업무 검증
복구 훈련 결과서백업/DR 검증RTO/RPO와 데이터 정합성
운영 인수인계구축→운영 전환Runbook·권한·RACI
현장 적용 판단

템플릿 자체를 운영 증거로 취급하지 않는다. 점검 결과는 시각, 시스템 버전, 관측값, 증거 링크, 담당자와 함께 보존해야 한다.

25.2 서비스 카탈로그와 의존성 맵

서비스 카탈로그는 CMDB의 단순 서버 목록과 다르다. 사용자가 어떤 업무를 수행하는지, 어느 FQDN으로 접근하는지, 무엇에 의존하는지와 누가 운영 결정을 내리는지를 기록한다. 서버가 바뀌어도 서비스 ID는 유지되어야 한다.

service_id: ERP-ACCOUNTING-EXAMPLE
service_name: ERP 전표 처리 (가상)
environment: PROD
business_owner_role: 회계 업무 책임자
technical_owner_role: ERP 운영 책임자
user_journey: 로그인 → 전표 입력 → 저장 → 조회
entrypoint: erp.example.invalid (예시 전용)
dependencies:
  - DNS / TLS / Reverse Proxy
  - ERP WAS / 인증 서비스
  - ERP DB / 백업 저장소
sli: 유효 전표 저장 성공률
slo: 업무 Owner가 승인한 목표 (미정)
rto: 합의 후 기입
rpo: 합의 후 기입
runbook_id: RB-ERP-001
change_approver_role: 운영 변경 승인권자
data_classification: 내부 정책에 따름

UC 메시징, 파일, 메일은 각각 데이터 저장소와 외부 연계 경로가 다를 수 있다. 단일 UC 서비스로 묶어 기록할 때도 업무별 SLI와 복구 검증은 별도로 정의한다.

25.3 일일 운영 점검표

매일 점검은 단순히 CPU 사용률을 기록하는 일이 아니다. 핵심 사용자 시나리오의 성공 여부를 먼저 확인한 후 계층별 지표를 검토한다. 경보 임계치는 시스템별 기준선과 업무 SLO를 바탕으로 결정한다.

순서점검 대상PASS 조건(예시)증거
1ERP 로그인·전표 조회/저장승인된 테스트 시나리오 성공테스트 실행 ID
2UC 메시지·파일·외부 접속기능별 시험 성공업무 테스트 로그

UNKNOWN을 PASS로 처리하지 않는다. 점검 계정은 최소 권한·가상 테스트 데이터로 분리하고 실제 전표를 생성하는 테스트는 승인된 방식만 사용한다.

25.4 주간 점검·용량 및 보안 리뷰

주간 점검은 당일 상태가 아니라 변화 추세를 검토한다. ERP DB 성장률과 Archive 사용량, UC 파일 저장량, Pod 재시작, 인증서 만료 예고, 패치 대기와 취약점 조치 기한을 한 보고서에서 확인한다.

주간 질문필요 증거조치 판단
DB/스토리지 여유는 언제 소진되는가?최근 4~8주 증가 추세예상 임계일과 증설 리드타임
업무 p95/p99가 악화되는가?동일 업무·동일 시간대 비교변경·부하·DB 대기 연관
노드 장애 시 N+1 가능한가?Requests/Allocatable 및 스케줄 시험용량 부족 시 No-Go
변경 실패/반복 장애가 있는가?변경·사고 티켓PIR 및 재발 방지
권한/인증서/취약점 위험은?만료 목록·보안 점검위험 수용 또는 기한 내 조치
  • 서비스 Owner와 운영 책임자가 결과를 검토한다.
  • 미해결 항목은 티켓, 담당, 기한, 업무 영향을 기록한다.
  • 백업 성공률과 실제 복원 성공률을 혼동하지 않는다.
  • 비표준 구성이 발견되면 CMDB와 예외 승인 기록을 함께 갱신한다.

25.5 점검 자동화와 데이터 품질

자동 점검은 관찰(읽기 전용) → 판정 → 증거 보존 → 사람의 결정으로 분리한다. 자동 조치는 별도의 정책과 승인을 필요로 한다. 스크립트의 종료코드 0은 비즈니스 기능 정상과 동의어가 아니다.

자동 점검 결과 JSON (교육용 스키마)
{
  "schema_version": "1.0",
  "service_id": "ERP-EXAMPLE",
  "observed_at": "2026-11-09T07:30:00+09:00",
  "environment": "STAGE",
  "check_id": "erp-login-synthetic",
  "status": "PASS",
  "evidence_ref": "internal-ticket-or-object-id",
  "metric_window_minutes": 5,
  "collector_status": "HEALTHY",
  "approved_action": null
}

수집 누락, 오래된 캐시 데이터, 잘못된 시각 동기화는 자동화 판단의 품질을 떨어뜨린다. 결과 JSON에는 스키마 버전과 관측 시각을 반드시 넣고, 비밀번호·토큰·개인정보를 저장하지 않는다.

현장 적용 판단

확장성 측면에서는 서비스별 병렬 수집과 재시도 제한이 필요하다. 보안 측면에서는 읽기 전용 계정, 결과 접근제어, 감사로그를 적용한다.

25.6 1부 완료 기준

  • 서비스 ID·업무 Owner·기술 Owner·의존성·RTO/RPO가 문서화되었다.
  • ERP·UC 주요 업무 시나리오가 일일 점검에 포함되었다.
  • PASS/FAIL/UNKNOWN의 판정 기준과 증거 위치가 정의되었다.
  • 주간 용량·보안·변경 위험 리뷰에 책임자가 있다.
  • 자동 점검 계정이 읽기 전용이고 비밀정보가 결과에 포함되지 않는다.
  • 템플릿과 실제 운영 정책의 차이를 예외 목록으로 관리한다.
