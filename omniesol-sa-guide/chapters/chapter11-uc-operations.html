11장 4부. 운영·장애 분석·인수인계

11.9 관측성과 운영 기준

클러스터 상태만으로 사용자 체감 품질을 설명할 수 없다. 브라우저부터 Ingress, Service, Pod, DB와 스토리지까지 동일 시간대의 지표를 비교한다.

계층관측 지표판단 질문
브라우저화면 로딩, 인증 실패, 실시간 연결 오류특정 사용자·네트워크 문제인가?
Ingress4xx/5xx, p95, 업스트림 연결라우팅 또는 타임아웃 문제인가?
PodRestart, Readiness, OOM, CPU 제한앱 또는 자원 문제인가?
NodeReady, 자원 압박, 디스크, 네트워크특정 노드에 집중되는가?
DB/Storage쿼리 지연, I/O, 연결 수, 오류확장으로 해결되지 않는 병목인가?

11.10 가상 장애 사례

사례 A — 로그인 후 UC 메뉴가 비어 있음: 실패한 브라우저 요청의 URL과 상태코드를 확인하고, 내부·외부 도메인 응답, 인증 경로, 프레임 허용 정책을 대조한다. 로그인 화면 표시만으로 전체 정상 판정을 하지 않는다.

사례 B — Pod는 Running인데 503: Service selector, EndpointSlice, readiness, 포트 설정, Ingress 경로를 확인한다. Pod 실행 상태와 요청 수신 가능 상태는 다르다.

사례 C — 노드 장애 이후 응답 지연: Pod 재배치 실패, 자원 요청량, 볼륨 접근 제약, 실시간 연결 재수립 부하와 DB 연결 대기를 구분한다. 복구 후 N+1 시험을 반복한다.

11.11 운영 점검 명령어 예시

아래 명령은 일반적인 읽기 전용 점검 예시다. 실제 운영 권한을 확인하고 결과에 포함된 민감 정보를 공개하지 않는다.

kubectl get nodes -o wide
kubectl get pods -n <namespace> -o wide
kubectl get deploy,sts,svc,ingress -n <namespace>
kubectl get endpointslices -n <namespace>
kubectl get pvc -n <namespace>
kubectl get hpa,pdb -n <namespace>
kubectl describe pod <pod-name> -n <namespace>
kubectl get events -n <namespace> --sort-by=.lastTimestamp
kubectl top nodes
kubectl top pods -n <namespace>

Pending은 스케줄링·자원·볼륨, CrashLoopBackOff는 종료 원인·설정·Probe, 503은 준비된 Endpoint와 라우팅, 느린 응답은 API·DB·스토리지 지연을 우선 확인한다.

11.12 설치·운영 인수인계 (Go/No-Go)

영역필수 증적판정
지원 조합제품·K8s·네트워크·스토리지 지원 버전 확인□ Go □ No-Go
접속내·외부 접속, 로그인, 파일, 실시간 기능 시험□ Go □ No-Go
용량피크 부하, 노드 장애 후 재배치·성능 시험□ Go □ No-Go
복구DB·파일 복원, RPO/RTO 측정 결과□ Go □ No-Go
보안접근 권한, 네트워크 정책, 패치·로그 점검□ Go □ No-Go
운영모니터링, 연락망, 변경·롤백 절차□ Go □ No-Go

중요 항목이 No-Go이면 위험 수용자, 영향, 임시 조치, 해소 기한을 문서화한다. 검증하지 않은 가용성과 복구 목표를 달성했다고 표기하지 않는다.

본 장은 공개 교육용 참조 설계이며 제품 공식 사양을 대체하지 않는다. 다음 장은 12장 통합형 Kubernetes 아키텍처다.
