16.1 성능 검증과 Sizing의 차이

7장 Server Sizing Matrix가 구축 전의 자원 배치 가정을 설명했다면, 16장은 그 가정이 실제 업무 부하에서 성립하는지 증명하는 방법을 다룬다. Sizing은 “CPU·메모리·스토리지·노드를 얼마나 확보할까?”에 답하고, 성능 검증은 “이 자원으로 피크 업무를 완료할 수 있는가?”에 답한다.

구분용량 산정(Sizing)성능 검증
입력업무 범위, 사용자 수, 성장률, 부하 추정업무 Mix, 데이터 분포, Think Time, 시험 조건
판단자원·HA·복구 요구를 만족할 후보 구성업무별 p95/p99, 성공 TPS, 오류율, DB 대기
산출물가정과 근거가 포함된 Sizing Matrix재현 가능한 결과서, 병목 원인, 승인 조건

단순 CPU 사용률이 낮다는 이유로 시험을 통과시켜서는 안 된다. 실제 사용자가 로그인·조회·저장·승인 업무를 끝낼 수 있어야 한다.

16.2 사용자 수·동시성·RPS·TPS

등록 사용자 1,000명과 동시 로그인 200명은 곧 200개의 요청이 동시에 실행된다는 뜻이 아니다. 사용자 대기 시간(Think Time), 화면별 API 호출 수, 배치·보고서, UC 알림, 로그인 집중에 따라 처리량이 크게 달라진다.

지표의미혼동 주의
등록 사용자계정이 등록된 사용자동시 부하의 직접 지표 아님
활성 사용자기간 내 실제 업무를 수행한 사용자DAU와 순간 동시 활성 구분
동시 세션특정 시점에 유지 중인 로그인/연결실행 중인 요청 수와 다름
RPS초당 HTTP 요청 수한 화면이 여러 API 요청을 만들 수 있음
TPS초당 비즈니스 트랜잭션 수트랜잭션 경계 정의가 먼저 필요
Think Time사용자 동작 사이의 대기시간생략하면 부하가 과대 추정될 수 있음

Little의 법칙으로 평균 진행 중 요청 수 계산

안정된 시스템에서 평균 시스템 내 요청 수 L = λ × W이다. λ는 평균 도착률(초당 요청 수), W는 평균 체류시간(초)이다. 예를 들어 120 RPS와 평균 0.35초라면 평균 42개의 요청이 진행 중이다. 이 값은 로그인 세션 수나 필수 스레드 수와 동일하지 않으며, 큐·비동기 처리·요청 종류에 따라 실제 자원 수요가 달라진다.

가상 업무 모델
등록 사용자: 1,000명
일간 활성 사용자: 400명
피크 로그인 세션: 200개
목표 요청 도착률: 120 RPS
평균 요청 체류시간: 0.35초
평균 in-flight 요청: 120 × 0.35 = 42
주의: 세션 200개 ≠ 실행 중 요청 42개

16.3 p95·p99·오류율을 정확히 읽기

평균 응답시간은 느린 일부 요청을 감춘다. p95가 1.5초라면 관측 요청의 약 95%가 1.5초 이하였다는 뜻이다. p99는 더 느린 꼬리 구간을 보여준다. 단, 관측 기간·표본 수·요청 종류를 명시해야 비교가 가능하다.

항목가상 승인 목표측정 시 주의
피크 성공 처리량120 RPS 이상오류 응답을 성공 처리량에 포함하지 않음
핵심 거래 p951.5초 이하업무별 엔드투엔드 시간
핵심 거래 p993.0초 이하충분한 표본과 동일 측정 구간
오류율0.5% 미만예상된 4xx와 시스템 실패 정의 분리
거래 정합성중복·누락·오류 0건HTTP 200 외 실제 DB 반영 확인

ERP 조회, ERP 저장, UC 검색을 하나의 p95로 합치면 중요 거래의 지연이 숨을 수 있다. 서비스·API·사용자군별로 나눠 본다. 브라우저의 전체 완료시간과 서버 처리시간도 다른 지표다.

통계적 오류 주의

Pod A의 p95와 Pod B의 p95를 산술평균해 전체 p95라고 보고하면 안 된다. 원시 표본 또는 병합 가능한 Histogram으로 전체 분포를 계산한다. Prometheus 공식 Histogram 문서를 참고한다.

16.4 사용자 응답시간과 계층별 지연 예산

“화면이 느리다”는 증상은 DNS/TLS, Proxy, WAS 큐, DB 대기, 네트워크 전송, 브라우저 렌더링 중 어느 계층에서도 발생할 수 있다. 계층마다 시간 측정의 시작·종료 기준이 다르므로 중복 집계하지 않도록 Trace ID와 측정 정의를 통일한다.

관측 결과가능성 높은 원인다음 증거
TTFB 높음, WAS 시간 낮음Proxy/네트워크/업스트림 연결Proxy Upstream Time, TLS, 연결 로그
WAS 시간 높음, DB 시간 낮음스레드 큐, GC, 외부 APIThread/GC/Connection Pool
DB 대기시간 증가SQL, Lock, I/O, Log WriteWait Event, 실행계획, Storage Latency
API는 빠르고 화면만 늦음JS 렌더링, 정적 리소스, 다중 API브라우저 Waterfall과 Long Task

16.5 Baseline과 시험 환경의 동등성

CPU·스토리지 성능, VM 오버커밋, DB 데이터 분포, 캐시 워밍, TLS/WAF, 네트워크, 제품 버전, JVM/DB 설정이 바뀌면 동일한 120 RPS 시험도 다른 결과를 낸다. 시험 전 아래 조건을 기록해 비교 가능성을 확보한다.

  • OS/JDK/WAS/DB/Kubernetes 및 제품 버전, 패치, 설정 변경 내역
  • 물리/VM 자원, NUMA, CPU 제한, 스토리지 종류와 I/O 지표
  • 합성 데이터 건수·분포·인덱스·첨부파일 크기
  • 캐시 워밍, 배치·백업·외부 연계 부하 포함 여부
  • 사용자 경로(내부·외부·모바일) 및 부하 생성기의 CPU·네트워크 여유
  • 관측 시간대, 클록 동기화, 로그의 민감정보 제거
시험 범위

운영 데이터·고객 계정·내부 주소·비공개 제품 설정은 공개 원고에 포함하지 않는다. 부하 시험은 승인된 비운영 환경과 합성 데이터로 수행한다.
