24.1 운영 KPI와 서비스 신뢰성의 차이

운영 KPI는 운영팀의 활동과 결과를 평가하는 지표이며, SLI(Service Level Indicator)는 서비스의 실제 품질을 측정하는 지표다. SLO(Service Level Objective)는 SLI의 목표이고 SLA(Service Level Agreement)는 계약상 서비스 수준 및 미달 시 책임을 규정할 수 있는 합의다. CPU 사용률이 낮다는 이유로 ERP가 정상이라고 판단하지 않는다. 사용자가 승인·조회·저장 업무를 수행할 수 있는지를 우선 측정한다.

서버 프로세스 가동률, HTTP 200 비율, 업무 거래 성공률은 서로 다른 지표다. 업무 기능을 대표하는 Synthetic Transaction과 실제 사용자 측정을 조합한다.

24.2 ERP·UC 업무 중심 SLI 설계

ERP 업무는 데이터 정합성과 거래 완료 여부가 중요하다. UC 업무는 메시지·파일·메일 전송과 세션 연결을 관찰한다. 인증 서비스·외부 연계·DB의 장애가 업무 성공률에 미치는 영향도 서비스 맵에 반영한다.

서비스업무 SLI분자 / 분모검증 관점
ERP 로그인정상 인증 성공률정상 처리된 유효 로그인 / 유효 로그인 시도비밀번호 오류 등 사용자 귀책 제외 규칙
ERP 전표 저장업무 저장 성공률검증·DB Commit 완료 / 유효 저장 시도중복 제출·취소·업무 오류 분류
ERP 조회응답 지연 p95유효 요청의 처리시간 95백분위브라우저/서버 양측 비교
UC 메시지전달 성공률합의한 시간 내 전달 / 유효 발송큐 적체·재시도·중복 제거
UC 파일업로드 완료율무결성 확인 완료 / 유효 업로드대용량·네트워크 단절 포함
UC 실시간 연결연결 유지율정상 종료/유지 연결 / 유효 연결SSE·WebSocket 중간 장비 영향

모든 실패를 시스템 오류로 계산하면 사용자 오입력에 의해 신뢰성 지표가 왜곡된다. 반대로 서버가 HTTP 200을 반환했어도 DB Commit에 실패했다면 업무 성공으로 계산해서는 안 된다.

24.3 분모·측정 창·백분위 정의

성공률의 분모는 정의된 유효 업무 요청이다. 5분 구간은 신속 탐지에 유용하지만 소량 트래픽에서는 분모가 작아 변동이 크다. 월간 SLO는 계약·운영 보고에 적합하되 짧은 장애를 감출 수 있다. 지표마다 데이터 누락, 계획 점검, 배치, 재시도 처리 규칙을 명시한다.

업무 성공률 = 정상 완료 유효 거래 수 / 전체 유효 거래 수 × 100
오류율 = 실패 유효 거래 수 / 전체 유효 거래 수 × 100
가용성(시간 기반) = 정상 제공 시간 / 측정 대상 시간 × 100

p95: 관측값의 95%가 이 값 이하인 지연시간
p99: 관측값의 99%가 이 값 이하인 지연시간
주의: 여러 노드의 p95를 단순 평균하면 전체 p95가 되지 않는다.
운영 데이터 품질

계측 장애로 지표가 사라졌다면 성공으로 간주하지 않는다. Unknown/No Data를 별도 상태로 보고하고, 로그·Synthetic Test 등 대체 증거를 확보한다.

24.4 오류 예산과 Burn Rate

99.9% 요청 성공률 목표는 관측 기간 동안 유효 요청의 0.1%까지 실패를 허용하는 목표를 뜻한다. 이를 오류 예산이라고 부른다. 트래픽이 균일하지 않은 서비스에서 시간 기반 다운타임 43.2분과 동일한 뜻은 아니다.

가상 월간 유효 요청SLO허용 실패 요청실제 실패예산 소비
1,000,00099.9%1,00060060%
1,000,00099.9%1,0001,500150% (초과)

예산 소비율은 실패 건수 / 허용 실패 건수로 계산한다. Burn Rate는 현재 오류 발생 속도를 허용 오류율과 비교한 배율이다. 예를 들어 99.9% SLO에서 오류율 1%는 Burn Rate 10배다. 짧은 구간과 긴 구간을 함께 관찰해야 순간 장애와 지속 장애를 구분할 수 있다.

SLO는 계약이 아니다

오류 예산은 위험한 변경을 정당화하는 면허가 아니다. 금융·급여·개인정보 등 중요 업무는 별도의 변경 통제와 복구 목표를 적용한다.

24.5 측정 아키텍처와 개인정보 보호

로그에 세션 토큰, 인증정보, 개인정보, 전표 본문을 저장하지 않는다. Trace ID는 요청 흐름을 연결하기 위한 식별자로 사용하되 사용자 식별정보와 직접 결합하는 방식은 피한다. 수집 파이프라인에는 필드 마스킹, 접근 권한, 보존기간, 암호화 및 감사 기록이 필요하다.

중앙 Collector표준화·수집 제어Collector 장애·비용 집중, 버퍼/HA 필요

24.6 SLI/SLO 정의서 체크리스트

  • 업무 Owner와 관측 책임자를 지정했다.
  • 유효 요청의 분자·분모와 제외 규칙을 명시했다.
  • 내부/외부·PC/모바일·ERP/UC를 필요에 따라 분리했다.
  • 지표 수집 누락을 성공으로 처리하지 않는다.
  • 월간 목표와 단기 알람의 관측 창을 구분했다.
  • 계약 SLA와 내부 SLO, RTO/RPO를 혼동하지 않는다.
  • 인증정보·개인정보가 계측 데이터에 노출되지 않는지 점검했다.
  • 서비스 증설 시 지표 Label Cardinality·보관 비용을 검토했다.
