11장 1부. UC 단독형 아키텍처

11.1~11.4 · 설계 경계, 요청 경로, Kubernetes 객체, 데이터 지속성

이 장의 전제

UC 단독형은 ERP와 독립된 자원·장애 영역에서 협업·커뮤니케이션 서비스를 제공하는 배포 방식이다. 이 장은 일반적인 Kubernetes 기반 UC 참조 아키텍처를 설명한다.

공식 사양과 구분: Ingress, Service, Deployment, DB, 캐시, 메시지 브로커, 공유 스토리지는 개념 설명을 위한 구성 요소다. 특정 OmniEsol 버전의 필수 요소나 공식 지원 조합이라는 뜻이 아니다. 실제 Kubernetes·CNI·CSI·DB·포트·SSO·배포 구조는 제품별 공식 문서와 계약 범위를 우선한다.

11.1 UC 단독형의 범위와 분리 경계

독립 배포의 핵심은 화면이나 도메인의 분리가 아니라 Compute, Network, Data, Identity, Operations의 책임을 명시하는 것이다. Namespace 분리만으로 강한 보안 격리나 장애 격리가 보장되지 않는다.

경계SA의 판단 질문대표 리스크
Compute전용 노드/클러스터 또는 공유 자원인가?다른 업무와 자원 경합
Network사용자·관리자·DB 통신이 분리되는가?과도한 접근 허용
DataDB·파일·세션 데이터는 어디에 남는가?Pod 교체 시 데이터 유실
IdentitySSO·인증서·쿠키 책임 주체는 누구인가?화면은 표시되지만 메뉴 인증 실패
Operations장애·패치·백업 담당과 승인자는 누구인가?복구 지연과 책임 공백

중요 업무에서는 클러스터 공유의 비용 절감과 독립 클러스터의 장애 격리·운영 복잡도 사이의 트레이드오프를 비교한다.

11.2 논리 아키텍처와 요청 경로

사용자 (Browser / Mobile)
      │ HTTPS, 필요 시 WebSocket
      ▼
 [내·외부 DNS] → [Firewall/WAF(선택)]
      │
 [Load Balancer]
      │
 [Ingress / Gateway]
      │
 [Kubernetes Service]
      │
      ├── [UC Web/API Pod × N] ── [DB]
      │                └──────── [파일 저장소]
      └── [실시간 서비스 Pod × N] ── [캐시/브로커(선택)]

기반: Control Plane / Worker / CNI / CSI
횡단: TLS / 인증 / 로그 / 모니터링 / 백업
구간점검 사항장애 증상
DNS → LB응답 IP, 접근 경로, TLS 인증서일부 사용자만 접속 불가
LB → Ingress라우팅·Host·Timeout·WebSocket 지원502/504, 연결 끊김
Ingress → ServiceService selector, EndpointSlice, targetPort503, 특정 API 실패
Pod → DB/Storage권한, 네트워크 정책, 연결·I/O 지연조회·파일 처리 지연

로그인 페이지가 보인다는 이유만으로 UC 전체가 정상이라고 판단하지 않는다. 인증, API, 실시간 통신, 첨부파일을 각각 검증한다.

11.3 Kubernetes 객체의 실무 역할

객체역할운영 점검
Node/Pod워크로드 실행 기반과 최소 실행 단위Ready, Restart, OOMKilled, 이벤트
Deployment무상태 워크로드 Replica/배포 관리Desired/Available, rollout
StatefulSet식별자·영속 볼륨 연계 워크로드PVC, 데이터 복원
ServicePod 집합의 안정적 네트워크 진입점Selector, EndpointSlice
Ingress/GatewayHTTP(S) 외부 라우팅Host, 경로, TLS, 컨트롤러

Probe 구분: Readiness는 트래픽 수신 여부, Liveness는 재시작 판단, Startup은 초기 기동 유예다. Liveness를 지나치게 엄격히 설정하면 일시적인 지연이 반복 재시작으로 확대될 수 있다.

11.4 Pod가 사라지면 데이터는 남는가?

Pod는 재생성될 수 있으므로 컨테이너 내부 파일시스템만을 중요한 데이터의 보관 장소로 삼지 않는다.

데이터일반적 저장 방식검증
업무 데이터DB정합성 백업·복원·PITR 지원 여부
첨부파일공유 볼륨 또는 Object Storage다중 Pod 접근·복원
세션/캐시외부 세션 저장소 또는 재인증 설계장애 시 세션 영향
로그외부 수집·보존 시스템Pod 삭제 후 추적 가능 여부

PV/PVC는 백업이 아니며 스냅샷만으로 DB·파일 간 애플리케이션 정합성을 보장할 수 없다. RPO(허용 손실 시간)와 RTO(복구 시간)는 고객 업무 요구를 기준으로 결정하고 실제 복원 시험으로 검증한다.
