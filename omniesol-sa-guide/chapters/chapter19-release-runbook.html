19.13 표준 릴리스 Runbook

Runbook은 명령어 모음이 아니라 중단 조건과 승인 권한이 포함된 운영 절차다. 같은 파일을 STAGE에서 시험했다고 해서 운영의 DB 데이터량, 인증서, DNS, 방화벽, 동접 부하가 같다고 가정할 수 없다. 아래 순서는 일반적 예시이며 제품별 설치/패치 순서는 공식 절차를 우선한다.

단계실행 내용증거·승인
1. Freeze릴리스 범위·의존성·Manifest 동결변경 ID·Artifact SHA·담당자
2. Preflight백업/복구점·버전·용량·권한·알람 기준 확인DBA/운영/보안 GO
3. Dry-runSTAGE 동일 Artifact·설정 차이·해시 검증자동 시험·배포 diff
4. Traffic Control배치·세션·Drain·공지·중단 창 적용업무 책임자 승인
5. DeployDB 호환 확장 → 서비스 → 소비자 순서각 단계 성공/실패 기록
6. Verify기술 Health + 실제 ERP/UC 업무 시나리오오류율·p95·정합성·보안
7. Close알람·백업·관찰 안정화·운영 인수배포 보고·변경 종료
중단 기준

예상하지 못한 DB 오류, 데이터 불일치, 권한 우회, SLO 위반, 배포 대상 해시 불일치가 확인되면 다음 단계로 진행하지 않고 사전 정의된 Stop/Go 판단을 요청한다.

19.14 롤백·복구 의사결정 Matrix

“문제가 나면 롤백”은 불충분하다. 어느 계층을 어떤 시점으로 되돌릴지, 복구 후 데이터 정합성은 누가 검증할지 사전에 정의해야 한다. 특히 DB DDL/데이터 이행 후 애플리케이션만 되돌리면 더 큰 오류가 발생할 수 있다.

19.15 배포 검증: 기능·성능·보안

프로세스가 기동되고 HTTP 200이 반환되는 것은 기술적 생존 신호다. 실제 업무가 성공했는지 확인하려면 승인된 테스트 계정과 비식별 데이터로 대표 시나리오를 실행해야 한다. 배포 직후 5분만 보는 것보다 배치·로그인·장시간 연결의 관찰 창을 분리한다.

검증 영역예시 시나리오판정 기준
ERP 핵심 업무로그인 → 전표 조회 → 저장 → 승인결과·권한·DB 반영 정상
UC/협업로그인 → 메시지/파일 → 알림중복·유실·권한 오류 없음
내부/외부PC·모바일·Proxy 경유·DNS 차이모든 승인 경로 정상
성능p95/p99·에러율·DB Wait·Pool사전 합의 SLO 유지
보안권한 없는 API·TLS·WAF·감사허용 성공·비허용 차단
HA노드 Drain/Failover·재연결승인된 RTO/중단 허용 범위
데이터변경 전후 건수·Checksum·첨부 참조업무 정합성 확인

수치형 승인 기준은 고객별 기준선과 14장 SLO, 16장 부하 시험을 연결해 정의한다. 제품 공통의 임의 p95 임계값을 공식 기준처럼 사용하지 않는다.

19.16 긴급 보안 패치와 예외의 수명

공개 취약점이 보고되면 패치 우선순위는 CVSS 점수만으로 결정되지 않는다. 실제 노출 경로, 악용 징후, 해당 모듈 사용 여부, 업무 중요도, 벤더의 지원 패치, 대체 통제를 함께 평가한다. 긴급 변경도 서비스 차단 가능성과 롤백 경로를 검토해야 한다.

항목운영 원칙
영향 평가제품 버전·실제 사용 기능·노출 경로를 확인
완화 조치접근 제한·WAF 정책 등 임시 통제는 범위·기한 명시
정식 패치지원 Matrix와 비운영 회귀 시험 수행
업무 검증로그인·모바일·SSE/WebSocket·배치·API 재확인
사후 관리예외 만료, 취약점 재검사, 감사 증거 보관
보안 기술 부채

취약점 대응을 이유로 WAF 전체 허용·SELinux 영구 해제·광범위 방화벽 개방을 반복하면 취약점은 줄지 않고 공격 표면만 증가한다.

19.17 변경 책임 RACI·지표·기술적 부채

운영 릴리스의 실패는 종종 기술보다 책임 경계에서 발생한다. 제품 패키지 제공, DB 마이그레이션, 고객 네트워크 변경, 배포 승인, 복구 결정의 소유자를 구분한다. 아래는 교육용 역할 예시다.
