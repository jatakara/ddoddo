19.1 변경의 유형과 위험 등급

SA가 운영 릴리스에서 먼저 판단할 것은 “어떤 명령을 실행하는가”가 아니라 변경 범위·가역성·업무 영향이다. 동일한 패치라도 정적 파일 교체와 DB 스키마 변경의 복구 난도는 다르다. 본 장은 특정 OmniEsol 버전의 공식 절차가 아니라, ERP·UC 현장에서 활용할 수 있는 독립 교육용 변경관리 모델이다.

변경 유형대표 작업주요 위험기본 검증
설정 변경TLS, Reverse Proxy, WAS Pool, DNS서비스 접근·연계 실패구문·라우팅·업무 회귀
애플리케이션 배포WEB/WAS 패키지, UC 이미지API 계약 불일치, 세션 중단버전·업무·성능
DB 변경DDL, 인덱스, 데이터 이행잠금·정합성·복구 난도DBA 승인·백업·전후 비교
플랫폼 패치RHEL, JDK, DBMS, K8s지원성·재기동·드라이버 충돌호환성 Matrix·복구 시험
보안 긴급 변경취약점 완화, 접근제어오탐·업무 차단허용/거부 테스트·예외 만료

운영 위험 등급은 예시로 낮음(L1), 보통(L2), 높음(L3), 긴급(L4)으로 분류할 수 있다. 실제 등급 명칭과 승인 권한은 고객의 변경관리 정책을 우선한다. 긴급 변경도 사후 기록과 만료일을 생략하지 않는다.

핵심 기준

‘서버 한 대만 수정’은 저위험의 근거가 아니다. 단일 DB 스키마, 공통 인증서, 공통 Proxy는 한 대의 변경으로 모든 서비스를 중단시킬 수 있다.

19.2 지원 Matrix와 버전 BOM

지원 Matrix는 “기동된다”는 경험과 “제품 제조사·DBMS·OS가 공식적으로 지원한다”는 사실을 분리하는 표다. 개발에서 실행된 조합도 운영의 장기 패치·장애 지원을 보장하지 않는다. 설치·업그레이드 전에 버전 BOM(Bill of Materials)과 근거 문서를 확보한다.

계층기록할 버전·속성승인 근거
제품 패키지ERP/UC 모듈 버전·빌드·패치 레벨제품 릴리스 노트·지원 Matrix
OSRHEL Major/Minor, Kernel, 필수 RPM공식 지원 OS 목록
WEB/WASWebtoB/JEUS 버전, JDK, 커넥터벤더 호환성·지원 정책
DBMSOracle/Tibero 등 DBMS·클라이언트 버전DBMS·제품 지원 문서·라이선스
KubernetesControl Plane, Node, CNI, CSI, Ingress배포/업그레이드 지원 정책
외부 연계SSO, 메일, API, TLS, 모바일 클라이언트API 계약·인증서·통합시험
가상 BOM 예시 (지원 여부 미확정)
ERP build: release-2026.10.x
UC build: release-2026.10.x
OS: [공식 검증 버전]
WEB/WAS/JDK: [검증된 조합]
DBMS/Driver: [검증된 조합]
K8s/CNI/CSI/Ingress: [검증된 조합]
Source / Build ID / SHA-256: [검증 가능한 값]
Support evidence / Owner / Date: [문서·담당자·일자]

예제의 문자열은 가상 식별자이며 공식 버전이나 설치 권장값이 아니다. 지원 Matrix가 불명확하면 임의로 상위 버전을 선택하지 말고 제품 기술지원의 확인 결과를 승인 기록에 첨부한다.

19.3 변경 흐름과 의존성 그래프

디렉터리 배포는 파일 경로를 기준으로 묶기 쉽지만, 실제 배포 순서는 코드 의존성과 서비스 계약에 의해 결정된다. WEB 정적 리소스, API, DB DDL, UC 연계가 같은 릴리스에 포함될 때는 의존성 DAG(Directed Acyclic Graph)를 먼저 그린다. 순환 의존성이 있으면 릴리스 단위를 재설계해야 한다.

의존성잘못된 순서의 결과검증 방법
WEB JS → API신규 JS가 구 API 필드를 요구신·구 버전 API 계약 테스트
WAS → DB코드가 존재하지 않는 컬럼 참조스키마 호환 시험
UC → ERP 인증토큰/Redirect 불일치SSO 갱신·로그아웃 시험
Proxy → WEB/WASHost/Path 재작성 오류내부·외부 요청 추적
Batch → DB스키마 변경 중 배치 중복/실패배치 정지·재개·재처리 기준

배포 순서와 서비스 시작·중지 순서는 같지 않을 수 있다. 시스템별 롤링 가능 여부와 무중단 조건은 반드시 별도 검증한다.

19.4 디렉터리 기반 배포의 위험

가상 사례: ERP 배포 도구가 변경 파일의 의존성을 계산해 동일 디렉터리의 관련 파일을 일괄 포함한다. 그중 고객별 전용 개발 파일이 아직 검증되지 않았는데도 공통 패키지에 포함된다. 문제는 “개발자가 실수했다”가 아니라 릴리스 대상 파일의 승인 경계가 없다는 점이다.

방식장점한계·기술 부채
디렉터리 전체 배포도입이 빠르고 기존 도구 변경 적음미승인 파일·개발 중 파일 포함 위험
차단 목록(denylist)단기 예외 적용이 쉬움새 파일·이름 변경에 취약, 기본 허용
승인 목록(allowlist)실제 릴리스 파일을 명시적으로 제한초기 목록·의존성 유지 비용
Manifest + 해시 + 검증재현성·추적성·변경 검증 향상도구 연동과 운영 절차 개선 필요
최소 변경 대안

기존 디렉터리 복사 방식은 유지하되, 배포 전 승인 Manifest에 포함된 파일만 선택하고, Manifest 밖의 추가 파일은 기본 차단(fail closed)한다. 의존성으로 자동 확장된 파일도 별도 승인 대상이다.

19.5 승인 Manifest와 파일 무결성

Manifest는 릴리스 파일의 계약서다. 파일 경로뿐 아니라 목적, 버전, 해시, 의존성, 소유자, 승인 상태를 포함한다. 예외 필터만으로 해결할 경우 “왜 제외되었는가”와 “어떤 버전을 운영에 배포했는가”가 남지 않는 기술적 부채가 생긴다.

release_id: REL-EXAMPLE-019
product: ERP
target_environment: PROD
source_revision: "git-commit-placeholder"
artifact_digest: "sha256:<검증된 값>"
approved_files:
  - path: "web/assets/app.js"
    sha256: "<빌드된 파일의 SHA-256>"
    owner: "frontend-team"
  - path: "was/modules/invoice.jar"
    sha256: "<빌드된 파일의 SHA-256>"
    owner: "app-team"
excluded_files:
  - "was/customer-extension/draft/*"
dependency_review: "APPROVED"
security_review: "APPROVED"
change_ticket: "CHG-EXAMPLE-019"
rollback_artifact: "REL-EXAMPLE-018"
  • 경로는 정규화하고 .., 절대경로, 심볼릭 링크 탈출을 차단한다.
  • 패키지 해시와 실제 배포 직전 파일 해시를 비교한다.
  • 중복 경로·대소문자 충돌·기존 파일 덮어쓰기를 검출한다.
  • Manifest 밖 파일은 자동 추가하지 않고 별도 승인 요청으로 분리한다.
  • 운영 배포 계정에는 개발 브랜치·테스트 산출물에 대한 직접 쓰기 권한을 주지 않는다.

SHA-256은 동일성 검증에 유용하지만 신뢰성을 단독으로 보장하지 않는다. 서명된 빌드 출처, 접근 통제, CI 로그, SBOM 등 공급망 검증을 병행한다.

19.6 개발·운영 배포 경로 분리와 사전 승인

기존 배포 시스템에 예외 필터가 있고 신규 배포 시스템에는 없다면 두 시스템을 병행하는 과도기 방안을 검토할 수 있다. 다만 개발용과 운영용 시스템을 복제해 영구 유지하면 정책·패치·감사 기능이 서로 달라지는 문제가 생긴다.

대안장점단점권고
개발/운영 배포 도구 2개 병행긴급 격리와 기존 예외 기능 활용설정 Drift·이중 유지보수·배포 추적 분산기한을 둔 임시 방안
단일 도구 + 환경별 승인 정책공통 감사·정책 관리, 운영 일관성정책 엔진 추가 개발 필요목표 아키텍처
운영 승인 Manifest만 추가기존 디렉터리 배포 최소 수정의존성·정합성 검증 추가 필요단기 우선 개선
Go/No-Go

공식 지원 조합, 전체 변경 파일 목록, 의존성 승인, 운영 복구점, 담당자, 업무 중단 범위, STAGE 결과가 없으면 배포를 시작하지 않는다.
