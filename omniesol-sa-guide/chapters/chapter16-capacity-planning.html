16.11 CPU 수요량을 실측 기반으로 계산

초기 사양은 등록 사용자 수보다 목표 RPS × 요청당 평균 CPU 소모량으로 검증하는 것이 낫다. 요청당 CPU Time과 사용자 응답시간은 다르다. 응답이 300ms 걸렸다고 CPU를 300ms 사용한 것은 아니다. DB/네트워크 대기와 스레드 큐 시간은 별도다.

가상 AP CPU 예제
목표 요청량: 120 RPS
요청당 AP CPU Time: 12ms = 0.012 CPU-seconds
평균 AP CPU 수요: 120 × 0.012 = 1.44 vCPU
평균 CPU 사용률 목표: 60%
필요 AP 계산 용량(이론치): 1.44 / 0.60 = 2.40 vCPU
초기 배치 검토 후보: 3 vCPU 상당 AP 자원
주의: GC, OS, 배치, 가상화, 피크 변동, DB·UC 자원 별도

3 vCPU는 위 가상 AP 처리량에 대한 이론적 출발점일 뿐, ERP 전체 최소 사양이나 제조사 권장 수치가 아니다. CPU Time은 업무 Mix에 따라 달라지고 병렬 처리 효율이 일정하지 않으므로 실측이 필요하다.

CPU 증설의 한계

DB Lock·I/O·연계 API가 병목일 때 AP CPU를 증설해도 지연이 해결되지 않을 수 있다. 먼저 포화 계층을 식별하고, 실제 성공 TPS와 p95를 비교한다.

16.12 메모리는 JVM Heap만 보지 않는다

Java 프로세스 메모리는 Heap 외에도 Metaspace, Thread Stack, Direct Buffer, JIT, Native Library 등을 포함한다. JVM 최대 Heap 8GiB를 설정했다고 RSS가 8GiB로 고정되는 것도 아니고, 8GiB가 즉시 전부 할당되는 것도 아니다.

영역확인 항목흔한 오류
WAS/JVMHeap, Non-Heap, RSS, Thread, GC PauseHeap만 합산해 물리 메모리 결정
OSAvailable, Page Cache, Swap, OOM캐시를 전부 회수 불가능한 사용량으로 오해
Oracle DBSGA, PGA, 세션, HugePages, OS 여유PGA 피크와 백업·배치 부하 누락
KubernetesPod Requests/Limits, Node AllocatableLimits 과소 설정으로 OOMKilled
공유 서버WAS+DB+OS+파일 캐시+운영 작업독립 산정한 자원을 단순 합산하지 않음

CPU Limit은 throttling을 유발할 수 있고, Memory Limit 초과는 OOM 종료로 이어질 수 있다. Requests는 주로 스케줄링의 예약 기준이다. Kubernetes Resource Management 공식 문서를 참고한다.

16.13 Kubernetes N+1: 장애 후 수용력을 계산

Node Allocatable은 Pod가 사용할 수 있는 노드 자원이다. kube/system 예약이 반영되지만, DaemonSet처럼 Pod로 실행되는 시스템 구성요소의 Requests는 별도로 고려해야 한다. 환경별 Allocatable과 실제 DaemonSet Requests를 확인해 중복 차감하지 않는다.

가상 CPU N+1 계산
노드당 Node Allocatable: 8 vCPU
노드당 DaemonSet Requests: 1 vCPU
업무 Pod용 예약 예산: 8 - 1 = 7 vCPU
업무 Pod Requests 합계: 12 vCPU
내부 목표: 장애 후 예약 비율 75% 이하

[3노드 구성]
노드 1대 장애 후 2대 잔존
예약 가능 예산: 2 × 7 = 14 vCPU
장애 후 예약 비율: 12 / 14 = 85.7%
결과: CPU 예약 여유 기준 NO-GO

[4노드 구성]
노드 1대 장애 후 3대 잔존
예약 가능 예산: 3 × 7 = 21 vCPU
장애 후 예약 비율: 12 / 21 = 57.1%
결과: CPU 예약 여유 기준 통과
단, Memory·Pod 배치·Storage·실제 부하 시험은 별도
추가 검증필요 이유실제 확인
Memory N+1CPU가 충분해도 메모리 부족으로 Pending 발생Allocatable·Requests·실사용량
Pod 크기/분산총합이 충분해도 큰 Pod가 노드에 못 들어갈 수 있음실제 재스케줄링·Affinity·TopologySpread
PVC/Zone볼륨의 노드/Zone 종속성으로 재시작 실패재연결·마운트·업무 데이터 검증
CPU Limit/실사용Requests만 통과해도 피크에 Throttle 발생p95·Throttle·CPU·OOM
공통 서비스LB, DNS, DB, Control Plane도 장애 가능계층별 장애·복구 시험

위 예제는 CPU Requests의 예약 여유만 판단한다. 실제 N+1 승인은 피크 120 RPS를 유지하면서 노드 1대 장애 후에도 성공 TPS, p95/p99, 데이터 정합성과 RTO/RPO가 충족될 때 가능하다. Node Allocatable 공식 문서를 참고한다.

16.14 스토리지 성장과 복구 공간 계산

스토리지 계획은 현재 DB 크기만으로 끝나지 않는다. 데이터 파일, 인덱스, redo/archive, Temp, 백업, 첨부파일, 재구축 중 임시 공간을 분리한다.

가상 데이터 볼륨 계산 (GiB)
초기 데이터: 400 GiB
연평균 증가율: 20%
3년 후 예상 데이터: 400 × 1.2³ = 691.2 GiB
목표 사용률 상한: 70% (30% 여유)
필요 볼륨: 691.2 / 0.70 = 약 987.4 GiB
검토 후보: 1 TiB(=1024 GiB) 이상
미포함: 백업·Archive·Temp·복제 여유·기타 파일
영역별도 산정이 필요한 이유
DB 데이터/인덱스업무 건수·삭제/보존 정책·인덱스 성장
Redo/Archive쓰기 피크·백업 주기·복구 지점
Temp대용량 정렬·보고서·배치
첨부파일문서 크기 분포와 보관 기간
백업/DRFull/Incremental 보관·독립 장애 도메인
I/O 성능IOPS·Throughput뿐 아니라 p95/p99 지연

단일 벤치마크에서 측정된 최대 GB/s를 실제 업무 트랜잭션 처리량으로 환산해서는 안 된다. DB의 랜덤 I/O, Commit Latency와 스토리지 공유 상태를 함께 측정한다.

보안·운영 부채

성능 때문에 WAF를 우회하거나 인증·감사 기능을 끄는 것은 적절한 튜닝이 아니다. 부하를 유발하는 정책은 최소 범위로 원인을 분리하고 보안 담당과 대안을 검증한다. 미검증 자동 확장 규칙은 DB 연결 폭증과 장애 전파를 일으킬 수 있다.
