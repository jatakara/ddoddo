공개 교육용 참조 설계

실제 고객·내부 시스템 정보, 인증정보, 비공개 구성은 포함하지 않는다. 모든 공격·복구 실습은 격리된 환경에서 수행한다. 실제 지원 버전·계약·보안 정책이 우선한다.

참조 아키텍처

Developer → Reviewed PR → CI (SAST/SCA/Secret Scan)
         → Isolated Build → SBOM + Provenance + Signature
         → Artifact Registry → Admission Policy
Operator (SSO/MFA) → Controller → Policy Engine
                                 ↓ Approved job (TTL, hash)
                         Isolated Action Runner → ERP/UC/DB
                                 ↓
                          Immutable Audit Evidence

확장성: 테넌트별 큐와 Runner 동시성 한도를 두고 중앙 Policy Engine·Audit Store의 병목을 측정한다. 보안: 신원·승인·실행·감사 경계를 분리하고 변경 권한은 기본 거부한다.

29.7 신원과 권한 경계

운영자 SSO/MFA, API 서비스 계정, Controller, Policy Engine, Runner, 대상 시스템의 신원을 구분한다. RBAC는 역할 기반 권한, ABAC는 환경·시간·자산 중요도 등 속성 기반 제약이다. 승인 권한과 실행 권한을 동일 계정에 집중하지 않는다.

29.8 승인 토큰과 TOCTOU

승인 시점과 실행 시점 사이에 대상·명령·파라미터가 바뀌는 TOCTOU 위험이 있다. 승인 객체에 job ID, 대상 자산 ID, 작업 종류, 인수 해시, 정책 버전, 만료 시각, 승인자 ID를 묶어 서명·검증한다. 실행 직전 재인가하며 만료·재사용·대상 변경을 거부한다.

29.9 비밀정보 생명주기

비밀정보는 발급 → 저장 → 접근 → 회전 → 폐기 단계를 관리한다. 평문 환경변수·명령 인수·로그 노출을 피하고 전용 Secret Manager와 짧은 TTL을 우선한다. 긴급 회전 훈련에서 연결 복구 시간과 구 토큰 차단 여부를 확인한다.

29.10 테넌트·환경 격리

테넌트별 자산 목록, 정책, 큐, 실행 자격증명, 감사 조회 범위를 분리한다. DEV 자격증명이 PROD를 제어하지 못해야 한다. 공유 Controller의 비용 효율은 높지만 권한 설정 오류의 폭발 반경이 커진다. 고위험 환경은 Runner·네트워크를 별도 격리한다.

29.11 정책 변경 관리

Policy-as-Code는 변경 PR, 2인 검토, 테스트, 버전 서명, 단계적 배포와 롤백을 거친다. DENY 정책을 임의로 비활성화하는 break-glass는 시간 제한·사유·별도 승인·사후 리뷰를 요구한다. 감사 저장소 장애 시 신규 변경은 중단한다.

29.12 공격 시나리오 실습

실습망에서 승인 토큰 재사용, 파라미터 변경, 만료 토큰, 교차 테넌트 자산 접근, 로그에 삽입된 비밀정보를 테스트한다. 예상 결과는 전부 DENY 또는 마스킹이며, 실패 사례의 요청 ID와 정책 결정 근거를 증거로 남긴다.

현장 점검 및 참고 표준

검증은 요청 ID, 정책 버전, 아티팩트 digest, 승인자, 대상 ID, 결과 로그로 추적한다. 기준 자료: SLSA v1.0, NIST SSDF SP 800-218, OWASP Top 10, Kubernetes Security. 제품별 지원 여부는 별도 검증한다.
