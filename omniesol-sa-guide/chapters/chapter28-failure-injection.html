공개 교육용 참조 설계

실제 고객·내부 시스템 정보 및 인증정보를 포함하지 않는다. 시험은 격리된 실습 환경에서 수행한다. 수치와 합격선은 예시이며 실제 지원 사양·계약·운영 정책이 우선한다.

28.7 장애 주입의 기본 원칙

Fault injection은 서비스 복구 시간뿐 아니라 승인되지 않은 조치가 실행되지 않는지 확인하는 안전성 시험이다. 반드시 별도 테스트 환경에서 시행하고 실제 운영망에 패킷 차단·프로세스 종료·디스크 고갈을 주입하지 않는다. 실험마다 중단 조건과 원복 담당자를 지정한다.

28.8 Controller 및 Leader 장애

작업 승인 직전, 승인 직후, 실행 직전에 Controller를 각각 중지한다. 복구 시 승인 토큰의 유효기간·대상·작업 해시를 재검증한다. 두 Controller가 같은 job을 동시에 실행하지 않도록 lease/fencing과 idempotency key를 확인한다.

28.9 Queue 중단과 재전달

브로커 중단, 네트워크 분리, 메시지 중복, 순서 역전, TTL 만료를 주입한다. At-least-once 전달에서는 중복 수신이 정상적으로 발생할 수 있으므로 exactly-once를 전제하지 않는다. 재처리 시 이미 수행된 변경은 실행 결과 조회 또는 멱등성 검증으로 차단한다.

28.10 Policy·Identity 장애

정책 서버 불가, 서명 오류, 만료 정책, IdP 토큰 갱신 실패를 각각 시험한다. 정책 판단 불가 시 신규 변경은 DENY, 읽기 전용 수집은 정책상 허용된 범위에서만 계속한다. 캐시된 과거 승인을 무기한 재사용하지 않는다.

28.11 Audit Store 및 Evidence 장애

감사 저장소 쓰기 실패, 지연, 스토리지 read-only 전환을 재현한다. 감사 기록의 내구성을 보장할 수 없으면 신규 변경을 차단한다. 장애 직전 시작된 작업은 안전 중단점에서 멈추고 불명확한 결과를 SUCCESS로 기록하지 않는다.

28.12 실행기와 대상 시스템 장애

Runner 프로세스 종료, SSH 세션 단절, 대상 API timeout을 시험한다. timeout은 실패의 증거가 아니라 결과 미확정 상태다. 대상 상태를 재조회하고 재실행 여부를 승인자가 결정한다. 재시작, 패치, 데이터 변경은 자동 무한 재시도를 금지한다.

Safety gate: 승인 무결성 + 실행 중복 방지 + 감사 기록

확장 시 Worker 증설보다 상태 저장소, 큐 파티션, 외부 API rate limit, 테넌트별 공정 스케줄링의 병목을 먼저 확인한다. TLS, 최소 권한, 단기 자격증명, 비밀정보 마스킹, 감사로그 변조 탐지를 시험 범위에 포함한다.
