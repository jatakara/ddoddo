10장 2부. ERP 고가용성과 복구

10.5~10.8 · 장애 영역, 세션, DB 정합성, RPO/RTO, DR

10.5 장애 격리와 고가용성(HA)

가용성 설계는 장애를 없애는 것이 아니라, 장애 발생 시 영향 범위를 줄이고 정상 상태로 복귀하는 시간을 통제하는 것이다. WEB/WAS 이중화와 DB 이중화는 해결하는 문제가 다르다.

장애 상황영향설계·검증 항목
WEB/WAS 프로세스 장애일부 요청 실패 또는 세션 단절헬스체크, 연결 배제, 재시도 안전성, 세션 처리
물리 호스트 장애같은 호스트 VM 동시 중단서로 다른 호스트·장애 영역에 배치
로드밸런서 장애모든 요청의 진입점 상실LB 자체 이중화와 DNS/가상 IP 전환
DB 장애쓰기 불가, 데이터 정합성 위험공식 지원 HA, 전환 절차, 복제 지연과 무결성
공유 스토리지 장애다수 계층 동시 영향독립 장애 영역과 복원 가능성
N+1의 의미: 정상 시 N개의 노드가 처리하는 부하를 장애 시 남은 노드가 수용할 수 있어야 한다. 2대가 각각 90% 사용 중이면 한 대 장애 시 서비스 유지가 어려울 수 있다.

10.6 세션·연결 풀·배포 중 가용성

WAS를 여러 대로 늘리면 요청 분산은 쉬워지지만, 로그인 상태·업무 중 임시 데이터·장기 요청·DB 연결의 일관성이 새로운 설계 과제가 된다.

구성 요소설계 질문
사용자 세션세션 고정(Sticky) 여부, 세션 공유·복원 가능성, 장애 시 재로그인 정책
DB 연결 풀WAS 인스턴스 증가 시 DB 최대 연결 수를 초과하지 않는가?
헬스체크프로세스 생존 확인과 실제 업무 준비 상태를 구분하는가?
배포요청 Drain, 세션 종료, 롤백 기준, 스키마 호환성을 검증했는가?
재시도결제·전표·승인 등 중복 실행 위험이 있는 작업을 무조건 재시도하지 않는가?
헬스체크 200 OK는 업무 정상성을 증명하지 않는다. 로그인·핵심 조회·쓰기 트랜잭션·외부 연계의 합성 테스트를 별도로 둔다.

10.7 DB 고가용성과 트랜잭션 정합성

DB의 이중화 방식은 엔진과 라이선스, 제품 검증 범위에 따라 달라진다. 동기·비동기 복제, 자동 전환, 단일 쓰기 노드 정책을 검토하고 애플리케이션의 재접속 동작을 함께 시험한다.

설계 항목실무 검증
복제쓰기 확정 기준과 복제 지연을 확인한다.
전환Failover 중 연결 실패·재연결·타임아웃을 측정한다.
Split-brain동시에 두 쓰기 노드가 활성화되지 않도록 제어한다.
정합성전환 전후 전표·첨부·시퀀스 등 핵심 데이터 일관성을 검증한다.
백업복제는 백업이 아니며 삭제·논리 오류도 복제될 수 있음을 전제한다.

Oracle 등 특정 DB를 사용할 경우에도 이 문서의 일반론보다 공급사 공식 지원 조합과 DBA 검증 결과를 우선한다.

10.8 백업·복구·DR 설계

서비스 중요도에 따라 RPO(허용 데이터 손실)와 RTO(목표 복구 시간)를 합의한 뒤 기술을 선택한다. '백업이 있다'와 '목표 시간 안에 복구된다'는 서로 다른 주장이다.

시나리오필요한 복구 설계검증 방식
단일 WAS 장애다른 인스턴스로 요청 우회인스턴스 중단 시험
DB 손상정합성 백업 + 로그 기반 시점 복구별도 환경 복원·데이터 검증
랜섬웨어·관리 실수격리된 불변 백업, 권한 분리백업 삭제 저항성과 복구 시험
센터 전체 장애DR 사이트, 데이터 동기화, DNS·접속 전환업무 시나리오를 포함한 DR 리허설
가상 예시: 업무가 RPO 15분, RTO 2시간을 요구한다면 백업 주기만 15분으로 정해서는 부족하다. 백업 정합성·로그 적용·DNS 전환·업무 검증까지 2시간 이내에 끝나는지 측정해야 한다.
