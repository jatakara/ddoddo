9장 OS·Network·Storage 기본 개념

서버가 느리다고 CPU부터 늘리지 않는다. 요청이 어느 구간에서 지연되는지 먼저 확인한다.

2026-10 · 공개 교육용 독립 기술 자료

9.1 학습 목표와 범위

ERP·UC 장애는 OS, Network, Storage 중 하나의 문제처럼 보이지만 실제로는 여러 계층의 지연이 합쳐져 발생한다. 이 장은 서버가 느리다는 신고를 받았을 때 무엇을 먼저 측정해야 하는지 설명한다.

영역실무 질문
OSCPU·메모리·프로세스·파일시스템 중 실제 병목은?
NetworkDNS, TCP, TLS, Proxy, 인증 중 어느 단계에서 실패하는가?
Storage용량이 남아도 DB 응답이 느린 이유는?
이 문서는 일반 인프라 교육용이다. OmniEsol 공식 지원 사양·포트·검증 버전은 최신 공식 자료를 우선한다.

9.2 요청 처리 경로

브라우저 / 모바일 앱
    │ DNS 조회 · TCP · TLS
    ▼
[WAF / L4·L7 / Reverse Proxy]
    │ Host · Path · 헤더
    ▼
[WEB / WAS / ERP] ─────→ [DB / Storage]

[UC 도메인] → [Ingress / Service] → [UC 워크로드]

화면이 열린다는 사실은 모든 기능이 정상이라는 뜻이 아니다. 기본 HTML은 성공했지만 별도 UC 도메인의 iframe, API 또는 실시간 연결만 실패할 수 있다. 요청별 FQDN → DNS IP → TLS 종단 → 백엔드 → DB를 문서화한다.

9.3 Linux OS: CPU·메모리·프로세스

CPU와 Load Average

CPU 사용률은 CPU가 실제 작업을 처리한 시간의 비율이다. Load Average는 실행 가능하거나 일부 I/O 대기 중인 작업 수의 평균으로 CPU 사용률과 동일하지 않다. 논리 CPU 개수, 작업 상태, 가상화 환경의 steal time을 함께 본다.

지표해석
user/system사용자·커널 코드 처리 비율. 높은 프로세스와 처리량을 함께 비교한다.
iowaitCPU 유휴 시간 중 I/O 대기 비중. 스토리지 병목의 단독 증거가 아니다.
stealVM이 실행을 원했으나 하이퍼바이저가 CPU를 제공하지 못한 시간.
load 1/5/15작업 부하 추세. CPU 수와 D 상태 프로세스를 함께 확인한다.
uptime
nproc
vmstat 1 5
ps -eo pid,comm,%cpu,%mem,state --sort=-%cpu | head

메모리

Linux는 남는 메모리를 페이지 캐시로 사용한다. free 값이 작다는 이유만으로 부족하다고 판단하지 않는다. available, swap 변화, OOM 로그, JVM Heap·Native Memory·DB Buffer·OS Cache의 합계를 확인한다.

free -h
cat /proc/meminfo | head -n 20
systemctl --failed
ss -lnt
서비스 프로세스가 살아 있다는 것과 사용자의 요청에 정상 응답한다는 것은 다른 사실이다. 헬스체크와 실제 업무 기능을 별도로 검증한다.

9.4 파일시스템과 로그

디스크 사용량은 바이트 기준과 inode 기준을 함께 본다. 파일이 지나치게 많으면 여유 공간이 있어도 쓰기에 실패할 수 있다. 파일시스템 읽기 전용 전환, 권한, SELinux, 로그 로테이션도 확인한다.

df -hT
df -i
findmnt
lsblk -f
journalctl -p warning --since '1 hour ago' --no-pager | tail -n 30
증상점검
로그 기록 실패용량·inode·권한·마운트·보안 정책
서비스 기동 실패서비스 로그·포트 중복·설정·파일 권한
로그 급증오류 시각·로그 레벨·로테이션 정책

장애 분석에 필요한 로그를 임의로 삭제하지 않는다. 개인정보·인증정보가 로그에 남지 않도록 관리한다.

9.5 TCP/IP·Routing·Firewall

단계성공 조건주요 실패 원인
DNS기대 FQDN에 맞는 IP 반환Split DNS, 캐시, hosts
Routing올바른 목적지·소스 경로비대칭 경로, NAT
TCPSYN → SYN/ACK → ACK방화벽, 리슨 포트, 패킷 손실
TLS인증서·프로토콜 협상 성공SNI, 체인, TLS 정책
HTTPHost·Path에 맞는 정상 응답Proxy, WAF, 인증, WAS
ip -br addr
ip route
ip route get 192.0.2.20
ss -tn state established
getent ahostsv4 erp.example.test

위 주소와 도메인은 설명용 예약 값이다. NAT는 주소·포트 변환이고 Reverse Proxy는 HTTP 요청의 전달·재구성·헤더·TLS 정책을 수행한다. 두 기능을 혼동하지 않는다.

9.6 DNS·TLS·Proxy와 인증

내부와 외부 사용자가 동일한 도메인을 조회해도 DNS 정책에 따라 다른 IP를 받을 수 있다. 브라우저 기본 페이지가 보이더라도 UC iframe은 별도 도메인, 세션 쿠키, CSP, CORS 또는 인증 리다이렉트 문제로 실패할 수 있다.

getent ahostsv4 uc.example.test
openssl s_client -connect uc.example.test:443 -servername uc.example.test </dev/null
curl -I --connect-timeout 5 https://uc.example.test/
증상확인 순서
외부만 정상내·외부 DNS, 경로, 방화벽, 인증 URL 비교
iframe만 실패iframe URL, CSP frame-ancestors, SameSite/Secure, 인증 세션
502/504프록시에서 백엔드로의 연결·TLS·타임아웃 확인
일부 API 실패Host/Path, CORS, 인증 헤더, WAF 탐지 로그
TLS 검증을 영구적으로 해제하거나 WAF 전체를 예외 처리하지 않는다. 최소 범위·기간·책임자·원복 조건을 명시한다.

9.7 Storage: 용량과 성능을 구분한다

지표의미실무 해석
IOPS초당 I/O 처리 횟수작은 랜덤 I/O에 중요
Throughput초당 전송량대용량 순차 처리에 중요
LatencyI/O 완료 시간평균뿐 아니라 p95/p99 확인
Queue Depth동시 대기·진행 I/O 수부하 증가 시 지연 변화 확인

예를 들어 8KiB I/O를 초당 4,000회 처리하면 이론적 데이터량은 약 31.25MiB/s다. 하지만 동시성·캐시·동기식 쓰기·지연이 다르므로 이 값만으로 DB 성능을 판단할 수 없다.

lsblk -o NAME,SIZE,TYPE,MOUNTPOINTS
findmnt
iostat -xz 1 5  # sysstat 설치 시
선택장점Trade-off
로컬 NVMe낮은 지연·단순 경로노드 장애 시 데이터 가용성·복제 설계 필요
SAN/NAS공유·중앙 관리컨트롤러·네트워크 경합 및 다중 경로 점검
가상 디스크할당·이동 편의호스트 오버커밋·스냅샷·물리 성능 확인

백업 성공과 복구 성공은 다르다. RPO/RTO, 복구 시나리오, 복구 테스트 증적을 별도로 관리한다.

9.8 장애 분석 순서

단계수집할 증거

② 브라우저HAR, 실패 URL, 상태 코드, TTFB, 다운로드, 렌더링 시간

④ OS/WASCPU·메모리·GC·스레드·연결 풀·로그
⑤ DB/Storage느린 SQL·잠금·I/O 지연·파일시스템
⑥ 검증동일 부하의 변경 전후 비교·영향·원복

한 번의 CPU 스냅샷보다 정상 시점과 장애 시점의 동일 지표 비교가 중요하다. 임계치는 업무 SLO, 정상 기준선, 공식 문서에 근거해 정한다.

9.9 실무 사례: 로그인 후 화면 지연

가상 사례: 로그인 후 첫 화면이 15초 이상 지연되지만 CPU 사용률은 높지 않다. 서버 증설을 결정하기 전에 다음 가설을 검증한다.

가설검증 방법
WAS 처리 지연TTFB와 WAS 처리 시간·DB 쿼리 시간 비교
응답 데이터 과다응답 크기·압축·페이로드 구성 확인
브라우저 렌더링Performance 프로파일의 JS·레이아웃 시간 확인
프록시 지연승인된 시험 환경에서 동일 요청의 경로별 시간 비교
서버 응답 대기가 대부분이면 WAS·DB·프록시를 우선 조사한다. 다운로드 후 시간이 오래 걸리면 JS·DOM 렌더링을 먼저 본다. CPU 사용률만으로 결론 내리지 않는다.
