특정 고객·제품 버전의 공식 설치·지원·복구 매뉴얼이 아니다. 모든 수치와 토폴로지는 가상 예시다. 실서버 복구·전환·삭제는 공식 지원 Matrix, 백업 소유자, 보안 정책, 변경 승인과 복구 훈련을 전제로 한다.

18.13 DR 아키텍처 선택과 Trade-off

DR 설계는 단순히 “원격지에 서버 한 대 더 설치”가 아니다. 장애 범위, RTO/RPO, 운영 비용, 네트워크 지연, 라이선스, 인력 가용성에 따라 Cold/Warm/Hot Standby와 Active-Active를 비교해야 한다. 아래는 일반적인 참조 구조이며 OmniEsol의 특정 배포 지원을 보증하지 않는다.

방식장점한계·비용검증할 조건
Cold Standby상시 운영비 낮음설치·데이터 복원으로 RTO 길어짐이미지·키·자동화 재현성
Warm Standby복구 속도와 비용 절충사전 자원·복제 관리 필요동기화·증설·연계 테스트
Hot Standby빠른 전환 가능상시 자원·운영 비용 높음복제 지연·쓰기 차단·전환 시험
Active-Active동시 서비스·분산 가능데이터 충돌·복잡성·운영 부담 매우 큼제품 공식 지원·분산 일관성

Active-Active는 비용 대비 가용성이 좋아 보일 수 있으나 데이터 일관성과 제품 지원성이 충족되지 않으면 위험하다. 업무별로 Active-Passive를 기본 비교 대상으로 놓고 기술 검증 결과에 따라 선택한다.

18.14 DR 전환 Runbook: 선언부터 개방까지

실제 장애에서 가장 어려운 것은 명령 입력이 아니라 누가 전환을 결정하고 어떤 데이터 시점을 선택하는지다. Runbook에는 승인자, 통신 수단, 판단 시간, 복구 시점, 되돌릴 수 없는 작업과 증거를 포함한다.

단계책임자(예시)필수 확인/승인
탐지·영향 분석운영/관제장애 범위·마지막 정상 시각
DR 선언업무 책임자·Incident CommanderRTO 위협·전환 조건·고객 공지
원본 쓰기 차단(Fencing)DBA·네트워크Split-brain/이중 쓰기 방지 증거
복구 시점 확정DBA·업무 책임자마지막 안전한 로그/파일 시점·RPO
인프라/데이터 기동플랫폼·DBA복원 성공·키·서비스 계정·권한
업무 검증업무 QA·운영로그인·조회·저장·승인·첨부·연계
DNS/LB 전환네트워크·보안내외부 접근·TLS·WAF·SSO
개방·사후 기록Incident CommanderGo/No-Go·고객 공지·남은 위험
이중 쓰기 위험

원본 사이트가 불안정하지만 살아 있는 상태에서 DR 사이트의 쓰기를 먼저 열면 두 곳의 데이터가 갈라질 수 있다. DB·애플리케이션·외부 송신 경로를 포함한 Fencing 절차가 필수다.

18.15 DR 전환 시간 예산과 DNS의 함정

전환 절차별 소요시간을 미리 할당하면 RTO 미달 원인을 찾기 쉽다. 다음은 가상 시간 예산이다. 전체 120분 목표를 맞추려면 모든 단계를 단순히 120분 이내에 시작하는 것으로는 부족하다.

가상 RTO 예산 (총 120분)
장애 탐지·선언           10분
원본 쓰기 차단·데이터 확인 15분
DR DB/스토리지 기동       40분
ERP·UC 애플리케이션 기동   20분
DNS/LB/보안 경로 전환     10분
업무·데이터 정합성 검증    25분
합계                    120분
주의: 단계 간 병렬 처리 가능 여부를 시험으로 검증

DNS TTL을 60초로 설정했다고 모든 사용자 연결이 60초 이내 전환되는 것은 아니다. 리졸버·클라이언트 캐시, 장시간 연결, 모바일 앱 내부 주소, 외부 API Allowlist, 인증서와 세션 유지 정책이 영향을 준다. 외부망과 내부망을 분리해 재접속 시험한다.

검증 대상대표 실패 사례대응 설계
DNS/TTL캐시·분산 리졸버 지연전환 전후 다중 네트워크 시험
TLS/WAFDR 인증서 누락·Host 불일치동일 보안 정책·인증서 관리
SSO/IdPDR URL Redirect 불일치사전 등록·토큰/쿠키 시험
외부 연계파트너 IP Allowlist 미갱신사전 승인·대체 접속 경로
배치/큐양 사이트에서 중복 실행배치 잠금·멱등성·전환 체크리스트

18.16 복구 훈련과 장애 주입 시나리오

DR은 문서 검토만으로 검증되지 않는다. 서비스 장애와 데이터 복구는 서로 다른 훈련이다. 운영 데이터 대신 가상·비식별 데이터를 사용하고, 처음에는 독립된 시험 환경에서 복원한 뒤 승인된 범위에서 단계적으로 실환경 전환 훈련을 수행한다.

시나리오관찰 항목통과 기준(예시)
AP 노드 1대 중단업무 오류율·N+1 재배치핵심 거래 성공
ERP DB 파일 손상백업 검색·RMAN Validate·복원DB OPEN + 거래 정합성
UC 첨부파일 유실메타데이터·원본 파일 연결복구 대상 파일 접근 성공
백업 저장소 접근 장애오프사이트/격리 사본대체 경로로 복원
주센터 전체 불능DR 선언·데이터·DNS/SSO 전환승인된 RTO/RPO 충족
관리 계정 탈취 가정백업 삭제 차단·키 격리보안 통제/감사 증거 확보

복구 훈련 기록에는 시작/종료 시각, 사용한 백업 세트와 로그의 식별자(민감정보 제거), 데이터 복구 시점, 정상 업무 완료 시각, 결함, 담당자, 개선 완료 예정일을 남긴다.

'서버만 이중화'와 '백업 성공이면 복구 완료'라는 문구는 향후 대규모 장애에서 치명적인 운영 부채가 된다. 실제 업무 성공까지 복구 시간을 측정하고, 복구 의존성을 코드·구성·문서로 관리해야 한다.
