20.13 자동화 성숙도와 책임 경계

자동화는 반복 작업을 빠르게 실행할 수 있지만, 잘못된 판단도 빠르게 확산시킨다. 특히 ERP DB·Kubernetes·방화벽의 변경은 다수 서비스에 영향을 줄 수 있으므로 관찰(Read-only)과 변경(Mutation)을 엄격하게 분리한다.

수준허용 범위예시통제
L0 수동사람이 수집·판단·실행점검표 수동 작성승인·이력
L1 자동 관찰읽기 전용 점검/보고OS·DB·Pod 상태 수집RBAC 최소권한
L2 자동 진단가설·증거·위험 추천Proxy 502 원인 후보 순위신뢰도·증거 출처
L3 승인형 복구사람이 승인 후 실행승인된 Runbook 재기동범위·만료·원복·감사
L4 제한된 자율 복구사전 승인된 저위험 작업만검증된 격리된 환경에서의 자동 처리강한 정책·중단 스위치·사후검증

AI가 추천한 조치가 곧 실행 권한을 의미하지 않는다. 특히 고객사 운영환경의 DB 복원, 보안 정책 변경, Pod/Node 강제 삭제는 자동화 수준을 높인다는 이유로 무승인 실행하지 않는다.

20.14 진단·복구 참조 아키텍처

Policy Engine은 진단 결과와 분리한다. AI 모델이 텍스트로 “안전하다”고 말해도, 승인 범위 밖의 명령은 실행기가 거부해야 한다. 승인 객체는 작업 ID, 대상, 명령 해시, 유효시간, 승인자, 예상 영향과 롤백 계획을 포함한다.

안전 경계

실행기는 고정된 Runbook ID와 허용 파라미터만 받는다. 자연어를 셸 명령으로 직접 실행하거나, 로그 내용에 포함된 명령을 실행하지 않는다.

20.15 읽기 전용 자동 점검 예시

자동 점검은 OS/WEB/WAS/DB/K8s의 상태를 모으되 인증정보와 업무 데이터를 수집하지 않는 방향으로 시작한다. 아래 명령은 승인된 관찰 권한을 가정한 예시이며, 환경별 호환성과 정보 노출 위험을 검토한다.

free -h
df -hT

journalctl --since "10 minutes ago" --priority=err --no-pager

kubectl -n demo get pods -o wide
kubectl -n demo get svc,endpointslices
kubectl -n demo get events --sort-by=.lastTimestamp

# 참고: logs/describe는 민감정보 노출 가능.

관찰 결과는 수집 시각, 명령 버전, 대상, 실행 주체, 실패 여부와 함께 저장한다. 비정상만 출력하면 정상 지표와 시간축을 비교하기 어렵다.

20.16 Runbook 승인·실행 계약 예시

다음 YAML은 설계 문서용 가상 계약이다. 특정 자동화 엔진에 바로 적용되는 실행 파일이 아니며, 위험 명령은 포함하지 않는다. 대상 식별과 권한 검증, 승인 만료, 실행 중단 조건을 명시한다.

apiVersion: operations.example.invalid/v1
kind: ApprovedRunbookRequest
metadata:
  requestId: INC-DEMO-0020
spec:
  environment: stage
  target:
    service: erp-web
    scope: one-instance
  runbookId: inspect-http-upstream-v1
  mode: read-only
  approval:
    required: true
    approverRole: oncall-operator
    expiresAt: "2026-11-02T02:00:00Z"
  guardrails:
    maxDurationSeconds: 60
    allowShellFromUserInput: false
    denySecretsInOutput: true
    requireAuditLog: true
  verification:
    expectedEvidence:
      - http-status
      - upstream-health
      - recent-change-id

실제 실행기는 runbookId를 버전 고정된 코드와 매핑하고, scope가 승인 범위를 벗어나면 거부해야 한다. 재시도는 Idempotency Key로 중복 실행을 방지하고, 타임아웃 이후에는 실행 결과를 확인한 뒤 재개한다.

로그·메트릭 수집L1 읽기 전용RBAC·민감정보 필터수집 자체가 업무 부하 유발
캐시 정리/서비스 재시작L3 승인형 검토단일 인스턴스·Drain·업무 검증DB 의존성 불명확, 피크 부하
K8s Pod 재생성L3 승인형 검토Replica 여유·PDB·Stateful 여부 확인단일 Pod·데이터 손실 위험
DB Failover/Restore수동 전문 승인RPO/RTO·복구 시험·DBA 확인복제 지연·정합성 미검증
방화벽/WAF 정책 변경보안 승인 필수범위 제한·만료·회귀 시험보안 통제 약화·전체 허용

롤백은 변경 전 상태를 되돌리는 기술 절차와 사용자 업무 정합성 확인을 함께 포함한다. 데이터 변경이 이미 발생했다면 이전 바이너리 배포만으로 롤백이 완료되지 않는다. 실행 전·후 SLI, 오류율, DB 상태, 감사기록을 비교한다.

기술적 부채

'모든 502를 Proxy 재시작으로 해결' 같은 단일 규칙은 원인을 가리고 장애를 재발시킨다. 증거가 부족하면 자동 실행이 아니라 진단 중단과 사람에게 에스컬레이션한다.

운영자/On-call증거 검토·실행 승인·업무 복구 검증

업무 책임자핵심 업무 영향·복구 수용 확인

  • 가짜 오류·SLO 위반·수집 결손을 각각 주입해 정확한 알림을 확인했는가?
  • 권한 없는 실행·승인 만료·대상 범위 초과를 강제로 거부하는가?
  • 중복 요청, 실행 중단, 네트워크 타임아웃 후 재시도 안전성을 시험했는가?
  • 모든 실행에 변경 ID·승인자·명령 버전·결과·원복 여부가 남는가?
  • 장애 복구 뒤 로그인·조회·저장·UC 주요 기능을 실제 검증하는가?

향후 확장 순서는 읽기 전용 진단 정확도 → 서비스별 SLO → 승인형 복구 → 안전성 실증이다. 먼저 데이터가 믿을 만한지 확인하고, 이후 실행 권한을 좁은 범위에서 점진적으로 늘린다.
