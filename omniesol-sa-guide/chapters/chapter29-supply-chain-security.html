공개 교육용 참조 설계

실제 고객·내부 시스템 정보, 인증정보, 비공개 구성은 포함하지 않는다. 모든 공격·복구 실습은 격리된 환경에서 수행한다. 실제 지원 버전·계약·보안 정책이 우선한다.

참조 아키텍처

Developer → Reviewed PR → CI (SAST/SCA/Secret Scan)
         → Isolated Build → SBOM + Provenance + Signature
         → Artifact Registry → Admission Policy
Operator (SSO/MFA) → Controller → Policy Engine
                                 ↓ Approved job (TTL, hash)
                         Isolated Action Runner → ERP/UC/DB
                                 ↓
                          Immutable Audit Evidence

확장성: 테넌트별 큐와 Runner 동시성 한도를 두고 중앙 Policy Engine·Audit Store의 병목을 측정한다. 보안: 신원·승인·실행·감사 경계를 분리하고 변경 권한은 기본 거부한다.

29.1 자동화 플랫폼의 공격 표면

운영 자동화는 SSH/API 토큰과 변경 권한을 집중하므로 일반 대시보드보다 침해 영향이 크다. 개발자 계정 → 소스 → CI → 패키지 저장소 → Runner → 대상 서버를 하나의 신뢰 사슬로 검토한다. 악성 의존성, 오염된 빌드, 장기 토큰, 승인 우회가 대표적인 위협이다.

29.2 SBOM·서명·출처 증명

SBOM은 구성 요소 목록이며 무결성 또는 안전성의 증명은 아니다. SHA-256은 전송 변조를 탐지하지만 공격자가 해시와 파일을 함께 바꾸면 방어하지 못한다. 신뢰된 빌드 주체의 서명과 provenance, 검증 키 관리, 배포 시 검증을 결합한다.

29.3 배포 게이트

Pull Request 검토 → 고정된 의존성 설치 → SAST·SCA·Secret Scan → 격리 빌드 → SBOM·서명·provenance 생성 → 정책 평가 → 승인 → 배포 → 실행 시 서명 재검증. 취약점 점수만으로 판단하지 않고 실제 노출 가능성, 수정 가능 버전, 예외 만료일을 기록한다.

29.4 키·토큰·이미지 관리

CI 장기 비밀키 대신 가능한 경우 OIDC 기반 단기 자격증명을 사용한다. 토큰은 환경·역할별로 분리하고 최소 권한을 적용한다. 컨테이너 이미지는 mutable tag가 아닌 digest로 고정하고 레지스트리 접근과 이미지 서명 검증을 통제한다.

29.5 공급망 위협 모델과 비교

빌드 서버 자체가 침해되면 단순 해시 비교는 무력화될 수 있다. 서명만 적용해도 신뢰할 수 없는 서명자가 발급하면 의미가 없다. 격리된 빌드·다중 승인·배포 검증은 비용과 배포 시간을 증가시키지만 운영 변경 권한을 가진 시스템에서는 합리적이다.

29.6 현장 검수

SBOM 존재, 서명자 신원, 아티팩트 digest, 정책 버전, 승인자, 배포 환경, 롤백 이미지 digest를 하나의 릴리스 ID로 연결한다. 임의 변조된 테스트 아티팩트가 거부되는지 검증한다. 서명 검증 실패 시 배포는 FAIL-CLOSED로 중단한다.

현장 점검 및 참고 표준

검증은 요청 ID, 정책 버전, 아티팩트 digest, 승인자, 대상 ID, 결과 로그로 추적한다. 기준 자료: SLSA v1.0, NIST SSDF SP 800-218, OWASP Top 10, Kubernetes Security. 제품별 지원 여부는 별도 검증한다.
