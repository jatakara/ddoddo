17.7 RHEL/OS 하드닝의 기본

OS 보안은 지원 버전, SELinux, 호스트 방화벽, 관리자 접속, 서비스 최소화, 시간 동기화, 패치와 로그를 함께 관리한다. ERP/DB 서버는 커널·라이브러리 의존성이 있으므로 하드닝 스크립트의 일괄 적용 전에 제품 호환성을 검증한다.

통제검증 질문운영 위험
OS·패치제품이 해당 커널·패키지를 지원하는가?비검증 업데이트로 서비스 장애
SELinuxEnforcing·거부 로그·정책 예외를 확인했는가?무조건 Disabled로 보호 상실
firewalld업무별 최소 허용 포트가 일치하는가?API·클러스터 통신 차단
SSH/sudo관리망·개인 계정·감사 정책을 적용했는가?공용 관리자·과권한
서비스·NTP미사용 데몬·시간·로그 보존을 확인했는가?공격 표면·토큰 검증 실패
# 읽기 전용 OS 점검 예시
cat /etc/os-release
uname -r
getenforce
sestatus
systemctl is-active firewalld
systemctl is-active chronyd
ss -lnt
하드닝 금지 패턴

SELinux나 firewalld를 무조건 비활성화하는 것을 보안 표준으로 제시하지 않는다. 차단된 업무 경로는 거부 로그·정책 분석과 승인된 최소 예외로 해결한다.

17.8 TLS·Reverse Proxy·WAF 보안

Reverse Proxy는 보안과 가용성의 공통 경계다. TLS 종료, 인증 헤더 전달, 요청 크기·타임아웃, WebSocket/SSE, WAF 검사는 서로 영향을 준다. ERP 화면과 UC 실시간 기능의 트래픽 특성을 고려해 정책을 검증한다.

통제검증 내용Trade-off
TLS안전한 프로토콜·암호군, 체인·만료, 클라이언트 호환성구형 클라이언트 영향
HSTSHTTPS 전환 후 단계적 도입오설정 시 장기 접속 장애
CSPReport-Only로 위반 수집 후 적용외부 스크립트·포털 영향
쿠키·캐시민감 응답 no-store, Secure/HttpOnly/SameSiteSSO·임베디드 앱 영향
WAF오탐·파일 업로드·압축·API 검사 검증정상 요청 차단
Proxy 헤더신뢰된 상위 Proxy의 Forwarded 헤더만 수용원본 IP 위조·감사 왜곡
# 가상 도메인에서 비파괴적으로 확인
curl -I --connect-timeout 5 https://erp.example.invalid/
openssl s_client -connect erp.example.invalid:443 \
  -servername erp.example.invalid -brief < /dev/null

응답 헤더·인증서의 공개 정보만 점검한다. 인증서 개인키·실제 내부 주소·비공개 헤더는 공개 GitHub나 외부 검사 서비스에 업로드하지 않는다.

운영 검증

WAF 정책 변경 후 로그인·파일 업로드·모바일 API·WebSocket/SSE·대용량 보고서의 회귀 시험을 수행한다. 요청 ID와 WAF 차단 로그를 연결해 오탐 원인을 판단한다.

17.9 Kubernetes RBAC·Pod Security·NetworkPolicy

Namespace는 자원·권한 구분에 유용하지만 물리적 격리나 완전한 보안 경계가 아니다. RBAC, Pod Security Admission, NetworkPolicy, 이미지 공급망, 노드/API 보안을 함께 설계한다.

통제검증흔한 실수
RBAC사용자·ServiceAccount의 실제 권한 범위cluster-admin 상시 부여
Pod SecurityBaseline/Restricted 지원성 시험일괄 Enforce로 업무 Pod 차단
NetworkPolicyCNI의 집행 기능과 Ingress/Egress 시험YAML 존재만으로 차단된다고 믿음
Pod 설정root·privileged·hostPath·seccomp 점검불필요한 호스트 권한
이미지digest·출처·취약점·서명/무결성latest 태그만 사용
API/Node인증서·감사·관리망 접근 제한관리 API 사용자망 노출
# 승인된 조회 권한으로만 실행
kubectl get namespaces
kubectl get networkpolicy -A
kubectl get rolebindings,clusterrolebindings -A
kubectl -n example-uc get serviceaccounts
kubectl -n example-uc get pods -o wide
kubectl auth can-i get pods -n example-uc
CNI 전제

NetworkPolicy는 지원 CNI가 집행해야 효력이 있다. L3/L4 정책은 업무 인가·TLS·WAF를 대체하지 않는다. 송신 Egress와 수신 Ingress를 함께 검증한다.

17.10 NetworkPolicy 도입 순서와 실패 사례

기본 차단(Default Deny)은 유용하지만 DNS, IdP, 외부 API, 모니터링, DB 연결까지 막을 수 있다. 흐름 관찰 → 허용 목록 설계 → 비운영 적용 → 정상·거부 시험 → 점진 배포 순서를 따른다.

단계작업합격 기준
1. 흐름 수집Pod↔Pod, DNS, IdP, DB, 외부 API 의존성 확인업무·배치·헬스체크 포함
2. 정책 설계Pod/Namespace label·Ingress/Egress 명시허용/차단 기대 결과 확정
3. 비운영 시험동일 CNI·버전에서 정책 적용로그인·파일·알림·모니터링 정상
4. 거부 시험비허용 Pod의 API/DB 연결 거부 확인거부 증거 확보
5. 운영 적용승인된 변경창·관측·원복 계획오류율·SLO 미악화
가상 장애 사례

UC Pod의 DB 접근만 허용했더니 로그인에 필요한 DNS/IdP 호출이 차단되었다. 정책의 강도만 평가하지 말고 실제 업무와 서비스 의존성을 검증해야 한다.

17.11 비밀정보·인증서·키 관리

비밀번호, API 토큰, DB 연결 문자열, TLS 개인키는 일반 설정값이 아니다. Git 저장소, 배포 스크립트, 로그, 메신저에 복사하면 노출 이력을 회수하기 어렵다. Kubernetes Secret의 base64 값은 암호화가 아니므로 etcd 암호화, RBAC, 외부 비밀 저장소 사용을 검토한다.

비밀보관 원칙교체 검증
DB 비밀번호비밀 저장소·서비스별 최소 권한새 값 반영·DB 풀 재연결
TLS 개인키접근 제한·갱신·백업 통제인증서 갱신·롤백
OIDC 비밀환경별 분리·노출 탐지기존/신규 키 전환
K8s Secretat-rest 암호화·RBAC·필요 Pod만 제공Pod 재시작/재배포 필요성
백업 키백업 데이터와 별도 보관·권한 분리키 복원 가능성
  • 키 교체는 생성 → 지원 시 병행 유효 기간 → 의존 서비스 전환 → 기존 키 폐기 → 감사 확인 순으로 진행한다.
  • Git에서 비밀을 삭제하는 것만으로 유출이 해결되지 않는다. 노출 값 폐기·재발급과 접근 이력 평가가 필요하다.
  • 환경변수, Pod spec, 진단 덤프, 로그를 통한 우발적 노출을 점검한다.

17.12 DB·백업·소프트웨어 공급망

DB 보안은 Listener 포트 차단만으로 끝나지 않는다. 계정 권한, 감사, 암호화, 백업 보관·복원, 키 관리, DBMS 라이선스 조건을 함께 검토한다. Oracle 보안 옵션은 에디션·계약·버전별 지원 조건을 확인해야 한다.

영역통제·검증Trade-off
DB 계정업무 스키마 최소 권한, 관리자 분리기존 SQL/배치 영향
데이터 암호화전송·저장 암호화, 키 관리, 라이선스CPU 비용·키 유실 위험
백업암호화·권한 분리·변조 방지·복원 시험비용·복구시간 증가
패키지·이미지지원 버전·SBOM·무결성·취약점 점검패치 호환성
CI/CD배포 계정·Artifact 접근·승인공급망 침해 시 확산
확장성과 보안

TLS·WAF·감사·암호화는 CPU와 I/O 비용을 증가시킬 수 있다. 16장 Capacity Planning의 p95·오류율·N+1 기준선과 보안 변경 전후 성능을 비교한다.
