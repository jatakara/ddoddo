12장 3부. 운영·복구·승인

12.9 데이터·백업·DR

ERP DB, UC DB, 파일 저장소, 캐시 등 상태 저장 요소는 제품 지원 구조에 따라 배치한다. 공유 스토리지라도 데이터 소유권, 보존 기간, 백업 주기, 복구 권한은 분리한다. ERP는 트랜잭션 정합성과 시점 복구(PITR), UC는 DB 메타데이터와 첨부파일의 일관성을 확인한다. PV/PVC와 스냅샷만으로 백업이 완성되지 않는다. RPO/RTO는 업무별로 합의하고 실제 복원 시험으로 검증한다.

12.10 운영 관측과 1차 진단

클러스터 평균 CPU가 아니라 ERP 업무 p95/p99, UC 로그인·메시지·첨부 처리, HTTP 오류율, DB 대기, Node Pressure, 스토리지 지연을 동일 시간축에서 분석한다.

kubectl get nodes -o wide
kubectl get pods -A -o wide
kubectl get events -A --sort-by=.lastTimestamp
kubectl get resourcequota,limitrange -n erp
kubectl get resourcequota,limitrange -n uc
kubectl get deploy,hpa,pdb -n uc

위 명령은 읽기 전용 예시다. Namespace는 실제 환경에 맞춘다. ERP·UC가 동시에 느리면 DNS, LB, Ingress, Node, Storage, SSO 등 공통 계층부터 조사한다.

12.11 운영 전 검증

시험합격 기준
ERP 마감 + UC 혼합 부하서비스별 SLO와 오류율 충족
Worker 1대 장애필수 Pod 재배치 및 업무 복구
UC 부하 급증ERP 지연 영향 허용 범위 이내
Ingress/SSO 장애복구 경로와 사용자 영향 확인
백업 복원RPO/RTO와 데이터 정합성 검증

장애 주입은 승인된 시험 환경에서 변경 승인·롤백 계획을 확보한 후 수행한다.

12.12 Go/No-Go

  • □ ERP·UC 실행 위치와 공통 자원이 명확하다.
  • □ 제품 공식 지원 구성과 라이선스를 확인했다.
  • □ 피크 및 노드 장애 후 자원 여유를 검증했다.
  • □ 혼합 부하에서 SLO를 충족했다.
  • □ RBAC·NetworkPolicy·Pod Security·Secret 관리가 검증되었다.
  • □ 공통 장애 지점과 백업 복구를 시험했다.

미지원 배포, ERP SLO 침해, 장애 후 재배치 불가, 복원 실패는 운영 승인 보류 사유다.
