2장. System Landscape와 환경 분리

개발·검증·운영 환경과 서비스·데이터·접속 경로를 구분하여 운영 가능한 시스템 지도를 작성한다.

독립 교육용 참조 원고

OmniEsol의 공식 설치·지원 사양을 대신하지 않는다. 구성 예시와 명령은 학습 및 검토용이며, 실제 고객 환경에서는 계약 범위·검증 버전·보안 정책·변경 승인을 확인한다.

2.1 Landscape란 무엇인가

System Landscape는 서버 목록이 아니라 서비스를 구성하는 시스템들의 배치·관계·환경·책임을 나타낸 것이다. 같은 제품이라도 고객사 IDC, 프라이빗 클라우드, 외부 사용자 접속, 독립 백업망 여부에 따라 물리 구조는 달라진다.

그림은 단계의 논리적 흐름을 나타낸다. 백업/DR은 단순히 운영의 마지막 단계가 아니라, 운영과 독립적으로 복구 가능해야 하는 경계다.

2.2 개발·검증·운영 분리의 실질적 의미

영역목적반드시 달라야 할 것
DEV신규 기능·설정 변경운영 데이터 및 외부 연계와 차단
STAGE최종 릴리스·장애 시나리오 검증운영과 유사한 버전·정책·용량 가정
PROD기업 핵심업무 지속승인 기반 변경, 감사, 백업
DR중대한 장애 이후 업무 복구별도 장애 도메인과 정기 복구 시험

환경 구분은 Namespace를 나누는 수준에 그쳐서는 안 된다. 계정·인증서·DB·외부 연계·비밀정보·방화벽 정책도 구분해야 한다. 테스트에 운영 DB 덤프를 복사하려면 개인정보 비식별화와 접근통제가 선행돼야 한다.

예제

DEV와 PROD가 서로 다른 URL을 사용하더라도 같은 Oracle 데이터베이스나 같은 파일 저장소를 사용하면 데이터 경계가 성립하지 않을 수 있다.

2.3 시스템 구성요소 목록화 방법

아키텍처 작성의 첫 작업은 논리 서비스와 실제 배포 단위를 매핑하는 것이다. ERP 화면은 한 URL이지만 뒤에서는 WEB, WAS, DB, 외부 인증과 파일 저장 등이 동작할 수 있다. 목록에는 호스트 이름만 적지 않는다.

항목예시(가상)왜 필요한가
서비스/역할ERP WEB, WAS, DB, UC Gateway장애 영향 범위 파악
배포 위치VM/물리/K8s, AZ 또는 랙공통 장애 원인 검토
연결HTTPS 443 → WEB → WAS방화벽과 관찰 지점 확정
데이터DB, 공유 스토리지, 세션 저장RPO와 백업 책임
소유자운영·DBA·네트워크·보안에스컬레이션 경계

IP와 호스트명은 관리 문서의 접근 제한 영역에 따로 보관하고 공개 기술서에는 가상 예제만 사용한다.

2.4 가용성·복구목표·공통 장애 도메인

가용성은 서버 대수보다 단일 고장으로 함께 멈추는 범위에 좌우된다. ERP와 UC를 별도 VM에 구성해도 같은 물리 호스트, 스토리지, L4, 외부 DNS를 쓰면 특정 장애를 공유한다.

개념질문검증 사례
HA하나가 죽어도 서비스가 이어지는가?노드 1대 강제 종료 후 업무 테스트
RTO얼마나 빨리 업무가 복구돼야 하는가?실제 복구 훈련 소요 시간
RPO어느 시점까지 데이터 손실을 허용하는가?로그 적용·백업 복구 지점
DR주센터가 불능이면 어디서 복구할까?DNS 전환·데이터 정합성·권한 검증

RTO 2시간, RPO 15분은 예시 목표일 뿐 권장 수치가 아니다. 업무 중요도와 고객 승인에 따라 목표와 비용이 결정된다.

2.5 네트워크 신뢰 구간과 이름 해석

같은 서비스 이름을 내부·외부 사용자가 접근한다고 해서 경로까지 같을 필요는 없다. Split DNS를 사용하는 경우 동일 FQDN에 내부/외부 IP를 다르게 응답할 수 있다. 단, 인증서, 포털 링크, API 호출, 모바일 접근까지 고려해야 한다.

외부 사용자 → 외부 DNS → WAF/Proxy → 허용된 서비스
내부 사용자 → 내부 DNS → 내부 LB/Proxy → 허용된 서비스
앱서버 → 내부 DB: 명시적 최소 허용 포트
운영 관리망 → 관리 API/SSH: 승인 계정 및 감사 로그
실무 위험

외부 사용자에게 WEB만 열었는데 애플리케이션이 내부 전용 주소로 API를 호출하면 화면 일부만 실패할 수 있다. 사용자별 요청 흐름을 단위 테스트한다.

2.6 Landscape 검수 항목

  • DEV/TEST/PROD/DR 각각에서 코드·계정·데이터·인증서를 구분했는가?
  • ERP/UC 접속 경로와 공통 인프라 의존성을 도면에 표시했는가?
  • DNS, L4, 스토리지, 하이퍼바이저 장애 시 영향을 분석했는가?
  • RTO/RPO를 숫자로 합의하고 복구 테스트로 검증했는가?
  • 고객사와 구축사 간 운영 권한 및 변경 승인자를 문서화했는가?

이 장에서 작성한 Landscape는 4장 배포 모델 비교와 7장 Sizing의 입력 자료가 된다. 구성도를 먼저 정하지 않고 서버 자원만 계산하면 중요한 공통 인프라와 복구 구성이 누락되기 쉽다.
