19.7 OS·JDK·WEB/WAS 패치 순서

OS와 런타임 패치는 단순한 보안 패치가 아니다. 커널 변경은 재부팅을 요구할 수 있고, JDK와 WAS 변경은 애플리케이션의 클래스 로딩·TLS·JDBC·GC 동작을 바꿀 수 있다. 제품 지원 Matrix와 릴리스 노트의 Known Issue를 확인한 후 비운영 환경에서 먼저 검증한다.

대상사전 확인적용 후 확인롤백 주의
RHEL/Kernel패키지 목록·커널·드라이버·서브스크립션부팅·NIC·스토리지·SELinux·서비스패키지 다운그레이드만으로 상태 완전 복원 불가
JDKWAS/애플리케이션 호환성, 인증서·CipherJVM 기동·GC·JDBC·TLS·업무 회귀구 JDK와 배포물 보존
WebtoB/JEUS지원 버전·설정 diff·모듈 호환성구문 검증·연결 풀·Proxy·세션설정 백업과 데이터 의존성 분리
Proxy/WAFHTTP/2, SSE, WebSocket, Timeout, URI 정책정상 업무·장시간 연결·보안 차단오탐 해제와 무분별한 모두 허용 구분
# 읽기 전용 변경 전 Baseline 예시 (RHEL 계열)
cat /etc/os-release
uname -r
rpm -qa | sort
dnf history list
systemctl --failed
ss -lnt
# 승인된 환경에서 결과를 보안 저장소에 보관; 계정/비밀정보 제외

운영 환경에서는 벤더 공식 절차와 유지보수 창을 따르며, 패키지 일괄 업데이트 또는 자동 재부팅을 승인 없이 수행하지 않는다.

19.8 WEB/WAS와 Reverse Proxy의 롤링 교체

WEB/WAS가 2대 이상이면 순차 교체를 고려할 수 있다. 그러나 DB·공통 세션 저장소·인증서·Proxy 라우팅이 단일 장애점이면 ‘AP 2대’만으로 무중단을 보장하지 않는다. 긴 요청, 파일 업로드, 배치, WebSocket, SSE 등 연결 유형별 종료 정책을 정한다.

기능검증 조건
세션Sticky/공유 세션 정책에 따른 재로그인·세션 손실
장시간 요청파일 업로드·보고서·배치의 Drain/Timeout
TLS/ProxyHost, X-Forwarded-*, SNI, Rewrite, HTTP/2
SSE/WebSocket연결 끊김 시 재연결·이벤트 중복/유실 처리
DB Pool교체 중 연결 폭증·Lock·Failover 영향
롤링의 한계

1대 구성에서는 Drain 대상이 없어 중단이 발생할 수 있다. 무중단 요구가 있다면 가용 노드, LB 정책, 배포 중 임시 자원, 애플리케이션 상태 외부화가 필요하다.

19.9 Oracle/Tibero DB 변경과 Expand–Migrate–Contract

DB 스키마 변경은 애플리케이션 바이너리 교체와 다르다. 컬럼 삭제·타입 변경·대량 UPDATE는 과거 버전 코드의 실행을 불가능하게 만들 수 있다. 안전한 일반 패턴은 Expand → Migrate → Contract다. 실제 지원 범위와 DDL 동작은 해당 DBMS 버전의 공식 문서를 확인한다.

단계예시기술 검증
Expand기존 컬럼을 유지한 채 신규 nullable 컬럼 추가신·구 앱 모두 정상
Migrate배치 단위 Backfill, 읽기/쓰기 경로 점진 전환Lock·Redo·Replication Lag·검증 건수
Contract구버전 사용 종료 후 이전 컬럼 제거승인된 별도 릴리스·복구계획
가상 데이터 이행 통제표
변경 ID: DB-EXAMPLE-019
영향 테이블/인덱스: [스키마 소유자 검토]
변경 전 row count / checksum: [승인된 집계]
Batch 크기·중단 조건: [부하 시험 근거]
대기 이벤트 / Redo / Undo / Archive 여유: [실측]
애플리케이션 호환 버전: old=N, new=N+1
데이터 복원 전략: [RMAN/PITR/논리 역변환 검증]
정합성 서명: [DBA + 업무 책임자]

Oracle DDL의 암묵적 Commit, 데이터 손실 가능성, 복구 목표를 고려한다. Guaranteed Restore Point는 전제조건과 FRA 공간이 필요하며 DB 전체 복구 시점을 다루므로, 일반적인 애플리케이션 패치 롤백 버튼처럼 취급하면 안 된다.

비가역성 주의

과거 WAS 버전으로 되돌려도 이미 삭제·변환된 데이터가 자동으로 복원되지는 않는다. DB 마이그레이션이 포함되면 ‘바이너리 롤백’과 ‘데이터 복구’의 승인 절차를 분리한다.

19.10 Kubernetes Deployment 롤링과 가용성

Deployment의 RollingUpdate는 새 Pod를 단계적으로 준비하고 이전 Pod를 교체하는 기능이다. 무중단을 보장하려면 준비된 Replica 수, 자원 여유, readinessProbe, 서비스 연결, 앱 호환성이 모두 충족되어야 한다. Pod가 Ready여도 ERP/UC의 실제 거래 성공 여부는 별도로 검증한다.

# 승인된 읽기 전용 상태 점검 예시
kubectl -n example-uc get deployment
kubectl -n example-uc get pods -o wide
kubectl -n example-uc get endpointslices
kubectl -n example-uc rollout history deployment/example-api
kubectl -n example-uc rollout status deployment/example-api --timeout=5m
kubectl -n example-uc describe deployment/example-api
설정/기능목적실패 모드
replicas >= 2배포 중 서비스 여유1 Replica만으로 무중단 보장 불가
maxUnavailable=0준비된 기존 Pod 최소 수 유지Surge 용량 부족 시 배포 정체
maxSurge=1신규 Pod 임시 추가CPU·메모리·Pod/IP 부족
readinessProbe준비되지 않은 Pod로의 트래픽 방지피상적 200 응답으로 조기 Ready
PodDisruptionBudget자발적 중단 제약배포 자체의 모든 가용성 위험을 해결하지 않음
revisionHistoryLimit이전 Pod 템플릿 보존DB·PVC·Config 외부 상태는 복원 안 됨

공식 Kubernetes 문서는 Deployment 롤백이 Pod 템플릿 변경 이력에 기반한다고 설명한다. DB 스키마, 영속 데이터, 외부 시스템 상태는 함께 되돌아가지 않는다.

19.11 ERP·UC 연계와 계약 호환성

ERP와 UC가 다른 배포 주기로 운영되면 구버전과 신버전이 일정 시간 공존한다. 이때 HTTP API, 토큰, 메시지 스키마, 파일 URL, SSO Redirect가 호환되지 않으면 두 서비스 모두 정상 상태인데 일부 기능만 실패한다.

계약배포 전 검증배포 후 증상
API 필드/URI구/신 소비자·공급자 계약 테스트404·400·역직렬화 오류
SSO/토큰서명·Audience·쿠키·만료·Redirect로그인 반복·권한 오류
모바일 URL내부/외부 DNS·Proxy·호출 도메인특정 망에서 메뉴만 실패
비동기 메시지이벤트 버전·멱등성·재처리중복 처리·지연·유실
파일/첨부권한·서명 URL·저장소 매핑다운로드 실패·메타데이터 불일치

호환성이 불명확한 경우 기능 플래그로 신규 호출을 비활성화한 채 공급자 API를 먼저 배포하고, 계약 시험 이후 소비자 기능을 개방한다. 플래그 역시 만료일과 소유자가 필요하다.

19.12 플랫폼 업그레이드의 확장성·보안 판단

패치와 업그레이드는 취약점 감소뿐 아니라 운영 부채를 줄이는 기회다. 다만 대규모 일괄 교체는 원인 추적이 어렵다. 컴포넌트별 Change Set과 Baseline을 유지하고, 단일 실패 지점부터 제거하는 순서를 설계한다.

의사결정장점비용/위험
인플레이스 업데이트장비/구성 변경 적음원복 어려움·환경 Drift
블루/그린검증된 신규 환경으로 트래픽 전환이중 자원·데이터 동기화 필요
카나리/점진적영향을 제한해 지표 기반 전환세션·버전 혼재·트래픽 분리 복잡
전체 중단 창정합성/변경 경계 단순업무 중단·복구 창 확보 필요
  • 보안: 이미지/패키지 서명, SBOM, 취약점, Secret·관리자 권한, 감사 로그를 검토한다.
  • 확장성: 배포 중 N+1, DB Pool, 배치 피크, K8s Surge 자원을 확인한다.
  • 운영성: 승인·원복·관찰·고객 공지 담당자를 명시한다.
  • 데이터: 업그레이드 후에도 이전 DB·백업 도구로 복구 가능한지 별도 검증한다.
